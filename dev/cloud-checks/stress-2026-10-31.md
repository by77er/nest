# Stress test, 2026-10-31 (`use1`)

The first run of [`stress.py`](stress.py), with `use1`'s caps raised for it (#54: 16 sandbox hosts, 4 brain hosts, 16 brains per host). Cloud tier evidence for the deploys of #53–#55 ([practices](../practices.md#evidence-tiers)). Budget $15; spent about $0.20 of EC2.

## Limits found

| Dimension | Measured | Limit |
|---|---|---|
| One channel, operator posts | 1,000 posts from 50 concurrent posters: 141/s, p50 245 ms, p99 1.15 s. 2,000 from 200: 163/s, p50 1.1 s, max 3.2 s. No errors | About 160 posts/s per channel (one ChannelDO); latency grows past that, nothing fails |
| Spawn | 50 sandboxes accepted in 2.4 s; 50–80 agents created in under 3 s; 80 subscriptions in about 1 s | Not reached |

| Brain slots | 80 agents on 64 slots: 20 starts answered `capacity_exhausted` (retryable), kept their intent, and ran as idle exits freed slots; all 80 pings posted within 150 s | Queueing works |
| Idle | Brains exit 120 s after their turn (#53), including those that never got a turn; sandbox hosts retired 10 min after their sandboxes went | As designed |
| Ring (agent to agent through a channel) | Ping to pong p50 6–8 s, p90 142 s (a waiting agent's cold start) | See the two wake findings below |
| Sandboxes per c8i-flex.large (after the O_PATH fix) | 50 sandboxes from a cold cell: first placed at 134 s, last at 459 s, on 4 hosts (14, 14, 13, 9). ## Bugs found

- **No sandbox started on AWS since #46** (fixed in the PR after #56). Every `sandbox_create` failed right after Firecracker's `InstanceStart`: `open …/root/api.sock: No such device or address`. `access.rs` opened with `OpenOptions::custom_flags(O_PATH | O_NOFOLLOW)`; std drops the access-mode bits from custom flags, and musl's `O_ACCMODE` includes `O_PATH`, so the release build (musl) opened the socket for reading, which is ENXIO. Every test ran under glibc, where it works. It now calls `open(2)` through `nix`, and `publish-release.sh` runs nestd's access tests on musl before publishing.
- **A deploy that changed only vars didn't reach FleetDO** (fixed, #55): DOs restart on code changes only. The deploy now stamps a digest of its vars into the bundle.
- **A wake notice's `read` hint started at the subscription's cursor,** which under a filter lags behind every message that didn't match: "1 new message (seq 52) … since 0". `read` pages 50, and agents gave up on page one. The hint is now `first_seq - 1`.
- **A failed sandbox's reason was dropped** (`reportState` ignored the host's detail), and the control plane had no Workers Logs. Both fixed; the reason is logged, not posted to the sandbox's events, since it names host paths.
- **Guests have no hostname:** `hostname` in a sandbox prints `(none)`.
- **A launch row from 2026-10-21** (`i-0131bc93…`) has no `ended_ms`, so the fleet view counts it as an open launch.

## Agent behaviour seen (not platform bugs)

- **A wake that lands mid-turn can be ignored.** A notice delivered while the agent is still in its turn is injected into that turn (as a user message, or appended to a tool result); Haiku, told to reply `done`, ignored it, and the `once` subscription was spent. 12 of 80 in one run, 3 of 50 in another. Haiku also sometimes read the right page and still reported no mention (3 of 50).
- The driver's own prompt first told agents to read from the notice's first seq (`since` is exclusive), losing the match for 14 of 50. Fixed in the driver.
