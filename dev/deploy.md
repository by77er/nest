# Deploy

**Decided: merges deploy to production automatically, and a health window rolls back on regression.** Nothing deploys from a branch, and agents never hold deploy credentials. The workflows follow the platform's [upgrade rules](../docs/control-plane/#upgrades).

**Built (`deploy.yml`, first cut):** after `ci.yml` passes on a push to `main`, or by `workflow_dispatch`, three jobs run in order. All three use the `production` environment and the cell's deploy role over OIDC.
1. **`infra`:** `inframe test` and `plan` (the plan's summary goes in the run summary), then `apply` for `use1`.
2. **`worker`:** `dev/deploy-use1.sh`, then `GET /v1/health` for up to two minutes. The script stamps a digest of every var into the bundle (`--define __NEST_CONFIG__`, shown as `config` in `/v1/health`): Durable Objects restart only when a deploy changes code and keep the env they started with, so a deploy that changed only vars (a cell's caps in `AWS_CELLS`) left FleetDO on the old config (seen 2026-10-31). Even then it isn't instant: after #58's deploy a FleetDO held up by connected hosts answered with the new caps about 5 min later. The same lag applies to new code: a route that calls a DO method the release added answers 500 until that DO restarts ([upgrades](../docs/control-plane/#upgrades); about 5 min for `/v1/admin/lifetimes` on 2026-11-01). The health check doesn't see it: it calls `health()` on each class's own `~health` instance, never on a busy one like a cell's FleetDO (that an idle instance takes new code at once is unverified). So a post-deploy cloud check of a new route retries for 10 minutes before it counts as a failure. If the health check fails, `wrangler rollback` returns to the previous version.
3. **`release`:** `scripts/publish-release.sh` builds the host binaries (static, musl) into `releases/current/`, which every host installs at boot. It first runs nestd's file-access tests on musl: CI tests under glibc, and std's `custom_flags` behaved differently under musl (it dropped `O_PATH`, so no jailed VM could start).
   - Firecracker, the jailer, the guest kernel and the guest image carry over from the current release.
   - If no file changes, nothing is published.
   - If the build's inputs (`crates/`, `protocol/`, the Cargo files, the toolchain, `.cargo/`, the script, by git object id) match a previous deploy's that published or found nothing to publish, nothing is built: an actions-cache marker saved after that publish says so. A dispatch always builds.
   - When it does publish, a host AMI build starts.

**The `edge` stack** (`deploy/lean/Edge/`): Cloudflare Access in front of the gateways (`*-gw-nest`, Service Auth for the one service token in `access:gateway`, 401 for a machine without it), the dashboard (`dash-nest`, the owner's login) and previews (`*-preview-nest`, the owner's login). The infra job plans and applies it after the cell when the `production` environment carries `CLOUDFLARE_ACCESS_API_TOKEN` (a Cloudflare token with Account › Access: Apps and Policies › Edit), and skips it with a notice otherwise. Applications created by hand before the stack existed are imported once, not recreated: `inframe tofu --stack edge -- import cloudflare_zero_trust_access_application.<name> <account id>/<application id>` for each, then a plan shows only the differences the stack settles. Done for `use1` on 2026-10-24: the gateway and dashboard applications were imported; the stack moves their policies inline (the old reusable policies stay in the account, unattached) and creates the previews application.

**The `projects` stack** (`projects/deploy/`) is the projects app's own, not nest's: Cloudflare Access in front of `projects-nest.bitcru.sh` (the owner's login; `/hooks` and `/mcp` bypassed), with its own state key (`projects/projects.tfstate`). `deploy-projects-infra.yml` tests, plans and applies it only on a push to `main` that touches `projects/deploy/` (or by hand), apart from this deploy, with the edge stack's `CLOUDFLARE_ACCESS_API_TOKEN` and the deploy role for the state, and skips the plan and apply with a notice without the token. The run summary shows `projects_aud`, the app Worker's `PROJECTS_AUD` ([projects/deploy/](../projects/deploy/README.md)).

**`AWS_CELLS` is the cell stacks'** (`aws_ssm_parameter.aws_cells`): each cell stack writes its own entry, `{"<cell>": {...}}`, to `/nest/control-plane/aws-cells/<cell>`, built from its launch template, subnets and proxy root CA key and from `CellSpec` (instance types, which `launch_types_within_iam` keeps inside IAM's `EightIOnly` patterns; spot, max hosts, timers, the regular-pages reserve). `dev/deploy-use1.sh` merges every parameter under that prefix after the apply, so a replaced template, subnet or key reaches the Worker on the same run, and no cell stack overwrites another's entry ([cells](../docs/compute/cells/)); a parameter whose one key isn't its own cell name fails the deploy. A cell outside us-east-1 isn't supported yet: its stack would write its parameter in its own region, while the script reads us-east-1 and sets `CELLS=use1`. The first apply that moves the parameter from `/nest/control-plane/vars/AWS_CELLS` replaces it (the plan shows `-/+` on `aws_ssm_parameter.aws_cells`): the old parameter is deleted if it was imported into the stack's state, and left behind, unused, if it never was (delete it by hand).

**Per-cell AWS credentials: the owner's migration, before the release that drops the globals.** The Worker reads each cell's control-plane access key from the secret `AWS_CELL_CREDENTIALS`, region and KMS key from `AWS_CELLS`, and nothing else: a cell without an entry loses STONITH by EC2, autoscaling and root CA signing (enrollment fails). The release before it fell back to the legacy `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`, `AWS_REGION` and `ROOT_CA_KMS_KEY_ID`, and adopted `ROOT_CA_CERT_PEM` as the cell's certificate. Migrate while that release runs:
1. `GET /v1/admin/fleet?cell=use1` shows `aws.sources` as `{"region": "cell", "credentials": "legacy", "kms_key": "cell"}`.
2. Write `{"use1": {"access_key_id": "…", "secret_access_key": "…"}}` to a file outside the repo: an access key of `nest-use1-control-plane`, either the one in today's `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` or a new one. `dev/cell-credentials.sh check < file` validates it with the control plane's own schema, and `dev/cell-credentials.sh put < file` validates it and puts it with `wrangler secret put AWS_CELL_CREDENTIALS`, which deploys a new version at once. `aws.sources.credentials` then reads `cell`. A malformed entry that reaches the Worker anyway shows as `aws.error` (fields, never values).
3. `GET /v1/admin/root-ca?cell=use1` returns the certificate FleetDO keeps for the cell: on first use it adopted `ROOT_CA_CERT_PEM`, the certificate for the same key. Check that it matches the certificate baked into the guest image. This step must happen before the new release: it never adopts `ROOT_CA_CERT_PEM`, so a cell that kept no certificate would self-sign a new root its baked images don't trust.
4. Then delete the legacy secrets (`npx wrangler secret delete` `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `ROOT_CA_KMS_KEY_ID` if it is set as a secret, and `ROOT_CA_CERT_PEM`) and the SSM parameter `/nest/control-plane/vars/ROOT_CA_KMS_KEY_ID` (the new release's deploy no longer passes it). `aws.sources` should read `cell` for all three; after the new release deploys, `aws` shows `"credentials": true, "kms_key": true`.

**The dashboard deploys apart** (`deploy-dashboard.yml`): on a push to `main` that touches `dashboard/` (or by `workflow_dispatch`), `npm ci`, typecheck, tests, `vite build` and `wrangler deploy` of the `nest-dashboard` Worker to `dash-nest.bitcru.sh`, then `wrangler secret put NEST_ADMIN_TOKEN` from the `production` environment's secret when it is set. It needs no AWS role; it shares nothing with the platform deploy but the Cloudflare token.

**The projects app deploys apart too** (`deploy-projects.yml`): on a push to `main` that touches `projects/` outside `projects/deploy/` (or by `workflow_dispatch`), `npm ci`, typecheck, tests, `vite build` and `wrangler deploy` of the `nest-projects` Worker to `projects-nest.bitcru.sh`, then `wrangler secret put` of `NEST_CLIENT_TOKEN`, `NEST_WEBHOOK_SECRET` and `GITHUB_WEBHOOK_SECRET` from the `production` environment's `PROJECTS_NEST_CLIENT_TOKEN`, `PROJECTS_NEST_WEBHOOK_SECRET` and `PROJECTS_GITHUB_WEBHOOK_SECRET`, each when it is set. Without them the Worker serves and fails closed (503 on its nest calls, 401 on the hooks). Its Access stack is `deploy-projects-infra.yml`'s.

**Not built yet:** the pause, deploy classification, the metrics health window, `rollback.yml`, desired host versions with canaries, and guest image rebuilds (the sections below are the design). Rebuild the guest image by hand (`images/guest/build-on-ec2.sh`) when `nest-guest` changes.

**Credentials:**
- **AWS:** the cell stack's `nest-<cell>-deploy` role, assumed over GitHub OIDC. Its trust policy accepts only `repo:by77er@39721110/nest@1416068100:environment:production`: GitHub's immutable subject format for repositories created after 2026-07-15 carries the owner and repository ids, and `GET /repos/by77er/nest/actions/oidc/customization/sub` confirms it for this repo ([OIDC reference](https://docs.github.com/en/actions/reference/security/oidc)). Applying the stack manages IAM, so the role is administrator-equivalent; the trust policy is what limits it. The first apply of a cell runs by hand with the provisioner key: it creates the role that later applies assume.
- **Cloudflare:** `CLOUDFLARE_API_TOKEN` (Workers edit) and `CLOUDFLARE_ACCOUNT_ID` are secrets on the `production` environment, and so is `CLOUDFLARE_TUNNEL_API_TOKEN` (Account: Cloudflare One Connector: cloudflared → Edit, Zone: DNS → Edit on the nest zone): `dev/deploy-use1.sh` writes it to the Worker with `wrangler secret put` whenever the deploy environment carries it, so the Worker can create and delete each sandbox host's tunnel and DNS record ([gateway](../docs/sandbox/gateway/)). The Worker's non-secret vars for the tunnel come from the script too: `NEST_DOMAIN` (`nest.bitcru.sh`, a literal) and `CLOUDFLARE_ACCOUNT_ID` from the SSM parameter `/nest/control-plane/vars/CLOUDFLARE_ACCOUNT_ID`, created once by hand like the other parameters.
- Pull requests get neither.

## The full `deploy.yml` (designed)

Built so far: the trigger, the environment, serialized runs, step 3 and a smoke check of `GET /v1/health` (one read-only round trip to each DO class) that runs `wrangler rollback` on failure. It runs when `ci.yml` succeeds on a push to `main` (`workflow_run`), and on `workflow_dispatch` by me. Its job uses the GitHub environment `production`, which only `main` may deploy from and which holds the secrets in [setup](setup.md) (`CLOUDFLARE_ANALYTICS_TOKEN` is for the health window below). Deploys are serialized (`concurrency: production`, never cancelled).

1. **Check the pause.** If the last production deployment was rolled back, an automatic run stops; a `workflow_dispatch` run clears the pause. The state is GitHub's own deployment statuses, so nothing else stores it.
2. **Classify.** Diff `wrangler.jsonc` against the deployed version. A Durable Object class change or a removed binding makes this a **one-way deploy**, since Cloudflare won't roll back across one (adding `CatalogDO` is one). Recovering from a bad one-way deploy is a forward revert: the previous code deployed again on top, which is why stored records keep the previous release's fields for one release.
3. **Deploy at 100%:** `wrangler deploy --message <sha>`, so every Worker version names its commit.
4. **Smoke:** `GET /v1/health` reaches the Worker and makes one round trip to each DO class (built: 200 only if every class answered within 5 s, else 503 naming the class; each `curl` has 10 s). It proves each class deploys, instantiates and answers with its SQLite reachable, on a health instance that skips the schema, so not that migrations work on stored data; host reconnection after the deploy is that canary.
5. **Health window (10 minutes):** every minute, query [runtime metrics](../docs/control-plane/metrics/) for the new version against the previous version's last 24 hours:
   - Worker 5xx and exception rates;
   - DO exceptions per class;
   - host reconnection: every host connected before the deploy reconnects and renews its leases within 2 minutes;
   - agent turn failures and brain crash restarts;
   - gateway refusals (`stale_epoch`, unknown bindings) and hands calls reported unknown;
   - reliable-channel resends.
6. **On regression:** `wrangler rollback <previous> --message "auto-rollback: <reason>"`, mark the deployment failed, and pause deploys. A one-way deploy is only marked failed and paused.
7. **Either way,** GitHub's `deployment_status` webhook reaches the maintainer and the monitor through their coordination integration.

## `rollback.yml` (designed)

`workflow_dispatch` with inputs `version?` and `reason`, in the `production` environment: rolls back and pauses. I can run it, and so can the monitor through `github.dispatch_workflow{workflow: rollback.yml}`, without either of us holding a Cloudflare credential.

## Hosts

Built: every host installs `releases/current/` at boot, so a release reaches hosts as they are replaced (autoscaling, spot loss), with no canary or version gate. Designed, following the platform's [upgrade rules](../docs/compute/provisioning/#upgrades) (hosts are replaced, never updated in place, and the two host kinds roll one after the other): CI on `main` builds the host binaries and the guest image into the cell's bucket, versioned by commit, and `deploy.yml` sets the cell's desired versions after the control plane is healthy, in this order:

1. **Brain hosts.** Set the desired brain-host version. FleetDO launches one canary host; the gate is a probe turn: a real Claude Code turn running the Python task against a probe sandbox through its gateway. Then the old brain hosts drain gently (no new brains, running brains exit at idle, forced after 30 min; AgentDO restarts the brains elsewhere with `--resume`). No sandbox is touched.
2. **Sandbox hosts.** Set the desired sandbox-host version and, when it changed, the guest image version. One canary host boots a probe sandbox, a hands call round-trips through its gateway and a commit lands; then the old hosts drain gently as the [autoscaler](../docs/compute/autoscaling/) does, forced after 30 min. Brains survive their sandbox moving.
3. **Done** when no host of either kind reports the old version in its `hello`.

The same 10-minute health window applies per host version, with the probe as its gate. `rollback.yml` sets a desired version back, and the same replacement rolls the old version forward again. A release that changes the gateway protocol's `min_supported` or (once memory snapshots exist) the restore ABI is one-way and ships alone, like a Durable Object class change.

## Pruning images

Old images cost money (EBS snapshots for host AMIs, S3 for guest builds), so `deploy.yml` runs `scripts/prune-images.sh use1 <bucket>` before each new host AMI. It keeps the AMI the launch template resolves to (the SSM parameter), the two newest, and any AMI a live instance runs; it deregisters the rest and deletes their snapshots and Image Builder records. Of the guest builds under `images/guest/`, it keeps the two newest finished ones and every `previous-*` backup, and it removes the builder's staging files. The bucket expires noncurrent versions after a day.

**Why not Image Builder's lifecycle policy alone:** it counts images "per recipe version", and every recipe change is a new version, so each old version kept its two newest images forever: 20 AMIs had piled up by 2026-11-01 ([lifecycle rules](https://docs.aws.amazon.com/imagebuilder/latest/userguide/image-lifecycle-rules.html)). An age rule can't replace it either: one without a minimum could delete the current AMI after an idle spell, and its `retainAtLeast` is per version too.

`DRY_RUN=1` prints what it would delete. After building a guest image by hand, run it the same way (with the deploy role, or credentials that may deregister images).

## Rollout rules

The deploy order is the pipeline's: the cell stack applies, then the Worker deploys, then the release is published, and hosts pick it up only as they are replaced. So the Worker always meets hosts one release behind.
- **Anything the Worker needs from a host is gated on the host saying so** (a field or capability in its `hello`), never on the release having rolled out. A host whose hello lacks `brain_epochs` is drained of brains on sight ([FleetDO](../docs/control-plane/durable-objects/fleet/)).
- **A cell's `AWS_CELLS` entry comes from infra,** which applies first: a cell whose entry lacks the `brain` section launches no brain host, and its brains wait.
- **A release with an ordering constraint gets its rule here,** including what a `wrangler rollback` does, and the rule goes once nothing still depends on it.
- **Brain hosts on AWS:** seen on 2026-10-29 with a scripted check against the live Worker: a brain host launched from the brain template (with the `ec2:InstanceProfile` conditions in place), installed the release, enrolled and took two workers' brains, whose sandboxes ran on a sandbox host and were driven through hands. Not yet checked on a host: `systemctl is-enabled` on each kind against `scripts/tests/test_bootstrap.py`.

**This release's rollout rule (hands during a checkpoint): not a one-way deploy, and no ordering constraint.** No Durable Object class is added (SandboxDO gains a kv key, `turn_checkpoint_inflight`) and no wire message or command variant: the one wire change is an optional field on a host-internal command, `sandbox_upsert.paused` (nestd → gateway, one host), and the rest is timers and retry policy in the runner and hands client.
- **Order:** the Worker deploys first as always; the host binaries (nestd, nest-gateway, nest-runner with the hands client) ship in the release and the host AMI built after it, and running hosts get them only when they are replaced (autoscaling, spot loss), never in place. Sandbox hosts and brain hosts may take it in either order.
- **Old and new pairings, all safe:** on one host nestd and the gateway come from the same release (both installed from `releases/current` at boot), so a mixed pair arises only from a hand install or a republish between the two installs; the wire rules hold for it anyway. A new nestd with an old gateway: the old gateway ignores `paused`, so binds to a paused VM hang the 5 s vsock timer and answer `busy`. An old nestd with a new gateway: no `paused` is ever sent, the same behaviour. A new runner (10 s bind timer, a bind timeout retried, 120 s only for a `busy` with `reason: paused`, 30 s for any other) against a new gateway waits out a checkpoint's pause; against an old gateway (no `reason`) it gets 30 s, which covers pauses up to about 30 s, so a sandbox host of the previous release keeps the incident's failure for longer pauses until it is replaced. The gateway's new `reason` field is optional and an old client ignores it. An old runner (5 s bind timer, final) against a new gateway gets the immediate `busy` and retries it within its 30 s budget, and against an old gateway still fails as in the incident until its brain host is replaced.
- **The gap after the deploy:** FleetDO calls a new SandboxDO method, `checkpointResult`; a SandboxDO still on the previous code for a few minutes refuses it (logged, nothing else breaks), and a SandboxDO on this code behind a FleetDO still on the previous one hears only failures (`commandFailed`). Either way a checkpoint whose result went unheard counts as in flight for at most 5 minutes.
- **What a rollback does:** `wrangler rollback` returns SandboxDO to sending a turn-end checkpoint per turn, rate-limited from the request; it ignores `turn_checkpoint_inflight`, and the release after a roll forward reads a stale one as in flight for at most 5 minutes (turns ending meanwhile wait, and its deadline asks for their checkpoint when the window ends). A previous host release republished as `releases/current` reaches only hosts launched afterwards and pairs as above.
- **Cloud check after the hosts roll:** on a sandbox host, start a hands call (`Bash sleep 1`) while a turn-end checkpoint of a large sandbox is paused (the gateway's log shows `sandbox paused: binds get busy`, then `bind refused code=busy`); the call returns after the `sandbox running again` line, not `hands unavailable`.

**This release's rollout rule (the live trace): not a one-way deploy.** No Durable Object class is added and no host changes: the trace is what AgentDO already gets from the runner ([live trace](../docs/control-plane/api/#live-trace)). AgentDO gains two tables (`trace`, `trace_head`), a `kv` key (`trace_sockets`), a WebSocket auto-response (`ping` → `pong`) and a socket tag (`trace`); the Worker a route, `GET /v1/agents/<id>/trace`.
- **The gap after the deploy:** an AgentDO still on the previous code for minutes answers the forwarded upgrade with its session route's 400 (no `x-nest-trace` header), and the Worker answers `503` (`internal`, `retryable: true`), never 500. A client retries with a backoff. Events an agent applied before its AgentDO restarted on this release were never recorded, so the first connect's ring starts at the restart.
- **Stored data (expand-only):** the new tables and key. Nothing is renamed or dropped.
- **What a rollback does:** the route answers 401 to a client (an unknown route to a non-operator) and 404 to the operator; open trace sockets close with the restart. The previous code never reads `trace`, `trace_head` or `trace_sockets`, and doesn't set the auto-response. After the roll forward the ring carries on from `trace_head` (no seq is reused). What happened during the rollback was never recorded, so no seq covers it and no gap reports it: the transcript has it.
- **Operator steps after the deploy:** none.
- **Cloud check:** with a client on `use1` and its token, `POST /v1/agents {template, cell: "use1", start: false}`, then connect to `wss://nest.bitcru.sh/v1/agents/<id>/trace` with `Authorization: Bearer <client token>` (e.g. `websocat -H`; retry a 503 for up to 10 minutes): the upgrade answers 101 and the first message is `{"type": "live"}` (an unstarted agent has nothing to replay), and `ping` gets `pong`. Another client's token gets 404. `POST /v1/agents/<id>/stop {"end": true}`: the socket gets `{"seq": m, "ts_ms": …, "type": "ended", "reason": "stopped"}`, and closes with 1000 within a minute (the end's alarm). Connecting again with `?after=<m - 1>` gets exactly the `ended` (seq `m`) and a close; with `?after=<m>`, `{"type": "ended", "reason": "stopped"}` without a seq and a close.

**This release's rollout rule (the gateway's own user).** The user data (bootstrap with install.sh) runs the gateway as `nest-gw`, which needs a nestd that knows `sockets.gateway_gid`; a sandbox host launched between the cell stack's apply and the release's publish installs the previous release's nestd, which doesn't. Both scripts run the installed `nestd --features`, which this release prints (`gateway-user`; `scripts/publish-release.sh` refuses a build that doesn't, and `crates/nestd/tests/features.rs` checks the binary) and the previous release rejects (exit 2). Without `gateway-user`, the gateway runs as root with `CapabilityBoundingSet=CAP_DAC_OVERRIDE` (the previous release's file access, nothing else of root's) and nestd.json names no gateway uid, so that host behaves as before until it is replaced. `scripts/tests/test_bootstrap.py` runs both. **Next release:** drop the check and the fallback (`--features` stays for the next such change).
- **What a rollback does:** `wrangler rollback` touches no host. A previous release republished as `releases/current` meets this user data the same way, through the fallback.
- **Cloud check after the first deploy:** on a sandbox host, `ps -o user= -C nest-gateway` is `nest-gw`, `/run/nest/gateway.sock` is `root:nest-gw`, a running VM's `vsock.sock` is `nest-fc:nest-gw` `0660` and its jail root `0710`, and a hands call round-trips through the tunnel.

**This release's rollout rule (caller identity for MCP servers): not a one-way deploy.** No Durable Object class is added (BrokerDO gains `identity_keys`), and no host change: the header is the control plane's, on its own requests to MCP servers.
- **Servers:** every request to a remote MCP server now carries `Nest-Identity` ([remote-mcp](../docs/interfaces/remote-mcp/)); a server that doesn't verify ignores it. A server should start requiring it only after this deploy, and expect it to vanish if the Worker is rolled back.
- **Keys:** the first sign or JWKS read makes the first key, which signs at once. `iss` is `PUBLIC_BASE_URL`, which deploys already set to `https://nest.bitcru.sh`.
- **What a rollback does:** requests go out without the header, and `/.well-known/jwks.json` answers 401 (an unknown route to a non-operator). `identity_keys` is never read by the previous code and is kept; after the roll forward the same keys sign, on the same schedule.
- **Cloud check:** `curl -s https://nest.bitcru.sh/.well-known/jwks.json` lists one `OKP`/`Ed25519` key with `Cache-Control: public, max-age=300`, and an agent's call to `mcp-test/` still works. The header itself isn't checked against production: `mcp-test/` records `_meta`, not headers.

**This release's rollout rule (removing the task ledger, microkernel stage 1): not a one-way deploy.** No Durable Object class is added or deleted: `TaskLedgerDO` stays declared (binding `TASKS`, migration `tasks`) as a stub that serves only health and leaves its rows alone, so `wrangler rollback` crosses this release. Deleting the class (a `deleted_classes` migration) is stage 4, which ships alone, after channels and workstreams are gone. No host change: the `task_*` tools reach a brain only through `tools_list`.
- **Stored data:** CatalogDO migrates from seed version 5 to 6, deleting `tasks` and `tasks-admin` and dropping them (and a template's `ledger` default) from every template, other capabilities kept. After a rollback the previous code reads the pruned templates as ordinary ones (it adds nothing back: its last step is 5) and spawns without the ledger; its routes and tools find the ledgers as they were. AgentDO records keep a stored `params` and `task_*` tools: this release ignores the one and never offers the others (a call to one is `unknown_tool`).
- **Lost at the deploy:** the `/v1/ledgers` routes, and the inbox notices a ledger still owed. The stub's alarm delivers nothing and, while the ledger has `deadlines` rows, re-arms a day later, so after a rollback the previous code's alarm runs within a day and delivers them. `overrides.params` on `POST /v1/agents` is refused (400) for one release.
- **Existing agents:** their stored system prompt still describes the task tools; a call to one answers `unknown_tool`. Stop and respawn them to drop it.
- **Cloud check:** `GET /v1/admin/catalog` lists no `tasks` or `tasks-admin` and `worker`/`captain` without them, and `GET /v1/health` names `TaskLedgerDO` `ok`.

**This release's rollout rule (removing channels, microkernel stage 2): not a one-way deploy.** No Durable Object class is added or deleted: `ChannelDO` stays declared (binding `CHANNEL`, migration `channels`) as a stub that serves only health and leaves its rows and its R2 bodies (`channels/<channel>/b/<id>`) alone, so `wrangler rollback` crosses this release. Deleting `ChannelDO` and `TaskLedgerDO` (one `deleted_classes` migration, plus the R2 bodies) is stage 4, which ships alone after stage 3. No host change: the channel tools reach a brain only through `tools_list`, and no wire type a host parses changed.
- **Stored data:** CatalogDO migrates from seed version 6 to 7: it deletes `channels` and `messaging-tree`, drops them from every template, strips the channel tools and the `grants` field from every other capability, and replaces the stored `spawning` prompt only if it is still the version-5 seed's text. After a rollback the previous code reads the pruned rows as ordinary ones (a capability without `grants` has none) and adds nothing back (its last step is 6), so spawns made then get no channel tools either. AgentDO records keep a stored `channel_grants` and channel tools: this release ignores the one and never offers the others (a call answers `unknown_tool`); after a rollback the agents spawned before this release have them again, and those spawned during it don't. AgentDO's `channel_subs`, `chan_wakes` and `chan_out` and SandboxDO's `chan_out` are left as they were, unread.

**This release's rollout rule (agent and sandbox lifetimes): not a one-way deploy, but from its second day it destroys dormant sandboxes.** No Durable Object class is added (AgentDO gains a `children` table, FleetDO's `sandboxes` a `lifetime_ms` column), and no host change: the brain kill and graceful stop are the existing `agent_stop` commands.
- **Sandboxes from before this release get the 1-day idle TTL:** FleetDO's daily prune arms each one's check (200 a day), and a sandbox dormant at its first check counts from then. So the first destructions come a day or two after the deploy, without a notice (a TTL of a day or less gets none). **Before the deploy,** list the sandboxes to keep (`GET /v1/admin/fleet`, and any suspended one with no agent attached) and give each a long TTL after it (`PUT /v1/sandboxes/<id>/lifetime {"idle_ttl_ms": …}`), or set `SANDBOX_IDLE_TTL_MS` (or a cell's `sandbox_idle_ttl_ms`) longer.
- **Stored data the previous code reads:** AgentDO's record gains `ended`, `depth` and spec fields (`spawn`, `ephemeral`, `sandbox_idle_ttl_ms`), which the previous code ignores and keeps; a turn may be `dropped` (logged as outside its enum, listed as read). After a `wrangler rollback` **an ended agent reads as merely stopped**: input lifts it again, and its sandbox may already be gone (its next start then stops: a destroyed sandbox can never run again). SandboxDO's record gains `owner`, `idle_ttl_ms`, `dormant_since_ms`, `expiry_notice_ms` and `expiry_checked_ms`, kept and unread (after the roll forward the gap in checks restarts every dormancy clock, so a sandbox used during the rollback is never destroyed on a stale one); its `expiry` deadline has no handler there (dropped when it fires; FleetDO's sweep arms it again within a week of the roll forward). Catalogs reach seed version 5 (`spawning`); the previous schema strips a capability's `spawn` and a template's lifetime fields, and the stored specs of agents spawned with `agent_spawn` list tools its registry lacks (ignored).
- **Unfinished ends across a rollback:** the previous AgentDO drops the `end` and `reap` deadlines (no handler) and never reads `ended`. After the roll forward the next alarm (the hourly `prune`) arms them again, so an end interrupted by a rollback finishes, unless input the previous release took meanwhile restarted its brain (then the end kills or stops it again).
- **The registry drops `spawn_agent` and `kill`** (they answered `not_implemented`): stored specs naming them lose them silently; a runner of the previous release lists whatever `tools_list` sends.
- **Operator steps after the deploy:** add `spawning` to the templates whose agents should spawn (a new catalog's `captain` has it), and its `spawn` list to name the templates they may spawn from; mark one-shot templates `ephemeral: true`.
- **Cloud check (the lead's):** a captain spawns an ephemeral worker with `sandbox: new` and a short task: the worker's `exited` reaches the captain, its sandbox is destroyed, and `GET /v1/admin/gc` counts one live sandbox fewer; then `agent_stop` on a second worker; then `POST /v1/agents/<captain>/stop {"end": true}`. Clean up nothing else: ended agents prune themselves after 30 days.

**Generation retention is on by default** (the owner's call, 2026-11-01: `report` mode is removed, with no report period). The deploy that switched it found no live sandbox in `use1` (`GET /v1/admin/gc?cell=use1`: `sandboxes: 0`), so nothing was dropped at once.
- **The switch** (`SANDBOX_RETENTION`, an optional var `dev/deploy-use1.sh` passes from the SSM parameter `/nest/control-plane/vars/SANDBOX_RETENTION` when it exists): unset or `on`, each sandbox's pass (a minute after a commit, every 6 h, and from its lifetime check) marks what it drops `deleting` (at most 500 a pass) and logs `retention: N ready, M to drop (K marked deleting, …)` in Workers Logs. `GET /v1/sandboxes/<id>/generations` lists every generation with `state` and `retained` (why it is kept). A long-lived sandbox drops most of its history on its first pass.
- **The first GC run after retention turns on is dry:** FleetDO records when it first sees `on` and counts only runs marked after that as proven. Check its report (`GET /v1/admin/gc?cell=use1`: `sweep_objects`, `sweep_bytes`, the sample) before the run after it deletes. Bytes go no sooner than that second run, after the 24 h grace.
- **Emergency stop:** `aws ssm put-parameter --name /nest/control-plane/vars/SANDBOX_RETENTION --type String --value off --overwrite`, then redeploy (`workflow_dispatch`). Passes stop marking; what is already `deleting` or unrooted stays so (one-way): roots follow those marks in either mode, so nothing a sweep may have taken is rooted again. Deleting the parameter (or `on`) turns it back on and makes the next GC run dry again.
- **A residual race** (unverified: it depends on when each Durable Object restarts on the new version): FleetDO decides dry or not at a claim, from its own code and env. If SandboxDOs already mark while FleetDO still runs the previous release (minutes, [upgrades](../docs/control-plane/#upgrades)), a run in that window deletes without the dry run first. The marks are retention's decisions either way; only the review is skipped. Check `GET /v1/admin/gc` that the first run after turning it on was dry.
- **`wrangler rollback` to the previous release:** it ignores `state` and roots every row, `deleting` ones too, and its SandboxDO has no `retention` handler (the deadline is dropped when it fires; the next commit or lifetime check after the roll forward arms it again). It also roots unrooted memory manifests again. Once a `deleting` generation's manifest or an unrooted memory manifest has been swept, that release's GC passes stop before any delete (a missing root manifest fails closed) until the roll forward: nothing is lost, GC stalls. It never restores a `deleting` generation: it restores only the head, which is never one.

## Host role names (expand/contract)

The host kinds' rename (`burst` → `sandbox`, `controller` → `brain`) spans two releases, so `wrangler rollback` (and the automatic rollback above) to the previous Worker keeps working.
- **Now (since brain hosts, #36):** everything reads both names; everything writes the old ones: FleetDO's `hosts`, `enroll_tokens` and `launched` rows (none is rewritten), host tokens, the role nestd sends in enrollment and `hello`, and the role the launch templates' user data writes (`burst` for the sandbox template, `controller` for the brain template). The control plane accepts an enrollment without a proxy CSR (a brain host's). Sandbox hosts keep the agent runner enabled, and nestd on a sandbox host still runs a brain it is sent.
- **What a Worker from before brain hosts does after a rollback to it:** it reads every row written since. Sandbox hosts are `burst` hosts to it: it starts workers' brains on their sandbox's host, where the runner still runs, except that its `pickHost` keeps an agent's previous brain host when it is healthy, for agents with hands too, so a worker whose last brain ran on a brain host restarts there (still reaching its sandbox through the gateway). A brain host is a `controller` host: it starts agents without hands there, leaves the workers' brains already there until they exit, launches no brain host, and never retires one (it retires only `burst` hosts), so an idle brain host runs until an operator terminates it or confirms it dead. A brain host that hasn't enrolled yet can't (that Worker requires a proxy CSR, which a brain host doesn't send); it is terminated at the enroll timeout. Nothing it reads is in a shape it doesn't know.
- **A pending brain launch blocks sandbox launches after such a rollback.** That Worker launches nothing while any launch is pending (its check has no role filter), so a brain host launched just before the rollback, which can never enroll with it, holds up every sandbox host launch until its enroll timeout (10 min) marks it ended. Remedy right after an emergency rollback: in the fleet view (`GET /v1/admin/fleet?cell=use1`), find a launch with no host and no end, terminate that instance (`aws ec2 terminate-instances`), and, if sandboxes can't wait 10 minutes, mark it ended in FleetDO's `launched` table (`UPDATE launched SET reason = 'enroll_timeout' WHERE instance_id = ?`; there is no admin route for it, so this needs SQL access to the FleetDO object, unverified for the dashboard; otherwise the wait is the 10 minutes). A brain host is launched only while an agent waits for one, so none is pending when no agent is waiting at deploy time.
- **Pending: the contract release** (not built; the follow-up to #36): writes `sandbox` and `brain` everywhere (FleetDO rewrites its `role` columns once, in its constructor; host tokens; nestd's wire names; the templates' user data); drops the agent runner from sandbox hosts' bootstrap; nestd on a sandbox host refuses `agent_start` and binds no runner socket. It still reads the old names, for the hosts and rows the expand release wrote. The release after drops them.
