# Deploy

**Decided: merges deploy to production automatically, and a health window rolls back on regression.** Nothing deploys from a branch, and agents never hold deploy credentials. The workflows follow the platform's [upgrade rules](../docs/control-plane/#upgrades).

**Built (`deploy.yml`, first cut):** after `ci.yml` passes on a push to `main`, or by `workflow_dispatch`, three jobs run in order. All three use the `production` environment and the cell's deploy role over OIDC.
1. **`infra`:** `inframe test` and `plan` (the plan's summary goes in the run summary), then `apply` for `use1`.
2. **`worker`:** `dev/deploy-use1.sh`, then `GET /v1/health` for up to two minutes. If the health check fails, `wrangler rollback` returns to the previous version.
3. **`release`:** `scripts/publish-release.sh` builds the host binaries (static, musl) into `releases/current/`, which every host installs at boot.
   - Firecracker, the jailer, the guest kernel and the guest image carry over from the current release.
   - If no file changes, nothing is published.
   - When it does publish, a host AMI build starts.

**The `edge` stack** (`deploy/lean/Edge/`): Cloudflare Access in front of the gateways (`*-gw-nest`, Service Auth for the one service token in `access:gateway`, 401 for a machine without it), the dashboard (`dash-nest`, the owner's login) and previews (`*-preview-nest`, the owner's login). The infra job plans and applies it after the cell when the `production` environment carries `CLOUDFLARE_ACCESS_API_TOKEN` (a Cloudflare token with Account › Access: Apps and Policies › Edit), and skips it with a notice otherwise. Applications created by hand before the stack existed are imported once, not recreated: `inframe tofu --stack edge -- import cloudflare_zero_trust_access_application.<name> <account id>/<application id>` for each, then a plan shows only the differences the stack settles. Done for `use1` on 2026-10-24: the gateway and dashboard applications were imported; the stack moves their policies inline (the old reusable policies stay in the account, unattached) and creates the previews application.

**`AWS_CELLS` is the cell stacks'** (`aws_ssm_parameter.aws_cells`): each cell stack writes its own entry, `{"<cell>": {...}}`, to `/nest/control-plane/aws-cells/<cell>`, built from its launch template, subnets and proxy root CA key and from `CellSpec` (instance types, which `launch_types_within_iam` keeps inside IAM's `EightIOnly` patterns; spot, max hosts, timers, the regular-pages reserve). `dev/deploy-use1.sh` merges every parameter under that prefix after the apply, so a replaced template, subnet or key reaches the Worker on the same run, and no cell stack overwrites another's entry ([cells](../docs/compute/cells/)); a parameter whose one key isn't its own cell name fails the deploy. A cell outside us-east-1 isn't supported yet: its stack would write its parameter in its own region, while the script reads us-east-1 and sets `CELLS=use1`. The first apply that moves the parameter from `/nest/control-plane/vars/AWS_CELLS` replaces it (the plan shows `-/+` on `aws_ssm_parameter.aws_cells`): the old parameter is deleted if it was imported into the stack's state, and left behind, unused, if it never was (delete it by hand).

**Per-cell AWS credentials: the owner's migration, once.** The Worker reads each cell's control-plane access key from the secret `AWS_CELL_CREDENTIALS`; until a cell has an entry it uses the legacy `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`, which keeps it working for one release. The release after that removes the legacy globals, and a cell still without an entry then loses STONITH, autoscaling and root CA signing (enrollment fails).
1. After the deploy, `GET /v1/admin/fleet?cell=use1` shows `aws.sources` as `{"region": "cell", "credentials": "legacy", "kms_key": "cell"}`.
2. Write `{"use1": {"access_key_id": "…", "secret_access_key": "…"}}` to a file outside the repo: an access key of `nest-use1-control-plane`, either the one in today's `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` or a new one. `dev/cell-credentials.sh check < file` validates it with the control plane's own schema, and `dev/cell-credentials.sh put < file` validates it and puts it with `wrangler secret put AWS_CELL_CREDENTIALS`, which deploys a new version at once. `aws.sources.credentials` then reads `cell`. A malformed entry that reaches the Worker anyway shows as `aws.error` (fields, never values) while the cell keeps using the legacy key.
3. `GET /v1/admin/root-ca?cell=use1` returns the certificate FleetDO keeps for the cell: on first use it adopted `ROOT_CA_CERT_PEM`, the certificate for the same key. If that certificate were for another key, enrollment and renewal would fail with an error naming it, rather than mint a root the guest image doesn't trust. Check that it matches the certificate baked into the guest image.
4. Then delete the legacy secrets (`npx wrangler secret delete` `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `ROOT_CA_KMS_KEY_ID` if it is set as a secret, and `ROOT_CA_CERT_PEM`) and the SSM parameter `/nest/control-plane/vars/ROOT_CA_KMS_KEY_ID`, which the deploy now passes only when it exists. `aws.sources` should read `cell` for all three.

**The dashboard deploys apart** (`deploy-dashboard.yml`): on a push to `main` that touches `dashboard/` (or by `workflow_dispatch`), `npm ci`, typecheck, tests, `vite build` and `wrangler deploy` of the `nest-dashboard` Worker to `dash-nest.bitcru.sh`, then `wrangler secret put NEST_ADMIN_TOKEN` from the `production` environment's secret when it is set. It needs no AWS role; it shares nothing with the platform deploy but the Cloudflare token.

**Not built yet:** the pause, deploy classification, the metrics health window, `rollback.yml`, desired host versions with canaries, and guest image rebuilds (the sections below are the design). Rebuild the guest image by hand (`images/guest/build-on-ec2.sh`) when `nest-guest` changes.

**Credentials:**
- **AWS:** the cell stack's `nest-<cell>-deploy` role, assumed over GitHub OIDC. Its trust policy accepts only `repo:by77er@39721110/nest@1416068100:environment:production`: GitHub's immutable subject format for repositories created after 2026-07-15 carries the owner and repository ids, and `GET /repos/by77er/nest/actions/oidc/customization/sub` confirms it for this repo ([OIDC reference](https://docs.github.com/en/actions/reference/security/oidc)). Applying the stack manages IAM, so the role is administrator-equivalent; the trust policy is what limits it. The first apply of a cell runs by hand with the provisioner key: it creates the role that later applies assume.
- **Cloudflare:** `CLOUDFLARE_API_TOKEN` (Workers edit) and `CLOUDFLARE_ACCOUNT_ID` are secrets on the `production` environment, and so is `CLOUDFLARE_TUNNEL_API_TOKEN` (Account: Cloudflare One Connector: cloudflared → Edit, Zone: DNS → Edit on the nest zone): `dev/deploy-use1.sh` writes it to the Worker with `wrangler secret put` whenever the deploy environment carries it, so the Worker can create and delete each sandbox host's tunnel and DNS record ([gateway](../docs/sandbox/gateway/)). The Worker's non-secret vars for the tunnel come from the script too: `NEST_DOMAIN` (`nest.bitcru.sh`, a literal) and `CLOUDFLARE_ACCOUNT_ID` from the SSM parameter `/nest/control-plane/vars/CLOUDFLARE_ACCOUNT_ID`, created once by hand like the other parameters.
- Pull requests get neither.

## The full `deploy.yml` (designed)

Built so far: the trigger, the environment, serialized runs, step 3 and a smoke check of `GET /v1/health` alone (no DO round trip) that runs `wrangler rollback` on failure. It runs when `ci.yml` succeeds on a push to `main` (`workflow_run`), and on `workflow_dispatch` by me. Its job uses the GitHub environment `production`, which only `main` may deploy from and which holds the secrets in [setup](setup.md) (`CLOUDFLARE_ANALYTICS_TOKEN` is for the health window below). Deploys are serialized (`concurrency: production`, never cancelled).

1. **Check the pause.** If the last production deployment was rolled back, an automatic run stops; a `workflow_dispatch` run clears the pause. The state is GitHub's own deployment statuses, so nothing else stores it.
2. **Classify.** Diff `wrangler.jsonc` against the deployed version. A Durable Object class change or a removed binding makes this a **one-way deploy**, since Cloudflare won't roll back across one (adding `CatalogDO` is one). Recovering from a bad one-way deploy is a forward revert: the previous code deployed again on top, which is why stored records keep the previous release's fields for one release.
3. **Deploy at 100%:** `wrangler deploy --message <sha>`, so every Worker version names its commit.
4. **Smoke:** `GET /v1/health` reaches the Worker and makes one round trip to each DO class.
5. **Health window (10 minutes):** every minute, query [runtime metrics](../docs/control-plane/metrics/) for the new version against the previous version's last 24 hours:
   - Worker 5xx and exception rates;
   - DO exceptions per class;
   - host reconnection: every host connected before the deploy reconnects and renews its leases within 2 minutes;
   - agent turn failures and brain crash restarts;
   - gateway refusals (`stale_epoch`, unknown bindings) and hands calls reported unknown;
   - reliable-channel resends.
6. **On regression:** `wrangler rollback <previous> --message "auto-rollback: <reason>"`, mark the deployment failed, and pause deploys. A one-way deploy is only marked failed and paused.
7. **Either way,** GitHub's `deployment_status` webhook reaches the maintainer and the monitor as a channel post.

## `rollback.yml` (designed)

`workflow_dispatch` with inputs `version?` and `reason`, in the `production` environment: rolls back and pauses. I can run it, and so can the monitor through `github.dispatch_workflow{workflow: rollback.yml}`, without either of us holding a Cloudflare credential.

## Hosts

Built: every host installs `releases/current/` at boot, so a release reaches hosts as they are replaced (autoscaling, spot loss), with no canary or version gate. Designed, following the platform's [upgrade rules](../docs/compute/provisioning/#upgrades) (hosts are replaced, never updated in place, and the two host kinds roll one after the other): CI on `main` builds the host binaries and the guest image into the cell's bucket, versioned by commit, and `deploy.yml` sets the cell's desired versions after the control plane is healthy, in this order:

1. **Brain hosts.** Set the desired brain-host version. FleetDO launches one canary host; the gate is a probe turn: a real Claude Code turn running the Python task against a probe sandbox through its gateway. Then the old brain hosts drain gently (no new brains, running brains exit at idle, forced after 30 min; AgentDO restarts the brains elsewhere with `--resume`). No sandbox is touched.
2. **Sandbox hosts.** Set the desired sandbox-host version and, when it changed, the guest image version. One canary host boots a probe sandbox, a hands call round-trips through its gateway and a commit lands; then the old hosts drain gently as the [autoscaler](../docs/compute/autoscaling/) does, forced after 30 min. Brains survive their sandbox moving.
3. **Done** when no host of either kind reports the old version in its `hello`.

The same 10-minute health window applies per host version, with the probe as its gate. `rollback.yml` sets a desired version back, and the same replacement rolls the old version forward again. A release that changes the gateway protocol's `min_supported` or (once memory snapshots exist) the restore ABI is one-way and ships alone, like a Durable Object class change.

## Rollout rules

The deploy order is the pipeline's: the cell stack applies, then the Worker deploys, then the release is published, and hosts pick it up only as they are replaced. So the Worker always meets hosts one release behind.
- **Anything the Worker needs from a host is gated on the host saying so** (a field or capability in its `hello`), never on the release having rolled out. A host whose hello lacks `brain_epochs` is drained of brains on sight ([FleetDO](../docs/control-plane/durable-objects/fleet/)).
- **A cell's `AWS_CELLS` entry comes from infra,** which applies first: a cell whose entry lacks the `brain` section launches no brain host, and its brains wait.
- **A release with an ordering constraint gets its rule here,** including what a `wrangler rollback` does, and the rule goes once nothing still depends on it.
- **Brain hosts on AWS:** seen on 2026-10-29 with a scripted check against the live Worker: a brain host launched from the brain template (with the `ec2:InstanceProfile` conditions in place), installed the release, enrolled and took two workers' brains, whose sandboxes ran on a sandbox host and were driven through hands. Not yet checked on a host: `systemctl is-enabled` on each kind against `scripts/tests/test_bootstrap.py`.

**This release's rollout rule (the gateway's own user).** The user data (bootstrap with install.sh) runs the gateway as `nest-gw`, which needs a nestd that knows `sockets.gateway_gid`; a sandbox host launched between the cell stack's apply and the release's publish installs the previous release's nestd, which doesn't. Both scripts run the installed `nestd --features`, which this release prints (`gateway-user`; `scripts/publish-release.sh` refuses a build that doesn't, and `crates/nestd/tests/features.rs` checks the binary) and the previous release rejects (exit 2). Without `gateway-user`, the gateway runs as root with `CapabilityBoundingSet=CAP_DAC_OVERRIDE` (the previous release's file access, nothing else of root's) and nestd.json names no gateway uid, so that host behaves as before until it is replaced. `scripts/tests/test_bootstrap.py` runs both. **Next release:** drop the check and the fallback (`--features` stays for the next such change).
- **What a rollback does:** `wrangler rollback` touches no host. A previous release republished as `releases/current` meets this user data the same way, through the fallback.
- **Cloud check after the first deploy:** on a sandbox host, `ps -o user= -C nest-gateway` is `nest-gw`, `/run/nest/gateway.sock` is `root:nest-gw`, a running VM's `vsock.sock` is `nest-fc:nest-gw` `0660` and its jail root `0710`, and a hands call round-trips through the tunnel.

**This release's rollout rule (channels): a one-way deploy.** It adds a Durable Object class, `ChannelDO` (migration tag `channels`), so `wrangler rollback` can't cross it; recovering is a forward revert that keeps the class, its binding and its migration (Cloudflare's migrations only grow). No host change: no wire type changed, and the new platform tools reach a brain only through `tools_list`.
- **Stored data the previous code reads:** AgentDO's record gains `channel_grants` (ignored and kept by the previous code), and new tables (`channel_subs`, `chan_out`) and `kv` keys (`read_tainted`, `last_text`) it never reads; SandboxDO gains `chan_out`. CatalogDO gains `kv.seed_version` and two capabilities with a `grants` field (the previous schema strips it). After a forward revert, a template that lists `channels` or `messaging-tree` no longer expands (its tools are unknown to that registry): take them out of templates before reverting.
- **Existing agents keep working unchanged:** their stored specs have no channel tools or grants, and `notify`, `ask`, `emit` and the inbox API take the same paths as before. What changes for them: their brain's events and their sandbox's events are posted to `<agt>/events` and `<sbx>/events` (from each object's alarm, after every other deadline). Nothing wakes them: the spawner's default subscription is made only for an owner whose spec has `read`, which no seed template gives, and a notice to an agent without `read` is taken but not delivered.
- **Operator steps after the deploy:** `GET /v1/admin/catalog` shows `channels` and `messaging-tree` (added once by the seed migration). To give agents the tools, add them to templates (`PUT /v1/admin/templates/<name>`); only later spawns get them. `GET /v1/admin/channels/user/messages` reads what agents post to `user`.

**This release's rollout rule (the task ledger): a one-way deploy, after channels'.** It adds a Durable Object class, `TaskLedgerDO` (migration tag `tasks`, after `channels`), so `wrangler rollback` can't cross it; recovering is a forward revert that keeps the class, its binding and its migration. No host change: the new tools reach a brain only through `tools_list`, and `not_found` is an ordinary tool error to a runner.
- **Stored data the previous code (channels) reads:** CatalogDO migrates from seed version 2 to 3, adding `tasks` and `tasks-admin` (where the names are free) with a `params` field the previous schema strips, and editing no template. AgentDO's record gains `params` (ignored and kept). A channel named `ledger` or `ledger/…` can no longer be created, and one made under the previous release becomes unreachable: every ChannelDO operation, its retention alarm included, checks the name before it reads stored data. Channels shipped the same day and no such channel is expected; `GET /v1/admin/channels` before the deploy shows whether one exists. After a forward revert, a template that lists `tasks` or `tasks-admin` no longer expands (unknown tools): take them out of templates before reverting.
- **Operator steps after the deploy:** add `tasks` to `worker`, and `tasks` and `tasks-admin` to `captain` (`GET /v1/admin/catalog`, then `PUT /v1/admin/templates/<name>` with the capability appended), then spawn with `overrides: {params: {ledger: <name>}}`.
- **Cloud check:** create a task with `POST /v1/ledgers/<name>/tasks`, read it back, comment, assign it to a test agent spawned with that ledger and see the notice in its inbox. Ledgers aren't deleted, so use a throwaway name.

## Host role names (expand/contract)

The host kinds' rename (`burst` → `sandbox`, `controller` → `brain`) spans two releases, so `wrangler rollback` (and the automatic rollback above) to the previous Worker keeps working.
- **Now (since brain hosts, #36):** everything reads both names; everything writes the old ones: FleetDO's `hosts`, `enroll_tokens` and `launched` rows (none is rewritten), host tokens, the role nestd sends in enrollment and `hello`, and the role the launch templates' user data writes (`burst` for the sandbox template, `controller` for the brain template). The control plane accepts an enrollment without a proxy CSR (a brain host's). Sandbox hosts keep the agent runner enabled, and nestd on a sandbox host still runs a brain it is sent.
- **What a Worker from before brain hosts does after a rollback to it:** it reads every row written since. Sandbox hosts are `burst` hosts to it: it starts workers' brains on their sandbox's host, where the runner still runs, except that its `pickHost` keeps an agent's previous brain host when it is healthy, for agents with hands too, so a worker whose last brain ran on a brain host restarts there (still reaching its sandbox through the gateway). A brain host is a `controller` host: it starts agents without hands there, leaves the workers' brains already there until they exit, launches no brain host, and never retires one (it retires only `burst` hosts), so an idle brain host runs until an operator terminates it or confirms it dead. A brain host that hasn't enrolled yet can't (that Worker requires a proxy CSR, which a brain host doesn't send); it is terminated at the enroll timeout. Nothing it reads is in a shape it doesn't know.
- **A pending brain launch blocks sandbox launches after such a rollback.** That Worker launches nothing while any launch is pending (its check has no role filter), so a brain host launched just before the rollback, which can never enroll with it, holds up every sandbox host launch until its enroll timeout (10 min) marks it ended. Remedy right after an emergency rollback: in the fleet view (`GET /v1/admin/fleet?cell=use1`), find a launch with no host and no end, terminate that instance (`aws ec2 terminate-instances`), and, if sandboxes can't wait 10 minutes, mark it ended in FleetDO's `launched` table (`UPDATE launched SET reason = 'enroll_timeout' WHERE instance_id = ?`; there is no admin route for it, so this needs SQL access to the FleetDO object, unverified for the dashboard; otherwise the wait is the 10 minutes). A brain host is launched only while an agent waits for one, so none is pending when no agent is waiting at deploy time.
- **Pending: the contract release** (not built; the follow-up to #36): writes `sandbox` and `brain` everywhere (FleetDO rewrites its `role` columns once, in its constructor; host tokens; nestd's wire names; the templates' user data); drops the agent runner from sandbox hosts' bootstrap; nestd on a sandbox host refuses `agent_start` and binds no runner socket. It still reads the old names, for the hosts and rows the expand release wrote. The release after drops them.
