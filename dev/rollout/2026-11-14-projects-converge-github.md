# The projects app converges what ran on nest's repos onto its own GitHub access (2026-11-14)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for the projects app ([converging onto the app's own access](../../projects/README.md#converging-onto-the-apps-own-access)): phase B4 of the plan to take service integrations out of nest's kernel ([decisions](../../docs/README.md#settled-decisions)). It needs B3 (`2026-11-12-projects-sandbox-github.md`) deployed, with its grant widening.

**Not a one-way deploy, and no ordering constraint on nest:** it uses only what B3 used (client secrets, bindings, guards, `POST /start`, the catalog routes). The grant narrowing comes after it, below.

- **What changes at deploy:**
  - **Each project's manager is looked at** at the project's first use (any request, event or alarm; opening a project's page wakes it). One on nest's repos (every manager started before B3) is replaced between turns by one on a fresh sandbox with the app's access, once the chat has been quiet for 30 minutes, nothing of the owner's waits for it, the grant covers the GitHub hosts and the App reaches the repo; else it's looked at again every 5 minutes. Its Claude Code conversation and nest timers don't carry over (nest can't move an agent to another sandbox); the board, chat, memory and the app's waits do. The chat says so. Its old sandbox is destroyed.
  - **Starts frozen before B3** (no agent yet) are begun again as new attempts on the app's access at their next try (a worker's, the manager's, a reviewer's), what the old attempt made destroyed by its labels; a routine run B3's migration marked (`nest_repos`) ends, failed, and its routine's next run is the app's.
  - **No spawn narrows nest's repos:** each start writes the template it names first (a shared one too: `writeSharedTemplate`), so the catalog sync needn't have run. A start B3 froze still sends B3's `overrides` (its Idempotency-Key binds them).
  - **New column and table** (expand only): `settings.converge_next_ms` (set to 0 by the migration for every project with a manager), `abandoned_starts`.
- **Live workers, reviewers and routine runs started before B3** run until they end by themselves (a worker once its PR merges). Nothing makes them end sooner.
- **Then, the operator's step** ([setup, step 11](../../projects/README.md#setup-the-operators)): once no sandbox of the projects client injects nest's `github`, `github_read` or `github_read_default` (`GET /v1/sandboxes?…` listing the client's sandboxes, then `GET /v1/sandboxes/<id>/policy` for each) and `GITHUB_TOKEN_SOURCE` is unset, `PATCH /v1/admin/clients/<id>` with the whole grant less `repos`, `read_repos`, `github`, `github_push` and `repo_owners`. Narrowed before that, a live agent still on nest's repos loses its GitHub token (nest mints nothing for repos the grant lacks; unverified which way nest refuses it) and its layer writes may be refused for nest's push opt-in.
- **Cloud check after the deploy:** each project's manager agent (`GET /v1/agents?label=project=<id>&label=role=manager`) is a new one whose sandbox's `client-policy` has the `gh_read` binding and whose `policy` has the `client:github-*` guards and none of `github_read`/`github_read_default`; the old managers' sandboxes are destroyed. The client's catalog templates `projects/reviewer` and `projects/routine` name no repo once a review or a run has started.
- **Untested live** (as of this PR): the replacement on the real managers (suspended sandboxes, no sandbox host up when this was written: the new manager's sandbox waits for one that applies guards, `hosts_not_ready` meanwhile, and the project has no manager until then).
- **What a `wrangler rollback` does:** B3 reads neither the column nor the table. A manager already replaced stays on the app's access (B3 keeps it). A replacement in flight (old one stopped, new one not yet started) is finished by B3's own lifecycle (the start is owed). A start begun again stays the new attempt; what its old attempt made, if `abandoned_starts` still listed it, is left to nest's idle TTL. B3 then sends B3's narrowing again for its own new starts, and a start this release froze (`overrides: {}`) is resent by B3 with `repos: []`, `read_repos: []`: a different request under the same Idempotency-Key, which nest refuses (409) if the first landed; the start then fails as a 409 does (a worker's stalls, shown; the manager's retries; a review spends an attempt). Templates this release wrote name no repo, which B3 narrows to none anyway.
- **Contract, with phase C:** B3's narrowing for starts it froze (`spawnOverrides` without `overrides`, a week after this deploy: frozen specs are kept 7 days), `routine_runs.nest_repos`, nest's `github_push` in live legacy workers' layers and Settings, and `abandoned_starts` once no rollback reaches B3.
