# The projects app converges what ran on nest's repos onto its own GitHub access (2026-11-14)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for the projects app ([converging onto the app's own access](../../projects/README.md#converging-onto-the-apps-own-access)): phase B4 of the plan to take service integrations out of nest's kernel ([decisions](../../docs/README.md#settled-decisions)). It needs B3 (`2026-11-12-projects-sandbox-github.md`) deployed, with its grant widening.

**Not a one-way deploy, and no ordering constraint on nest:** it uses only what B3 used (client secrets, bindings, guards, the catalog routes, stop). The grant narrowing comes after it, below.

- **What changes at deploy:**
  - **Each project's manager is looked at** at the project's first use (any request, event or alarm; opening a project's page wakes it). One on nest's repos (every manager started before B3) is replaced by one on a fresh sandbox with the app's access, **make before break**: its successor's start is frozen and its sandbox made first (the grant checked, the read token written, nest's 409 `hosts_not_ready` heeded), and only then is the old one stopped. Until a sandbox host that applies guards is up, nothing changes: the old manager keeps running and it's tried again every 5 minutes. Then only between turns (nest's state `idle`, `ready` or `detached`), with nothing of the owner's or the app's waiting for it and the chat quiet for 30 minutes. Its Claude Code conversation and nest timers don't carry over (nest can't move an agent to another sandbox); the board, chat, memory and the app's waits do, and what the app owes the manager during the swap is kept for its successor, after its brief. The chat says so. Its old sandbox is destroyed.
  - **Accepted risk:** a turn that starts between nest's state read and the stop (issued right after it) is cut.
  - **Starts frozen before B3** (no agent yet) are begun again as new attempts on the app's access at their next try (a worker's, the manager's, a reviewer's), what the old attempt made destroyed by its labels; a routine run B3's migration marked (`nest_repos`) ends, failed, and its routine's next run is the app's.
  - **Each start writes the template it names first** (a shared one too: `writeSharedTemplate`), so the catalog sync needn't have run. The spawn's overrides stay B3's (`{repos: [], read_repos: []}`, narrowing nothing now), frozen with the start.
  - **New column and table** (expand only): `settings.converge_next_ms` (set to 0 by the migration for every project with a manager), `abandoned_starts`; `messages` rows kept for the next manager carry `to_agent = 'manager:next'` and no `next_ms`.
- **Live workers, reviewers and routine runs started before B3** run until they end by themselves (a worker once its PR merges). Nothing makes them end sooner.
- **Then, the operator's step** ([setup, step 11](../../projects/README.md#setup-the-operators)): once no sandbox of the projects client injects nest's `github`, `github_read` or `github_read_default` (list the client's sandboxes, then `GET /v1/sandboxes/<id>/policy` for each) and `GITHUB_TOKEN_SOURCE` is unset, `PATCH /v1/admin/clients/<id>` with the whole grant less `repos`, `read_repos`, `github`, `github_push` and `repo_owners`. The spawns' empty narrowing fits the narrowed grant. Narrowed before that, a live agent still on nest's repos loses its GitHub token (unverified which way nest refuses the mint) and its layer writes may be refused for nest's push opt-in.
- **Cloud check after the deploy:** each project's manager agent (`GET /v1/agents?label=project=<id>&label=role=manager`) is a new one whose sandbox's `client-policy` has the `gh_read` binding and whose `policy` has the `client:github-*` guards and none of `github_read`/`github_read_default`; the old managers' sandboxes are destroyed. Until a guard-applying sandbox host is up, the old managers stay as they are (the app's logs say the successor can't start yet). The client's catalog templates `projects/reviewer` and `projects/routine` name no repo once a review or a run has started.
- **Untested live** (as of this PR): the replacement on the real managers (suspended sandboxes, no sandbox host up when this was written).
- **What a `wrangler rollback` does:** B3 reads neither the column nor the table. A manager already replaced stays on the app's access (B3 keeps it). A replacement in flight (old one stopped, new one not yet started) is finished by B3's own lifecycle (the start is owed); a successor sandbox made for a move that didn't happen is reused by that start's key or ended by nest's idle TTL. Messages kept for the next manager stay unsent (not due) and are pruned after a week. A start begun again stays the new attempt; what its old attempt made, if `abandoned_starts` still listed it, is left to nest's idle TTL. Starts this release froze send the same overrides B3 does, so B3 resends the same requests under their Idempotency-Keys. Templates this release wrote name no repo, which B3 narrows to none anyway.
- **Contract, with phase C:** the spawns' empty narrowing (`NARROWED`; sending no overrides once no rollback reaches B3 and nest drops the field), `routine_runs.nest_repos`, nest's `github_push` in live legacy workers' layers and Settings, and `abandoned_starts` once no rollback reaches B3.
