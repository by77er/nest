# Read-only repos and the App's identity for API clients (2026-11-02)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)).

**Not a one-way deploy.** No Durable Object class is added and no host changes: nest-proxy already substitutes whichever binding's placeholder a request carries. BrokerDO gains two methods (`readInjectionSecret`, `githubApp`) and a table (`github_app_identity`); SandboxDO a layer field (`read_repos`) and kv keys (`agent_read_repos`, written only once an agent has read-only repos, and `read_token`); the policy two bindings (`github_read`, `github_read_default`); templates, overrides, specs and grants an optional `read_repos`.
- **What exists keeps its tokens:** a sandbox, spec, template or grant without `read_repos` gets exactly the guards, binding and token it did (the GitHub fixture `egress_policy.github.json` is unchanged), and a push token's reuse key is the previous release's, so no token is re-minted at the deploy. **Two behaviour changes:** a policy change that changes its tokens now sends `secrets_update` before `policy_update` (a host of the previous release applies each as it comes, so nothing on hosts changes), and a spawn whose overrides narrow a template's allowlist to none now drops the template's unscoped GitHub brokered grants (before, they reached every repo the App is on); agents already spawned keep their stored spec.
- **The gap after the deploy** (minutes, until each Durable Object restarts on this release): a SandboxDO of this release asking a previous BrokerDO for a read-only token finds no method (refused, retried in 2 minutes), never a push token in its place: that is why it is a method and not a field. A previous SandboxDO ignores `read_repos` in a layer and the read-only repos an attaching agent passes, so an agent created then has none until it is created again: fail closed. `github_app` is absent from answers while BrokerDO lacks `githubApp` (the answers go out without it).
- **What a rollback does:** the previous code ignores `read_repos` in stored templates, specs, grants and layers (and refuses it in a grant written to it), and never reads `agent_read_repos`: read-only repos lose their token at the sandbox's next secrets push, and none gains write. The previous BrokerDO never reads `github_app_identity`, nor the `inject:github_read:` secrets beyond deleting them with the sandbox or once expired. A client's answers lose `app_id` and `app_slug`.
- **Operator steps after the deploy:** install the GitHub App on the read-only repos too (it mints only for repos it is on). Give a client read access with `PATCH /v1/admin/clients/<cli> {grant}` adding `read_repos` (`PATCH` replaces the whole grant).
- **Cloud check (mints nothing beyond the grant):** create a client whose grant has `read_repos: ["by77er/nest"]` and no `repos`, and a sandbox-backed agent from a template in its namespace with `read_repos: ["by77er/nest"]`. In its sandbox, `git ls-remote https://github.com/by77er/nest` works, and `git push` to a branch is refused with 403 `request_denied` (`guard: github-push` in the egress audit). The day's `audit/broker/` in R2 has one mint for that sandbox, `binding: github_read`, `repos: ["by77er/nest"]`, `permissions: {contents: read, metadata: read}`, and no mint with `write` for it. A template naming `repos: ["by77er/nest"]` is refused 403 (`repos by77er/nest`). With `github: {repos: ["by77er/nest"], permissions: {checks: "read"}}` added to the grant, `GET /v1/clients/self` shows `github_app.app_id` equal to the App's id on its settings page, and `POST /v1/clients/self/github-token` answers the same `app_id` (and `app_slug`). Then delete the agent, the sandbox and the client.
