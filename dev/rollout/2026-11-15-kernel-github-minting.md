# The kernel's repo fields, GitHub guards and token minting go (2026-11-15)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for [no repo tokens](../../docs/sandbox/networking/egress/policy/#no-repo-tokens): phase C3 of the plan to take service integrations out of nest's kernel ([decisions](../../docs/README.md#settled-decisions)). It follows C2 (`2026-11-15-brokered-github-actions.md`) and needs B4 (`2026-11-14-projects-converge-github.md`) done: nothing of the projects app runs on nest's repos.

**Not a one-way deploy. Ordering constraint: the operator puts the GitHub write floor into the cell's base layer before the merge, or accepts the window without it (below).** No Durable Object class, table, column or host wire change. RPC methods go (`BrokerDO.injectionSecret`, `readInjectionSecret`, `githubToken`; `SandboxDO.pushRepos`, `repoAccess`, `pushWorkflows`); the `agent_spawn` tool's schema loses `repos` and `read_repos`.

- **Checked before the merge** (a read-only inventory of `use1`, 2026-11-15): three live sandboxes, all the projects app's, none with a kernel binding (`github`, `github_read`, `github_read_default`), an allow rule from repos or a minted token: each policy has only `client:gh_read` and the kernel's no-repo GitHub guards beside the app's own `client:github-*` guards. No live agent's view shows `repos`, `read_repos` or `github_push`. The catalog holds `repos` or `read_repos` in `projects/manager`, `projects/worker`, `projects/routine` and one per-model worker template (an old catalog sync; the app rewrites the shared ones before each start), and nowhere else. The cell's base layer is the seed (no guards).
- **What changes at deploy:**
  - No sandbox's policy gets a guard, binding or allow rule nest constructs: the GitHub guards every sandbox had (`github-push`, `github-write`, `github-api-write`, `gist-write`, `githubusercontent-write`) go from each sandbox at its next policy push, as do the `github`, `github_read` and `github_read_default` bindings where any were.
  - `repos`, `read_repos` and `github_push` are refused (400) when they grant anything: in templates (admin and client routes, and CatalogDO itself), spawn overrides (operator and client), the operator's layer (`PUT /v1/sandboxes/<id>/policy`, a create's `policy`), a sandbox's create and its client layer. One that grants nothing (an empty list, `{"workflows": false}`) is taken and dropped, so the projects app's spawn overrides `{repos: [], read_repos: []}` keep working. The `agent_spawn` tool is the exception: its schema loses them, so it refuses either as an unknown argument, even empty (a brain started before the deploy still lists them; no live template spawns with them). `GET …/client-policy` no longer answers `github_push` (the app sends it only when `GET` does).
  - Stored data naming them reads as pruned: a template row reads without them (the catalog view and every spawn from it, which succeeds with none); an agent's stored spec keeps them in its record and leaves them out of its view, and nothing acts on them; a sandbox's stored operator layer keeps them and nothing reads them. Nothing of this is rewritten.
  - A sandbox deletes the kv keys a release before kept to mint from (`agent_repos`, `agent_read_repos`, `github_push`, `agent_github_push`, `read_token`) at each start of its Durable Object.
  - BrokerDO mints nothing and scans no `github_tokens`. At each start it forgets everything the previous release minted (`github_tokens`, and `injections` with the `inject:<binding>:<sandbox>` secrets it names, expired or not), so an operator binding of the same name never resolves to a minted token, placed or not. An operator's own `inject:<binding>:<sandbox>` secret stays unless it was written over a name the previous release had minted under (its `injections` row still there): then it goes too, and the binding falls back to `inject:<binding>` (closed, never someone else's token). The `github_*` and `injections` tables stay created and unwritten.
  - `github_app`'s shape is no longer checked when stored; the name stays never resolvable into a host command.
  - GitHub's and git's env names (`GITHUB_TOKEN`, `GH_TOKEN`, `GIT_CONFIG*`, …) are reserved nowhere.
  - **The guest image is unchanged until C4:** its `git-credential-nest` and `GITHUB_TOKEN` still carry `nest-ph-github`, which nothing fills unless an operator binding takes that placeholder. Without one, git and `gh` send the placeholder to GitHub as a credential and are refused (no secret is involved). The projects app's sandboxes set their own `GH_TOKEN` and reset git's helper list through `GIT_CONFIG_*`, so they don't use them.
- **The operator, before the merge (merges deploy at once):** the kernel's GitHub guards made every sandbox's writes to GitHub (pushes, REST and GraphQL writes, gists, the content hosts) need a credential nest injected (`{injected: "*", at: "authorization"}`), so a credential planted in a sandbox (a token carried in by a prompt injection, say) wrote nowhere there. From the deploy on, each sandbox loses them at its next policy push (every new sandbox, attach and client-layer write), and the seed base layer allows github.com: a sandbox without guards of its own (the operator's, a client's without any) can then push anywhere with any credential it holds, the seed's main exfiltration path. The projects app's guards confine its sandboxes' writes to the project's repo, but don't ask for its own credential. To keep the floor as operator data, put the same guards in the cell's base layer first: `GET /v1/admin/egress/base?cell=use1`, then `PUT` a body of only `allow` (as read, unchanged) and `guards` (the `guards` of `protocol/fixtures/control/egress_policy/egress_policy.github_none.json`, exactly what the kernel built for a sandbox without repos; reword their `reason`s, data like the rest, since they say "this sandbox has no repos of nest's own"): the route's schema is strict, so the `version` and `pending` a `GET` answers can't go back. This works on the current release too, beside the identical kernel guards (neither the control plane nor nest-proxy limits base guards by name), and the `PUT` sends every live sandbox a new policy. The app's pushes, REST writes and GraphQL pass it: its binding names the Basic username, so Basic is written whole, as Bearer is. It needs every sandbox host of the cell to enforce `*` and `at` (409 otherwise). Then add "the base layer's guards are the fixture's" to this file's "Checked before the merge" bullet. If the owner instead accepts the window, say so in the PR. Plan phase D1 is where the operator decides the base layer for good.
- **The gap after the deploy** (minutes, until each Durable Object restarts on this release), each direction:
  - A previous AgentDO attaching an agent passes its spec's repos and push opt-in: this SandboxDO ignores them (its `attach` keeps the two positional parameters, ignored).
  - A previous Worker hands this release's CatalogDO a template with the fields (its schema took them): refused if they grant anything, else stored without them. It hands this SandboxDO an operator layer with them: the same. A create's top-level `github_push`, or a client layer's `workflows`, is ignored.
  - A previous SandboxDO calls this BrokerDO's mint methods, which are gone: the call fails, and that SandboxDO logs it and retries later (its mint path catches it, and its push goes without the token); its `forgetInjections` still answers. No live sandbox has repos.
  - A previous CatalogDO expands a template with repos into a spec holding them: this AgentDO and SandboxDO act on none of it.
  - A previous Worker's client spawn, or a previous AgentDO's `agent_spawn`, with non-empty `overrides.repos` reaches this CatalogDO and is refused (400) by the strict `SpawnerOverrides`. No live template spawns with them.
  - This Worker calling a previous SandboxDO's `setClientLayer` passes no `workflows`, which that SandboxDO reads as off (narrower). Its `GET …/client-policy` passes a previous SandboxDO's answer through, `github_push` included: an app echoing `workflows: true` would get 400 (none has it on).
  - A previous Worker's operator spawn with `overrides.repos` reaches this CatalogDO, which takes the operator's overrides as parsed and ignores the field: the agent spawns without repos (narrower, not refused).
  - This SandboxDO with a previous BrokerDO: it no longer asks BrokerDO to forget a sandbox's minted tokens before each push, so an operator binding written in those minutes, named as one a sandbox with repos has a token under, could resolve to that token (under an hour left) until this BrokerDO starts and forgets it. No live sandbox has repos.
  - A previous BrokerDO is asked by this SandboxDO only for `forgetInjections` (at a destroy), `injectionSecretRefs` and client references, which it has.
- **Cloud check after the deploy:** `GET /v1/sandboxes/<id>/policy` for each live sandbox shows no guard named `github-*`, `gist-write` or `githubusercontent-write` beyond the base layer's floor once its policy was pushed again, and still its `client:` guards and `client:gh_read`; `GET /v1/admin/catalog` shows the projects templates without `repos` or `read_repos`; a projects start still succeeds.
- **What a `wrangler rollback` does:** the previous release reads stored rows as they are, so a template or layer that held repos holds them again: a spawn from such a template, or an operator layer holding repos, gets kernel-minted tokens again. An existing agent's stored repos don't come back: AgentDO attaches only when the agent is created, and this release's start deleted the sandbox's kv keys that held them. That purge is what keeps a rollback from widening: this release's detach no longer clears `agent_repos`, and the previous release's `pushRepos` unions every entry, attached or not. The read-token flag comes back only with a new read-only token (a sandbox without it never asks BrokerDO to forget one; BrokerDO's rows were forgotten at this release's start). Its GitHub guards come back at each sandbox's next policy push. What this release wrote names none of the fields, except a spec a previous CatalogDO expanded with repos in the gap and this AgentDO stored (harmless after a rollback: AgentDO attaches only at an agent's create). To keep a rollback from bringing repo grants back, the operator rewrites the catalog templates still holding `repos` or `read_repos` without them before the merge (the projects app rewrites its shared ones before each start); a base-layer floor stays through a rollback (the previous release reads it).
- **Contract, a release later, with a precondition:** the projects app sends `overrides: {repos: [], read_repos: []}` on every start, and a start frozen before resends that exact request (its Idempotency-Key binds it for 24 h; a rollback of the app resends it too), through the strict `SpawnerOverrides`. So the shim stays until the app stops sending them and no frozen start can still carry them. Then the `RemovedRepoFields` shim goes: a write naming `repos`, `read_repos` or `github_push` is then refused as unknown where the schema is strict and dropped where it isn't. `SandboxDO.attach` keeps its 5-argument shape (the third and fourth ignored) until a renamed method replaces it: a release passing the extras third would have them read as repos, and dropped, by a SandboxDO of this release in its deploy gap, so an agent's client guards would silently not apply. `forgetInjections`, BrokerDO's and SandboxDO's purges at start, and the tables go with phase C5; the read prunes (`withoutRemovedRepoFields` in `AgentDO.info()` and `SandboxDO.operatorLayer()`, and the non-strict `Template` read) stay while stored rows may hold the fields, since nothing rewrites them: until a release rewrites them once, as C2's contract does for capabilities; the guest image's helper and `GITHUB_TOKEN` with C4; `push_check.py` (retired here: it exits 2 at once) and the e2e push check's move onto a client guard with C6.
