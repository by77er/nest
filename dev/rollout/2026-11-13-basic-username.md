# A binding's Basic username, and `at` on Basic only then (2026-11-13)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for [any injected credential](../../docs/sandbox/networking/egress/policy/#any-injected-credential): a Basic password location may name a `username`, which nest-proxy writes in place of the request's, and a Basic substitution counts as written whole for a guard's `at` only then.

**Not a one-way deploy. One ordering constraint, enforced by the control plane** (the `nest-wire` capability-flag pattern, as for `guard_injected_any`):
- **Why:** a nest-proxy of the previous release ignores `username` (its unit variant reads the location with it as the plain one) and takes any Basic substitution as whole, so `at` beside a Basic binding would hold for `Basic base64(<a username the sandbox chose>:<placeholder>)`. Some services (GitHub) take a token as the Basic username.
- **How it's enforced:** nestd's fleet hello says `guard_basic_user: true`; FleetDO records it per host (`hosts.guard_basic_user`, default 0).
  - **Writes:** a guard newly using `at` (the base layer, the operator layer, a client's create, layer write or an agent's attach) is refused (409 `hosts_not_ready`) while any sandbox host of the cell, any not dead, lacks it. `*` without `at` still needs only `guard_injected_any`.
  - **The invariant:** a sandbox on a host without `guard_basic_user` never has, in its effective policy, both a Basic password binding (from any source, nest's own GitHub binding included) and a guard using `at`. Placement: a Basic binding or a guard using `at` goes only to a host with it. Every change of the effective policy (a client's layer, an attach with its extras and repos, an agent's repos added, the operator's layer and repos) is judged against the sandbox's own host in one gate, and refused (409 `hosts_not_ready`) if it newly brings the pair there; repos bring it by themselves (nest's binding beside GraphQL's `at`). What can't be refused (a detach, a release's guards) fails closed: the policy pushed to such a host has its guards without `at`.
  - **nest's own binding** names `x-access-token` as its Basic username (the guest's helper sends the same), and GraphQL's exception for the sandbox's token asks `at: authorization`.
  - **Catalog templates:** a binding naming a `username` is refused (400) in this release (expand first: the previous release's CatalogDO would drop the template). The release after takes it.
- **What changes on this release's proxies:** a Basic substitution without a `username` is no longer whole: `at: authorization` stops holding for it. Nothing stored relies on that today (the only `at` users are written since #267, with Bearer or none); a client that wants `at` with Basic names its username.
- **Wire:** `InjectionLocation::AuthorizationBasicPassword` gains `username?` (absent from the JSON when unset, so every existing binding is the same bytes); the hello gains `guard_basic_user?`. Fixtures: `host_to_fleet/hello.guard_basic_user.json`, `policy_update.basic_username.json`, `sandbox_upsert.basic_username.json` and a `username` in `egress_policy.client_inject.json`; the round trip and the previous release's reading are `nest-protocol`'s `a_basic_location_names_a_username_only_when_set`.
- **In the gap** (the Worker deployed, a cell's hosts one release behind): guards newly using `at` are refused there; sandboxes with a Basic binding or a guard using `at` (any sandbox with repos) are placed only on hosts with the flag, and a sandbox already on an older host gets no repos and no write that brings the pair; everything else runs as before.
- **Before #271's Worker deploys, every sandbox host of each cell reports `guard_basic_user`.** #271 adds `at` to a live sandbox's GitHub guards when it holds no repos, by the deploy itself, so a sandbox already on an old host with a Basic binding would get `at` there ungated. The deployer checks it (the hosts' rows in FleetDO, `guard_basic_user = 1` for every sandbox host not dead). Today use1 has no sandbox hosts, and new ones install the current release.
- **What a `wrangler rollback` does:** the previous control plane ignores `hosts.guard_basic_user` and gates `at` on `guard_injected_any` alone, and places without it. Its client schema is strict: a client's binding naming a `username` is refused (400) at a write, so a client sending back a layer it read (`GET …/client-policy` answers the stored binding with it) is refused until rolling forward. A sandbox's stored one is read as stored (SandboxDO doesn't parse it again), so it still reaches nest-proxy with its `username`. CatalogDO does parse its templates, strictly, and would skip one naming a `username`: so this release refuses that in templates. The operator's model is a plain object and drops `username` at an operator write.
- **A host rollback:** hosts of the previous release launched again: the invariant holds there too. Sandboxes with a Basic binding or a guard using `at` wait unplaced if only those are free; one already on such a host gets no write that brings the pair (409), and a pair it has anyway is pushed there without `at`; new `at` guards in the cell are refused until they are replaced.
