# Firecracker pinned in the repo (2026-11-18)

Not a one-way deploy, and no ordering constraint: only the `release` job changes. No stored state, wire field or route; `wrangler rollback` doesn't touch the release.

- **What changes:** `scripts/publish-release.sh` no longer carries `firecracker` and `jailer` from the current release. It downloads upstream's `firecracker-<version>-x86_64.tgz` for the pinned `FIRECRACKER_VERSION`, checks it against `FIRECRACKER_SHA256` before unpacking, and publishes the archive's two binaries. `vmlinux` and `nest-base.ext4.zst` are still carried. The release's file set is unchanged, so hosts on any `install.sh` install it as before.
- **The first release after the merge:** the script changed, so the release job builds. The pin is v1.17.0, the version the hosts run. If the bucket's `firecracker` and `jailer` are upstream's 1.17.0 binaries (the owner checks this before the merge: the PR body), nothing changes and nothing is published (`changed=false`). If they aren't, the pin is wrong: change it before the merge, or the release replaces the deployed Firecracker.
- **A later pin change** (a PR changing the two lines) publishes a release whose `firecracker` and `jailer` differ, and starts a host AMI build. Hosts launched from then on install it at boot; running hosts keep theirs until they are replaced (hosts are never updated in place: [upgrades](../../docs/compute/provisioning/README.md#upgrades)). So old and new Firecracker run side by side until the old hosts are gone.
- **The restore ABI:** the Firecracker version becomes part of the restore ABI once memory snapshots exist ([upgrades](../../docs/compute/provisioning/README.md#upgrades), [restore ABI](../../docs/sandbox/state/memory/README.md#restore-abi)). Today restores are disk-only, so a pin change is not one-way; once snapshots exist, a change whose snapshot format differs is, and ships under that rule.
- **A publish interrupted between uploads** leaves new binaries next to the old `SHA256SUMS` (uploaded last): a host booting then fails the check and installs nothing, as for any release. The release job didn't save its inputs marker, so the next deploy builds and publishes again.
- **Going back:** a revert PR. Reverting a pin change publishes the previous version's binaries for hosts launched after it. Reverting this change restores the carrying script, which carries whatever the current release holds (the pinned binaries, if a pin change was published).
