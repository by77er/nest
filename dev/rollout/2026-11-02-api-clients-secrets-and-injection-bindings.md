# API clients' secrets, injection bindings and `workflows: write` (2026-11-02)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)).

**Not a one-way deploy.** No Durable Object class is added (BrokerDO gains a table, `client_secrets`, and methods; SandboxDO kv keys) and no host change: a client's binding is an ordinary `InjectionBinding` on the wire (`egress_policy.client_inject.json`), resolved by FleetDO like the operator's ([API clients](../../docs/control-plane/api/clients/#secrets)).
- **The gap after the deploy:** a BrokerDO still on the previous code for minutes lacks the new methods. `PUT`, `GET` and `DELETE /v1/clients/self/secrets…`, `GET /v1/admin/clients/<cli>/secrets` and a client's `DELETE` answer `503` (`internal`, `retryable: true`), never 500. A SandboxDO pushing a client's bindings in that window logs the refusal and tries again in 2 minutes; the proxy holds no value for them meanwhile, so their placeholders are refused, never sent bare. A FleetDO on the previous code resolves no `client-secret:` reference (outside its allowlist): the same, until it restarts. A previous BrokerDO given `workflows` mints without it (narrower), until it restarts.
- **Stored data (expand-only):** BrokerDO's `client_secrets` and `client-secret:` rows in `secrets`; grants may carry `secrets`, `inject_hosts` and `github_push` (a grant stored before reads as none of each); templates may carry `inject` and `github_push`; specs `inject` (with each binding's client and placeholder) and `github_push`; a sandbox policy layer `github_push`; SandboxDO kv `client_inject`, `github_push`, `agent_inject`, `agent_github_push`; BrokerDO's `injections` reuse key gains `workflows` only for a token minted with it (the others keep theirs, so tokens are reused across the deploy).
- **What a rollback does:** the previous schemas strip `inject` and `github_push` from templates, specs and the layer (a grant is stored as JSON and kept raw: the previous code ignores its new fields, and its `PATCH` refuses them); its SandboxDO never reads the new kv keys, so client bindings leave the next policy (and their values the next `secrets_update`), and a push token minted after is without `workflows`. Its admin secrets route lets the operator write a `client-secret:` name; its `secrets_update` allowlist doesn't resolve one, so nothing reaches a proxy. The `/v1/clients/self/secrets` routes answer 401 (an unknown route to a non-operator). After the roll forward, everything stored is read again as before, and the next push restores the bindings.
- **For the operator's own bindings too:** a `secrets_update` reference that resolves to nothing (a deleted or expired static secret) is now left out rather than sent as `""`, so nest-proxy refuses its placeholder (`injection_unavailable`) instead of substituting an empty credential. An operator layer naming a binding `client:…` is refused (400); none existed before, as the prefix is new.
- **Operator steps after the deploy:** for a client that injects, `PATCH /v1/admin/clients/<cli> {grant}` with `secrets: {max_count, max_bytes}`, `inject_hosts` and, for CI edits, `github_push: {workflows: true}` (`PATCH` replaces the whole grant). Allow the hosts in the egress policy where the client's sandboxes run (a binding opens no host). Give the GitHub App the `workflows` permission before granting it (GitHub refuses a token naming a permission the installation lacks). Keep repos' CI secrets in approval-gated environments ([workflow files](../../docs/control-plane/api/clients/#workflow-files)).
- **Cloud check:**
  1. A client on `use1` with `secrets: {max_count: 2, max_bytes: 256}` and `inject_hosts: ["httpbin.org"]`, with `httpbin.org` allowed in the operator's base or a sandbox layer, stores `PUT /v1/clients/self/secrets/probe {"value": "<a random string>"}`.
  2. It creates `POST /v1/sandboxes {"cell": "use1", "inject": [{"name": "probe", "secret": "probe", "hosts": ["httpbin.org"], "locations": [{"type": "header", "name": "X-Probe"}]}]}`.
  3. In the sandbox (through an agent's hands, e.g. its `Bash`), `curl -s -H "Accept-Encoding: identity" -H "X-Probe: nest-ph.<cli>.probe." https://httpbin.org/headers` (uncompressed: the proxy masks only a body it reads as identity) shows the header masked to the value's length (the proxy masks a reflected secret, so the upstream got it), `env` and the sandbox's files hold only the placeholder, and the same header to `example.com` is refused with `egress_alert`.
  4. `GET /v1/clients/self/secrets` shows `probe` with `size` and `last_injected_ms` and no value; another client's `DELETE /v1/clients/self/secrets/probe` answers 404; BrokerDO's audit has `client_secret_injected` for the sandbox, without the value.
  5. Then `DELETE` the sandbox and the secret.
