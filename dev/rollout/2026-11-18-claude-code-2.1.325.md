# Claude Code baseline 2.1.325 (2026-11-18)

Not a one-way deploy, and no ordering constraint with the Worker: the change is `CLAUDE_VERSION` in `deploy/host/install.sh`, and nothing in the control plane reads it.

- **What the apply changes:** a new version of both launch templates (their user data carries `install.sh`), and the Image Builder component and recipe (their version is `install.sh`'s hash). `AWS_CELLS` names the templates, not their versions, so it doesn't change, and the Worker job deploys the same bundle. No release is built: its inputs (`crates/`, `protocol/`, the Cargo files, the toolchain, `.cargo/`, `scripts/publish-release.sh`) are unchanged. So no host AMI build starts either, since the release job starts one only after a publish. The AMI the launch templates resolve keeps 2.1.301 until the next build.
- **When a host gets 2.1.325:** at launch, after the apply. `install.sh` runs in its user data, finds the AMI's 2.1.301, and installs 2.1.325 with Claude's native installer. The installer comes from `downloads.claude.ai`, so every boot downloads the binary (about 366 MB uncompressed) until a host AMI built after the apply bakes 2.1.325 in. To bake it sooner, start a build by hand: `aws imagebuilder start-image-pipeline-execution --image-pipeline-arn <nest-use1-host>` (`deploy/lean/Cell/Stack.lean`). A host that is already running keeps 2.1.301 until it is replaced (idle retirement, spot loss, autoscaling). Both kinds run `install.sh`; only brain hosts run Claude Code.
- **A mixed fleet:** brain placement doesn't look at Claude Code versions, and both host sets run the same nest release. Its only preference is the host that ran the agent last ([brain hosts](../../docs/compute/brain-hosts/)), so until the last 2.1.301 brain host is gone an agent's session can move between versions in either direction:
  - **Written by 2.1.301, resumed by 2.1.325:** the upgrade gate (resuming the previous baseline's sessions, [runner](../../docs/agents/runner/)). The owner checks it before approving.
  - **Written by 2.1.325, resumed by 2.1.301:** an older binary reading a newer session file. This is unverified. The session JSONL is internal and "changes between versions" ([sessions](https://code.claude.com/docs/en/sessions)), and no gate covers this direction. If the older binary can't resume the file, `--resume` fails at the brain's start. The agent then needs a fresh session, as for a rollback ([provisioning](../../docs/compute/provisioning/#upgrades)).
- **Closing the window:** retire the 2.1.301 brain hosts, so every brain starts on 2.1.325. These are the ones launched before the apply (their launch time, or an `aws:ec2launchtemplate:version` tag below the brain template's new default version; FleetDO doesn't keep the `claude_code` version a host's `hello` carries). `POST /v1/admin/hosts/<id>/drain` doesn't work here: it refuses a brain host with 409 ("only a sandbox host is drained by hand", `FleetDO.drainHost`). Two ways that do work:
  - **Wait:** a brain host with no brain for 30 min is terminated.
  - **Terminate it in EC2 while its agents are idle:** a brain host holds no sandbox. Once its lease expires (30 s), AgentDO starts each of its brains on another brain host with `--resume`, or FleetDO launches one on 2.1.325. A brain mid-turn loses up to 5 s of transcript that wasn't yet durable, and its turn continues through AgentDO's recovery turn.

  Terminate one host at a time, and the next only when no brain still waits for a host.
- **Rollback (a forward revert):** a PR that sets `CLAUDE_VERSION` back to 2.1.301. Hosts launched after that apply install 2.1.301. Hosts launched in the meantime keep 2.1.325 until they are replaced, so the fleet is mixed the other way round. A session that 2.1.325 wrote and 2.1.301 can't resume needs a fresh session. If a host AMI was built with 2.1.325, `install.sh` reinstalls 2.1.301 at each boot until the next build.
