# GitHub guards where nest injects no GitHub token (2026-11-12)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for the GitHub constructor's guards [without nest's own token](../../docs/sandbox/networking/egress/policy/#github).

**Not a one-way deploy. Ordering: after #273 (a binding's Basic username, and `at` on Basic only then), which merged first. No manual host check: the control plane gates on what each host says** (the `nest-wire` capability-flag pattern; [deploy](../deploy.md) never gates the Worker on a release having rolled out). nestd's fleet hello says `guard_sealed_segments` (this release's nest-proxy seals encoded separators, below); FleetDO keeps it per host (`hosts.guard_sealed_segments`, default 0). A host enforces `at` only with both it and `guard_basic_user`: a sandbox with a Basic binding or a guard using `at` is placed only on such a host, a write newly bringing `at` (or a Basic binding beside it) to a sandbox on another is refused (409 `hosts_not_ready`), and what a sandbox holds anyway is pushed to another without `at`, failing closed. A host launched from an earlier release (between this Worker's deploy and the host release's publication, or by a host rollback) says no `guard_sealed_segments` for life, and is treated so. Before it, `at` takes a Basic field as nest's whole whatever username the sandbox chose, so the exception below would hold for a credential the sandbox planted as the username. No stored state, route or wire field: only the guards SandboxDO builds for a sandbox with no repos of either kind and no operator GitHub binding change, and they reach nest-proxy at its next policy push (`policy_update` or a create). A sandbox with nest's own token gets exactly the guards it did.

- **What changes:** in those sandboxes (no repos of either kind, and no operator binding that is a GitHub credential by name, placeholder or a `github.com`/`*.github.com` host), `github-push`, `github-api-write`, and `github-write` for receive-pack and Git LFS's API only, let a write through when the request's one `Authorization` field is a credential nest's injection wrote whole (`{injected: "*", at: authorization}`), and `github-push` lets push discovery through bare. Before, they refused every write there. github.com's cookie-authenticated web routes stay refused.
- **Hosts:** the exceptions use `*` and `at`. A nest-proxy without `guard_injected_any` reads `*` as a binding named `*` (never present): fail closed. And since they use `at`, every sandbox without repos (and no operator GitHub binding) now needs a host that enforces `at` (`guard_basic_user` and `guard_sealed_segments`): with none free it waits, unplaced. A sandbox already on another host when this deploys gets its guards without `at` at its next push: its GitHub writes are refused there until it moves. **Availability:** while a cell's sandbox hosts are #273's (`guard_basic_user` without `guard_sealed_segments`) or older, sandboxes without repos wait unplaced; if the cell is at its host cap, so no new host (of this release) is launched, the operator drains or replaces those hosts ([deploy](../deploy.md)). Residual (unverified): FleetDO's `hosts` columns keep the last hello's flags, so after a host rollback a host keeps what it last said until it says hello again; whether a Durable Object deploy makes every host say hello again isn't checked.
- **Who it's for:** the projects app's new spawns, which bind their own GitHub tokens as client secrets and add their own client guards. They need this release live before they can push.
- **What a rollback does:** the previous release builds the old guards again at the next policy push, so those sandboxes refuse every GitHub write again, an app's own binding's included. Nothing to undo.
- **Removed by** phase C3, with the constructor: the operator then keeps a floor like this in the base layer, as data.
- **nest-proxy:** a path segment holding `/` or `\` once decoded matches an exception only under `**`, so `/o/r%2Ftree-save%2Fmain/git-receive-pack` isn't taken for git's. A host image from before this release lacks it: there the exceptions this release adds for a sandbox without repos would take that spelling, which nothing let through before (such a sandbox had no exception for git's writes at all). Hence `guard_sealed_segments` above. Residuals (unverified against GitHub's routing): the LFS exceptions also match paths without `.git`, served by github.com's web app (no known write route); an overlong UTF-8 slash (`%C0%AF`) or a fullwidth one (`%EF%BC%8F`) isn't sealed; a `;params` suffix inside a `*` segment is taken as part of it; decoding stops after three rounds; and `tests/guard_equivalence.rs`'s comparison with the previous evaluator skips paths with an encoded separator (there the new one only refuses more, checked in the other test).
- **A pre-existing hole closed here, in every sandbox:** `github-write`'s fetch exceptions (`POST …/git-upload-pack`, and LFS batch downloads) were open in front (`/**/…`), so a cookie-authenticated web-editor write whose path ended like one (`/<o>/<r>/tree-save/<branch>/git-upload-pack`) passed with no credential at all. They are anchored at the repo now (`/*/*/…`); git's own fetches are unchanged.
