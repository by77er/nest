# GitHub guards where nest injects no GitHub token (2026-11-12)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for the GitHub constructor's guards [without nest's own token](../../docs/sandbox/networking/egress/policy/#github).

**Not a one-way deploy. Ordering: after #273 (a binding's Basic username, and `at` on Basic only then), or with it, and only once every sandbox host of each cell runs a host release built from this PR's nest-proxy or later (which also reports `guard_basic_user`).** The deployer checks that last before the Worker deploys: each cell's sandbox hosts not dead (FleetDO's `hosts` rows, `guard_basic_user = 1`) were all launched from a host release published from this PR's merge or later ([deploy](../deploy.md)); FleetDO records no host version, so the deployer compares launch times with the release's publication. This release adds `at` to a live sandbox's GitHub guards when it holds no repos, at its next policy push, so a sandbox already on an older host with a Basic binding would get `at` there with no write to gate it. Today use1 has no sandbox hosts, and new ones install the current release. Before it, `at` takes a Basic field as nest's whole whatever username the sandbox chose, so the exception below would hold for a credential the sandbox planted as the username. No stored state, route or wire field: only the guards SandboxDO builds for a sandbox with no repos of either kind and no operator GitHub binding change, and they reach nest-proxy at its next policy push (`policy_update` or a create). A sandbox with nest's own token gets exactly the guards it did.

- **What changes:** in those sandboxes (no repos of either kind, and no operator binding that is a GitHub credential by name, placeholder or a `github.com`/`*.github.com` host), `github-push`, `github-api-write`, and `github-write` for receive-pack and Git LFS's API only, let a write through when the request's one `Authorization` field is a credential nest's injection wrote whole (`{injected: "*", at: authorization}`), and `github-push` lets push discovery through bare. Before, they refused every write there. github.com's cookie-authenticated web routes stay refused.
- **Hosts:** the exceptions use `*` and `at`, which a nest-proxy without `guard_injected_any` reads as a binding named `*` (never present): fail closed, so such a write is still refused there, as before. No placement constraint follows (only exceptions use `*`). Every sandbox host launched since #267 has the flag.
- **Who it's for:** the projects app's new spawns, which bind their own GitHub tokens as client secrets and add their own client guards. They need this release live before they can push.
- **What a rollback does:** the previous release builds the old guards again at the next policy push, so those sandboxes refuse every GitHub write again, an app's own binding's included. Nothing to undo.
- **Removed by** phase C3, with the constructor: the operator then keeps a floor like this in the base layer, as data.
- **nest-proxy:** a path segment holding `/` or `\` once decoded matches an exception only under `**`, so `/o/r%2Ftree-save%2Fmain/git-receive-pack` isn't taken for git's. A host image from before this release lacks it: there the exceptions this release adds for a sandbox without repos would take that spelling, which nothing let through before (such a sandbox had no exception for git's writes at all). Hence the host check above. Residuals (unverified against GitHub's routing): the LFS exceptions also match paths without `.git`, served by github.com's web app (no known write route); an overlong UTF-8 slash (`%C0%AF`) or a fullwidth one (`%EF%BC%8F`) isn't sealed; a `;params` suffix inside a `*` segment is taken as part of it; decoding stops after three rounds.
- **A pre-existing hole closed here, in every sandbox:** `github-write`'s fetch exceptions (`POST …/git-upload-pack`, and LFS batch downloads) were open in front (`/**/…`), so a cookie-authenticated web-editor write whose path ended like one (`/<o>/<r>/tree-save/<branch>/git-upload-pack`) passed with no credential at all. They are anchored at the repo now (`/*/*/…`); git's own fetches are unchanged.
