# API clients (2026-11-02)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)).

**Not a one-way deploy; it needs the ClientDO declaration deployed first.** The class shipped alone, as a stub, in the one-way deploy before it; this release fills it in ([API clients](../../docs/control-plane/api/clients/)), so `wrangler rollback` crosses it back to the stub. No host change: `agent_spawn`'s new optional `labels` reaches a runner only through `tools_list`.
- **What a rollback does:** the stub serves only health and ignores ClientDO's stored records, so client tokens stop working (401 from the previous release's admin-only routes) and nothing is admitted or counted; each client's record and registry stay as they were. The previous release ignores the records' `client` and `labels` (kept). After the roll forward, an agent that ended meanwhile reports it at its next alarm (its registry state is compared, not assumed), and ClientDO's hourly recheck of live rows finds a sandbox destroyed meanwhile. Catalog rows naming `<client>/<entry>` don't parse under the previous schema and are skipped (logged).
- **Stored data (expand-only):** AgentDO and SandboxDO records gain `client` and `labels` (absent: the operator's, no labels). An agent's `owner` may now be a client id: only an `agt_` owner is told of an end or walked as an owner chain. FleetDO's `agent_registry` and `sandboxes` gain nullable `client` and `labels`; rows from before read as none, so a label filter skips them. Catalog rows may be named `<client>/<entry>` and name such entries.
- **API:** the agent and sandbox routes an owner needs take a client token as well as the admin token (`auth: "owner"`); `GET /v1/agents` and `GET /v1/sandboxes` are new. A client's `overrides` are `SpawnerOverrides`. `PUT /v1/agents/<id>/rules`, policy layers, ports, grants, `resolve` and `place` stay admin-only. `POST /v1/agents` accepts `owner: "user"`.
- **Operator steps after the deploy:** `POST /v1/admin/clients {name, grant}` for each external system; keep the token it answers (shown once) in that system's secrets.
- **Cloud check:** `GET /v1/health` names `ClientDO` `ok`. Then create a client with a grant on `use1` (`credentials: ["claude_oauth_token"]`, `max_agents: 1`). With its token, `PUT` a template in its namespace and `POST /v1/agents {template: "<name>/<t>", cell: "use1", start: false, labels: {k: v}}`; `GET /v1/agents?label=k=v` lists it, and a second create answers 403. `GET` an operator agent's id with the client token answers 404. End the agent and delete the client.

**Generation retention is on by default** (the owner's call, 2026-11-01: `report` mode is removed, with no report period).
- **The switch** (`SANDBOX_RETENTION`, an optional var `dev/deploy-use1.sh` passes from the SSM parameter `/nest/control-plane/vars/SANDBOX_RETENTION` when it exists): unset or `on`, each sandbox's pass (a minute after a commit, every 6 h, and from its lifetime check) marks what it drops `deleting` (at most 500 a pass) and logs `retention: N ready, M to drop (K marked deleting, …)` in Workers Logs. `GET /v1/sandboxes/<id>/generations` lists every generation with `state` and `retained` (why it is kept). A long-lived sandbox drops most of its history on its first pass.
- **The first GC run after retention turns on is dry:** FleetDO records when it first sees `on` and counts only runs marked after that as proven. Check its report (`GET /v1/admin/gc?cell=use1`: `sweep_objects`, `sweep_bytes`, the sample) before the run after it deletes. Bytes go no sooner than that second run, after the 24 h grace.
- **Emergency stop:** `aws ssm put-parameter --name /nest/control-plane/vars/SANDBOX_RETENTION --type String --value off --overwrite`, then redeploy (`workflow_dispatch`). Passes stop marking; what is already `deleting` or unrooted stays so (one-way): roots follow those marks in either mode, so nothing a sweep may have taken is rooted again. Deleting the parameter (or `on`) turns it back on and makes the next GC run dry again.
- **A residual race** (unverified: it depends on when each Durable Object restarts on the new version): FleetDO decides dry or not at a claim, from its own code and env. If SandboxDOs already mark while FleetDO still runs the previous release (minutes, [upgrades](../../docs/control-plane/#upgrades)), a run in that window deletes without the dry run first. The marks are retention's decisions either way; only the review is skipped. Check `GET /v1/admin/gc` that the first run after turning it on was dry.
