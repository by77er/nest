# The guest image's GitHub credential helper and GITHUB_TOKEN go (2026-11-15)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for [GitHub in the image](../../docs/sandbox/networking/egress/injection/#github): phase C4 of the plan to take service integrations out of nest's kernel ([decisions](../../docs/README.md#settled-decisions)). It follows C3 (`2026-11-15-kernel-github-minting.md`), after which nothing in the control plane fills `nest-ph-github`.

**Not a one-way deploy, and no ordering constraint.** No Durable Object class, table, column, route, RPC method or wire change; no `nest-guest` change. The Worker and the host release this merge publishes behave exactly as C3's: the only control-plane source change is a comment.

- **What changes:** the image's source only. `images/guest/build.sh` no longer installs `git-credential-nest`, sets git's system `credential.https://github.com.helper`, or writes `GITHUB_TOKEN=nest-ph-github` to `/etc/environment`; `build-on-ec2.sh` no longer stages the helper. `git` and `gh` stay, unconfigured. The fixtures `egress_policy.github.json` and `egress_policy.github_read.json` (what C3's deleted constructor built) go with nest-proxy's tests on them; `egress_policy.github_none.json` becomes `egress_policy.base_floor.json`, the floor use1's base layer holds (its guards exactly as `GET /v1/admin/egress/base?cell=use1` answered them on 2026-11-15, version 1), which a vitest carries through `PUT /v1/admin/egress/base` to a sandbox's policy.
- **When it reaches sandboxes: at the operator's next hand rebuild, not at the merge.** The pipeline carries `vmlinux` and `nest-base.ext4.zst` over from the current release (`scripts/publish-release.sh`), so the live image keeps the helper until then. The rebuild is the operator's (it launches a builder instance):
  1. `images/guest/build-on-ec2.sh <bucket> <subnet> <security group> <instance profile> <ami> <root CA PEM>`, then wait for `images/guest/<build id>/SHA256SUMS` (its `build.log` ends in `BUILD-OK`).
  2. Not while a deploy runs: copy `releases/current/{vmlinux,nest-base.ext4.zst,SHA256SUMS}` to `images/guest/previous-<date>/` (the backup `scripts/prune-images.sh` keeps).
  3. Copy the build's `vmlinux` and `nest-base.ext4.zst` into `releases/current/`, then, last, `releases/current/SHA256SUMS` with those two lines replaced by the build's: hosts verify every file against it (`deploy/host/install.sh`), and `publish-release.sh` refuses carried files it doesn't vouch for.

  These steps are read from the scripts, not from a written procedure (unverified as a whole). The rebuild ships more than C4: it builds from `releases/current/nest-guest`, so every `nest-guest` change since the last rebuild arrives with it (the guest's hostname fix in `dev/cloud-checks/stress-2026-10-31.md`, for one), and apt installs the day's `noble-updates` and `noble-security` versions of git, `gh` and the rest. The host serves a range of guest versions ([host-guest](../../docs/interfaces/host-guest/)).
- **Then, which sandboxes get it:** hosts install `releases/current/` at boot, so the new image reaches each sandbox host as it is replaced. A sandbox created there gets a copy of it. A sandbox with a committed generation boots its own disk wherever it moves, and a fork copies its parent's, so every sandbox created from the older image (every live one today), and its forks, keeps the helper; one that never committed a generation boots a fresh copy of whichever image its host has.
- **A sandbox with the older image's disk** keeps the helper and `GITHUB_TOKEN=nest-ph-github`. Nothing fills that placeholder unless an operator binding takes it (none does; an operator binding whose placeholder were `nest-ph-github`, or contained in it, would be filled from these disks), so git and `gh` without an app's environment send it to GitHub as a credential and are refused; the base layer's floor refuses their writes first, since no credential nest injected is in `Authorization`. The projects app's sandboxes are unaffected: their `GH_TOKEN` comes before `GITHUB_TOKEN` for `gh`, and their `GIT_CONFIG_*` empties git's helper list before adding the app's (`projects/test-node/git-credential.test.ts` runs both against each image's configuration).
- **A sandbox with the new image** has no helper and no GitHub environment. Without an app's environment, git asks for a credential only after GitHub's 401 and, finding no helper, prompts on a terminal or fails without one; `gh` has no token, so its commands that need one fail and ask for `gh auth login`. Public fetches work as before. An app's sandboxes get the same `GH_TOKEN` and helper from the app as on the older image.
- **The control plane against either image:** no difference since C3; it reads nothing from the image. `nest-ph-github` stays out of every placeholder nest assigns (`injectionPlaceholder`; nest-proxy finds placeholders as substrings) while older disks may carry it.
- **What a `wrangler rollback` does:** the previous Worker (C3's) behaves the same. A Worker from before C3 is two versions back; there, a sandbox with kernel repos on a new-image disk would push with no credential (git finds no helper) and be refused: narrower, and no live sandbox has kernel repos.
- **Rolling the image back:** put the `previous-<date>/` files back into `releases/current/` the same way (`SHA256SUMS` last); hosts launched after that create sandboxes with the helper again, which nothing fills. Sandboxes created from the new image keep it.
- **Cloud check after the rebuild:** on a sandbox created on a host with the new image, `command -v git-credential-nest` and `git config --system --get-all credential.https://github.com.helper` print nothing, and `GITHUB_TOKEN` is unset; a projects start still pushes its branch.
- **Contract:** nothing to drop now. The `nest-ph-github` exclusion goes once no sandbox created or forked from the older image remains (phase C6, [decisions](../../docs/README.md#settled-decisions)).
