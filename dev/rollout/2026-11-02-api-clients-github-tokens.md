# API clients' GitHub tokens (2026-11-02)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)).

**Not a one-way deploy.** No Durable Object class is added and no host changes: BrokerDO gains a method, `clientGithubToken`, and no table (a client's tokens share `github_tokens`, under `client:` keys). It needs the API clients release below deployed first.
- **The gap after the deploy:** until BrokerDO restarts on this release (minutes, as for any new DO method: see `worker` above), `POST /v1/clients/self/github-token` finds no method and answers `503` (`internal`, `retryable: true`), never 500. A client retries.
- **Grants:** `POST` and `PATCH /v1/admin/clients` now take only GitHub's repository permissions in `github.permissions`, at the levels GitHub offers (`workflows` only `write`; `repository_projects` also `admin`); organization and account permissions are refused. A grant stored by the previous release reads as stored; a name in it outside the list can't be asked for, so it mints nothing.
- **What a rollback does:** the route answers 401 (an unknown route to a non-operator). Tokens already handed out last until they expire, an hour at most. The previous code never reads the `client:` rows in `github_tokens` (its keys start with a repo); after the roll forward they're reused or deleted once expired. A grant stored with `repository_projects: admin` stays as stored: the previous code doesn't re-validate stored grants.
- **Operator steps after the deploy:** give the GitHub App the repos and permissions a client's grant will name (a token can't exceed the installation's; GitHub refuses, and the route answers 502). Then `PATCH /v1/admin/clients/<cli> {grant}` with `github: {repos, permissions}` added (`PATCH` replaces the whole grant).
- **Cloud check:** create a client with `github: {repos: ["by77er/nest"], permissions: {pull_requests: "read"}}`. With its token, `POST /v1/clients/self/github-token {"repo": "by77er/nest", "permissions": {"pull_requests": "read"}}` answers 200 with `expires_at` about an hour on (retry a 503 for up to 10 minutes). Without printing the token, pipe it into `GET https://api.github.com/installation/repositories`, which lists only `by77er/nest`. Asking for `contents: read` answers 403, and the admin token 403. The day's `audit/broker/` in R2 has the mint with `caller: {client: "cli_…"}` and no token. Then delete the client.
