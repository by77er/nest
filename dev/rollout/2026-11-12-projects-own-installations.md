# The projects app lists and binds repos through its own App's installations (2026-11-12)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for the projects app ([repo authority](../../projects/README.md#repo-authority)): phase B2 of the plan to take service integrations out of nest's kernel ([decisions](../../docs/README.md#settled-decisions)). It needs B1 (`2026-11-12-projects-own-app-tokens.md`) deployed first: it builds on its App tokens.

**Not a one-way deploy, and no ordering constraint** beyond B1's (the App's secrets set). No nest change, no Durable Object class, table or column, no stored state.
- **What changes at deploy:** the create form's repo list (`GET /api/repos`) is the App's installations' repos (`GET /app/installations`, then each one's `GET /installation/repositories` with a token of that installation, `metadata: read`, revoked after), not nest's `/v1/clients/self/grant/repos`. Creating a project and applying a rename ask GitHub (the installation lookup and a mint narrowed to the repo), not nest. The app's own GitHub tokens are no longer checked against nest's grant (B1 checked them).
- **Before deploying, the owner checks:** the App's installations select every repo a project is on (else its calls are refused, 404 or 422, shown as each call's failure); every project's repo is on the App owner's account, or `GITHUB_ACCOUNTS` (a Worker var, account ids) names its account (else the app refuses it, as not covered); and nest's grant `repos` still covers every repo the App reaches that a project may be put on (until B3, nest checks spawns and catalog templates against it: a repo it doesn't cover attaches, gets its branch protection requiring `nest-projects/review`, and no reviewer to set that check). The owner-wide grant entry for the owner's account covers this.
- **Cloud check:** after the deploy, the New project form lists the repos of the App's installation (the same as before, if the grant and the installation agreed); an attached project's Re-read answers 200; the Worker's logs show no calls to `/v1/clients/self/grant/repos`.
- **What a `wrangler rollback` does:** the previous release (B1) lists through nest's grant again and checks its tokens against it. Nothing this release wrote is read differently: a rename it applied because the App reached the new name is a directory rename like any other, and a binding that followed a transfer to another account's installation keeps that installation (B1 follows the same lookup).
- **Contract, with phase C1:** nothing of this release's to remove; nest's `/grant/repos` routes can go once no deployed app release calls them (this one doesn't).
