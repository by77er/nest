# Rule approvals let the call through (2026-11-11)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)).

**Not a one-way deploy, and no ordering constraint.** No Durable Object class or table is added. AgentDO's `approvals` gains nullable `kind` (`sink` or `rule`; null reads as `sink`), `input` and `input_bytes` columns, and its record an optional `rules_version`. The session channel gains `approval_check` (runner → AgentDO), `approval_checked` (AgentDO → runner), both unreliable, and an optional `hello_ack.rule_approvals`; fixtures in `protocol/fixtures/control/`.

- **Worker first, hosts a release behind:** a runner of the previous release never sends `approval_check`; it emits `escalation`, which this AgentDO records as the plain question it always did (its answer can't let the call through, as before). It ignores `rule_approvals` (an unknown field) and never receives `approval_checked`.
- **New runner, previous AgentDO** (a `wrangler rollback`, or a brain host upgraded first): that AgentDO's `hello_ack` has no `rule_approvals`, so the runner never sends `approval_check` on that connection (a check made while disconnected is answered unsupported, never sent) and escalates instead. The previous AgentDO would refuse the message as `invalid_message` and the runner would reconnect, which is why it's gated.
- **What a rollback does with the rows this release wrote:** the previous release reads `approvals` without `kind`. A rule's approval has `name` = the Claude Code tool (`WebFetch`, `mcp__nest__…`), which no sink name takes, so its sink gate never matches one; an approved rule row has `expires_ms` null, which its `approvalUsable` treats as unusable anyway. Its hourly prune deletes a decided rule approval asked for over 7 days ago and still unspent: the call is then asked again (fail closed). An open rule ask answered under the previous release is decided with its one-hour expiry and the turn text it always sent; its runners escalate, so the approval goes unused.
- **The shim:** `escalation`'s plain-question handling and the runner's fallback stay while any runner predates this release or any rollback reaches a Worker without `rule_approvals`; drop both, and make the flag implicit, in the release after every brain host runs this one.
- **`nest hook --event` (a separate fix in the same PR):** the managed settings now pass `--event <event>` to every sync hook. They ship in the host image with the `nest` binary that reads it; a previous binary ignores the extra arguments (it looks only for `--sync`), and this binary without `--event` denies unreadable input as a `PreToolUse`. Nothing in the control plane.
- **Answers that approve:** `approves()` now takes only a bare approving word (`approve`, `yes`, `ok`, …); an answer that merely starts with one, which used to approve a sink call, now denies it. The projects app sends exactly `approve`. A client that answers in phrases ("ok, go ahead") gets denials from this release on.
- **Questions and `input`:** an approval's question is now one argument a line (it was JSON in prose), and `GET /v1/agents/<id>/asks` adds `input` and `input_bytes` (additive). A client that parsed the old question text must read `input` instead. A rollback's previous release ignores the two columns and lists asks without them.
