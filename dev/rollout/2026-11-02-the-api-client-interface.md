# The API client interface: mcp capabilities without `auth`, `?cell=` only on a cell's routes, idempotency keys on creates (2026-11-02)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)).

**Not a one-way deploy.** No Durable Object class is added (ClientDO gains a table, `idempotency_keys`, and an instance, `operator`, that holds the operator's keys), and no host change: everything is the Worker's ([which routes take a cell](../../docs/control-plane/api/#which-routes-take-a-cell), [idempotency keys](../../docs/control-plane/api/#idempotency-keys), [no bearer](../../docs/agents/capabilities/mcp/#no-bearer)).
- **The gap after the deploy:** a ClientDO still on the previous code for minutes has no `claimKey`: a create with an `Idempotency-Key` answers `503` (`internal`, `retryable: true`) until it restarts, never 500; a create without one is unchanged. A caller retries with the same key.
- **Stored data (expand-only):** ClientDO's new `idempotency_keys` table; a capability's `mcp` may omit `auth`; an agent's spec's mcp grants may omit `auth` and carry `client` (the client whose namespace the capability is in). Nothing is renamed or dropped. A connector's name is unchanged for a grant with a credential and no client, so existing agents keep their connectors; an agent spawned from a client's own mcp capability gets that namespace's connector, whose first list is one more `tools/list` to the server.
- **What a rollback does:**
  - The previous schema requires `auth`: CatalogDO skips (and logs) a capability without one, so templates listing it don't expand (spawns answer 400) until the roll forward. An agent spawned with such a grant has its calls refused `forbidden` by BrokerDO (`undefined is not a capability credential`) and its server listed nothing: no request leaves without a credential the previous code expects.
  - Routes that aren't about a cell check `?cell=` again: a caller sending none gets 403 `unknown cell local` where `CELLS` doesn't name `local` (`use1`). The dashboard, the e2e harness and `dev/cloud-checks/` send one where they did before.
  - The `Idempotency-Key` header is ignored: a create retried during the rollback can make a second object. The keys stay unread and still bind for the rest of their 24 h after the roll forward; a create made during the rollback was never recorded.
- **Operator steps after the deploy:** none. An external app may drop its `?cell=` from routes that aren't a cell's, send `Idempotency-Key` on creates, and drop a placeholder secret it stored only to satisfy `auth` (its capability rewritten without `auth`; then the secret and the grant's credential go).
- **Cloud check:** with a client on `use1` and its token, and no `?cell=` anywhere: `PUT /v1/catalog/templates/<name>/t` answers 200 (was 403 `unknown cell local`). `POST /v1/sandboxes {"cell": "use1"}` with `Idempotency-Key: <uuid>` twice: the same `sandbox`, the second with `Idempotent-Replayed: true` (retry a 503 for up to 10 minutes); with `{"cell": "use1", "labels": {"x": "y"}}` and the key, 409 `conflict`. Then `DELETE /v1/sandboxes/<id>`. A capability without `auth` can't be checked end to end against `mcp-test/` (it requires its bearer): put one naming it, spawn an agent and call `echo`: the answer is `unauthorized`, naming the caller identity as the only credential sent (`mcp-test` refuses any request without its bearer). The header itself is checked only in `test/mcp.test.ts`.
