# API clients' request guards (2026-11-12)

A release's rollout rule ([Rollout rules](../deploy.md#rollout-rules)), for [request guards](../../docs/control-plane/api/clients/#request-guards).

**Not a one-way deploy. One ordering constraint, enforced by the control plane:** client guards apply only once every sandbox host of a cell runs this release's nest-proxy.
- **Why:** hosts take a release only when they are replaced, so a nest-proxy of the previous release (decoding per matcher, on targets of any length) can run indefinitely, and on one a client's guards could cost about 0.2 s per request on workers every sandbox on the host shares.
- **How it's enforced (the `nest-wire` capability-flag pattern, as for `brain_epochs`):** nestd's fleet hello says `guard_bounds: true` (nest-proxy ships with it); FleetDO records it per host (`hosts.guard_bounds`, default 0). SandboxDO refuses (409) a create, a client-layer write or an attach that brings client guards while any sandbox host of its cell, any not dead, lacks it (a layer write whose guards are all already stored goes through). Refused, never dropped, since a dropped guard fails open. FleetDO places a sandbox whose policy carries a client guard only on a host with it; with none free, it waits unplaced. Chosen over a written rule because any client can write guards the moment the Worker deploys, and nothing else would stop it.
- **Control plane:** new optional fields (`guards` in the client layer, sandbox specs, templates, spawn overrides and stored agent specs), two SandboxDO kv keys (`client_guards`, `agent_guards`) and a FleetDO column (`hosts.guard_bounds`). Client guards reach nest-proxy as ordinary `RequestGuard`s in `EgressPolicy.guards`: no policy wire change.
- **nest-proxy:** decodes a guarded host's request once instead of per matcher, tries one split for a pattern with one `**` (the same decisions: `tests/guard_equivalence.rs`), and refuses a request to a guarded host whose path is over 4096 bytes or 256 segments or whose query is over 8192 bytes or 256 parameters (414 `request_target_too_long`). That applies to the GitHub rules' hosts too: a longer URL to `github.com`, `*.github.com` or `*.githubusercontent.com` from a sandbox now fails (long non-ASCII file names, percent-encoded, are the likely case).
- **In the gap** (the Worker deployed, a cell's hosts one release behind): client guards are refused in that cell; the operator's guards and the GitHub rules run on the old proxy as before.
- **Apps:** send `guards` only to a control plane whose `GET …/client-policy` answers them, and check `GET …/policy` for the `client:` guards they rely on.
- **What a rollback does:**
  - **Refused (400):** `PUT …/client-policy` and client spawn overrides carrying `guards`.
  - **Silently dropped, with a 2xx (fails open):** `POST /v1/sandboxes`, template writes and the operator's spawn overrides carrying `guards`. What they make has none of the refusals.
  - **Stored guards stop applying:** the previous release ignores the new kv keys and spec fields, so its next policy push for a sandbox leaves the client guards out (the operator's guards and the GitHub rules are unaffected). It strips `guards` from a template when it reads it. An agent detached under it leaves its `agent_guards` entry behind, which this release ignores (only attached agents' keys count).
  - **Rolling forward** applies the stored guards again at each sandbox's next policy push, which nothing forces: an app rewrites its client layers (`PUT …/client-policy`) to get them back at once. A template written during the rollback must be written again.
  - **A host rollback** (hosts of the previous release launched again): sandboxes with client guards are never placed on them. One already on a current host stays there. One that needs placing again (spot loss, a reassignment) while only old hosts are free waits unplaced, unavailable rather than unbounded, until a current host is free. New client guards in their cells are refused until the old hosts are replaced; layer writes that add none still go through.
  - **A control-plane rollback** leaves `hosts.guard_bounds` unread; this release reads it again from each host's next hello.

So an app must not rely on client guards for a refusal it can't lose until this release is settled.
