# CatalogDO

One instance (`catalog`): the [templates and capabilities](../../../agents/capabilities/) I edit, stored as data. Spawning reads it; nothing else does.

- **Capability:** `{tools, rules, prompt, spawn?, mcp?, brokered?}` (`mcp`: [mcp capabilities](../../../agents/capabilities/mcp/); `brokered`: [brokered actions](../../../agents/capabilities/brokered/), copied into the spec at spawn like `mcp`): platform tools from the registry (`platform-tools.json`), the runner's permission rules they need (the per-tool rules grants will replace), and a prompt section. `spawn` names the templates its `agent_spawn` may spawn from (the spawn grant; the spec's `spawn` is the union, and it isn't checked against existing templates, which may come later). A row stored without `spawn` has none; a stored `params` (the task ledger's) or `grants` (channel grants, below) is ignored.
- **Template:** `{capabilities, launch, hands: required | forbidden | optional, credential, repos?, read_repos?, ephemeral?, sandbox_idle_ttl_ms?, share_sandbox?}`. `repos` is its agents' push allowlist, `read_repos` the repos they may only read ([read-only repos](../../../sandbox/networking/egress/policy/#read-only-repos)). The last three are [lifetimes](../../../agents/#lifetimes): its agents end themselves when done; the idle TTL of a sandbox `agent_spawn` makes for them (absent: the cell default); a spawner may attach one to its own sandbox (`sandbox: share`). `credential` names a Claude setup token in [BrokerDO](../broker/) (`claude_oauth_token` or `claude_oauth_token:<name>`, nothing else: its value goes to a brain host).
- **Seeded once** with the current seed. Seed version 1 (`SEED_CATALOG_V1`, frozen) is `worker` and `captain` matching the previous release's roles of those names (tools, launch, rules and setup token), so records migrated from a role behave the same; a new catalog's `captain` also lists `spawning`. A new catalog also differs from version 1 where the design does: `management` has no `delegate` (no such tool), and `worker` has no `subagents` and launches with Claude Code's task and web tools only (`TaskCreate`, `TaskGet`, `TaskUpdate`, `TaskList`, `WebSearch`, `WebFetch`; no `TodoWrite` or `Agent`, [runner](../../../agents/runner/)). A catalog seeded earlier keeps its entries until I edit them (`PUT` with the `GET /v1/admin/catalog` body changed). An entry I delete stays deleted.
- **Seed migration:** each later seed version (`SEED_STEPS` in `lib/spec.ts`, pure: `seedMigration`; versions strictly increase, each release appends the next) adds its new entries once to a catalog seeded earlier (no `seed_version`: version 1), only where the name is free, and records the version reached (`kv.seed_version`) in the same synchronous step; adding never edits an entry, so an entry I delete after the migration stays deleted and an operator's entry of the same name stays theirs. Version 4 adds `egress` (`egress_policy`), in no seed template. Version 5 adds `spawning` (`agent_spawn`, `agent_stop`; `spawn: [worker]`), which a new catalog's `captain` lists.
  - **Compat (one release):** every template row written (a `PUT` or a fresh seed) also carries the previous release's `escalate_to: user` and `subscribe: []`, which that release requires (no default for `escalate_to`), so a rollback still spawns from it; this release's schema strips both on read, and a stored row's are ignored.
  - Version 2 added `channels` and `messaging-tree`, which version 7 removes: a catalog that skips from before 2 to 7 never gains them.
  - Version 3 added `tasks` and `tasks-admin`, the task ledger's; it adds nothing now.
  - Putting an added capability in existing templates is my step (`PUT /v1/admin/templates/<name>` with the capability appended; `GET /v1/admin/catalog` gives the bodies). Not done in place because a template listing a capability whose tools the previous release lacks doesn't expand under it, so a forward revert would stop spawning from it.
  - Version 6 removes `tasks` and `tasks-admin` (the task ledger left the platform: [principle 9](../../../README.md#principles)), by name, whoever wrote them: it deletes both rows and drops them from every template's list, keeping the template's other capabilities in order, and drops the `ledger` default of a template that listed one (`pruneTemplate`, on the raw row, so fields this release doesn't know survive). The removal edits templates, unlike an addition, because a template naming a capability that no longer exists doesn't expand; the previous release, after a rollback, reads the pruned rows as ordinary templates (and would refuse a `ledger` default no listed capability declares, hence its removal). A row that isn't JSON is left alone.
  - Version 7 removes channels ([principle 9](../../../README.md#principles)) the same way: it deletes `channels` and `messaging-tree` and drops them from every template's list; from every other capability's raw row it strips the channel tools (`channel_create`, `post`, `read`, `subscribe`, `unsubscribe`, `message`) and the `grants` field, keeping its other fields; and it replaces the stored `spawning` prompt only if it is still the version-5 seed's text exactly, which promised that a child's events reach its spawner (no longer true). The previous release reads the pruned rows (a capability without `grants` has none), and the stored version (7) keeps it from adding the channel capabilities back after a rollback.
  - Version 8 removes workstreams' tools ([principle 9](../../../README.md#principles)) the same way: it deletes `messaging` (`notify`, `ask`) and `events` (`emit`) and drops them from every template's list; from every other capability's raw row it strips `notify`, `emit`, `ask` and the workstream stubs (`spawn_workstream`, `send`, `list_workstreams`, `get_status`, `wait_events`, `merge`, `notify_user`). Template rows keep their `escalate_to` and `subscribe`, which the previous release requires. A new catalog has neither capability, and its `management` none of those tools.
- **Checked on write:** a capability names only registry tools (on expansion a stored one naming a tool the registry no longer has, such as `delegate`, `spawn_agent`, `kill`, a `task_*` tool, a channel tool or `notify`, is read without it), a template only existing capabilities, each once; a capability a template lists can't be deleted, nor changed so that a template listing it no longer holds together (409). Routes: `GET /v1/admin/catalog`, `PUT|DELETE /v1/admin/capabilities/<name>`, `PUT|DELETE /v1/admin/templates/<name>`.
- **Client namespaces** ([API clients](../../api/clients/#the-clients-catalog)): an entry may be named `<client-name>/<entry>`, and templates and `spawn` lists may name such entries. A client sees the operator's entries and its own; everything written into its namespace, and every expansion in its subtree, is held to its grant (`ClientScope`: refused at write and at spawn, 403). Routes: `GET /v1/catalog`, `GET|PUT|DELETE /v1/catalog/{templates,capabilities}/<client-name>/<entry>`. A deleted client's namespace is deleted with it. The previous release's schema refuses a template or capability naming a `/` entry, so after a rollback it skips those rows (logged).
- **Expansion is a pure function** (`lib/spec.ts`, unit- and property-tested): the template's hands rule against whether a sandbox is given; tools as the union of its capabilities' (in registry order), narrowed by `overrides.tools` and never widened; rules as the capabilities' in order, each once (or `overrides.rules`); the system prompt as the template's text followed by each capability's prompt (or `overrides.launch`); `credential` from the template unless overridden.
- **Two kinds of overrides.** `OperatorOverrides` (the admin API only: the operator holds the root) may replace the launch or the rules, narrow the tools, and pick the setup token. `SpawnerOverrides`, for any spawn an agent makes, can only narrow: a subset of the template's tools, and `deny` or `ask` rules placed before the template's (first match wins); anything else (launch, built-in tools, credential, an `allow` rule) is refused. Lifetimes only shorten: `ephemeral: true` may be added, never cleared, and `sandbox_idle_ttl_ms` is the shorter of the spawn's and the template's (the cell default when the template has none: the template is the operator's, and may give longer). `share` (the spawner's own sandbox) needs `share_sandbox`. The operator's overrides may also set `ephemeral` either way. The operator's `repos` and `read_repos` replace the template's; a spawner's narrow them (`read_repos` to the template's read-only repos or its allowlist: reading a repo it may push to is less). The push allowlist narrows against the template's, not the spawner's: the spawn grant on the template is the operator's authorization for what it gives, as for tools. Narrowing against the spawner's own holdings waits for grants: tools aren't grants (a captain holds no hands tools, yet spawns workers), so checking a child's tools against its spawner's would forbid the seeded pattern.
- **AgentDO stores the expanded spec** at spawn, so editing a template changes only later spawns. `template` is shown and labels the agent's inbox posts (`<template>:<agent>`); nothing decides on it.
- **Storage:** a row that doesn't parse (a later release's shape, a hand edit) is logged and skipped, so it can't stop spawning from the other templates. The tables are bounded by what I write ([data](../../../data/#retention)).
- **Deploying it is one-way:** a new Durable Object class means `wrangler rollback` can't cross the release that adds it ([deploy](../../../../dev/deploy.md)).

**Not built:** the `api` source, capability parameters (`spawning{budget}`), grants beyond the spawn list, and their attenuation against a spawner's, backend, budget, priority and labels in a template.
