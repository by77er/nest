# CatalogDO

One instance (`catalog`): the [templates and capabilities](../../../agents/capabilities/) I edit, stored as data. Spawning reads it; nothing else does.

- **Capability:** `{tools, rules, prompt, grants}`: platform tools from the registry (`platform-tools.json`), the runner's permission rules they need (the per-tool rules grants will replace), a prompt section, and the channel grants its tools need (`{action: post | read, channel: <pattern>}`; patterns are `/`-joined literals, `*`, a final `**`, `{self}`, `{owner}` or `{child}`; [ChannelDO](../channel/)). An agent's spec holds the union of its capabilities' grants (`channel_grants`); overrides never change them. A row stored without `grants` has none.
- **Template:** `{capabilities, launch, hands: required | forbidden | optional, credential, escalate_to, subscribe}`. `credential` names a Claude setup token in [BrokerDO](../broker/) (`claude_oauth_token` or `claude_oauth_token:<name>`, nothing else: its value goes to a brain host). `subscribe: [workstream]` makes the new agent its workstream channel's subscriber.
- **Seeded once** with `worker` and `captain`, equal to what the roles were: the same tools, launch, rules and setup token. An entry I delete stays deleted.
- **Seed migration:** each later seed version (`SEED_STEPS` in `lib/spec.ts`, pure: `seedMigration`) adds its new entries once to a catalog seeded earlier (no `seed_version`: version 1), only where the name is free, and records the version reached (`kv.seed_version`); it never edits an entry, so an entry I delete after the migration stays deleted. Version 2 adds the capabilities `channels` (`channel_create`, `post`, `read`, `subscribe`, `unsubscribe`; `post` on `user`) and `messaging-tree` (`message`; `post` on `{owner}/inbox` and `{child}/inbox`: the design's `messaging{peers: tree}` until parameters exist). Putting them in templates is my step: the seed templates are unchanged.
- **Checked on write:** a capability names only registry tools, a template only existing capabilities, each once; a capability a template lists can't be deleted. Routes: `GET /v1/admin/catalog`, `PUT|DELETE /v1/admin/capabilities/<name>`, `PUT|DELETE /v1/admin/templates/<name>`.
- **Expansion is a pure function** (`lib/spec.ts`, unit- and property-tested): the template's hands rule against whether a sandbox is given; tools as the union of its capabilities' (in registry order), narrowed by `overrides.tools` and never widened; rules as the capabilities' in order, each once (or `overrides.rules`); the system prompt as the template's text followed by each capability's prompt (or `overrides.launch`); `credential` and `escalate_to` from the template unless overridden.
- **Two kinds of overrides.** `OperatorOverrides` (the admin API only: the operator holds the root) may replace the launch or the rules, narrow the tools, and pick the escalation and the setup token. `SpawnerOverrides`, for any spawn an agent makes, can only narrow: a subset of the template's tools, and `deny` or `ask` rules placed before the template's (first match wins); anything else (launch, built-in tools, credential, escalation, an `allow` rule) is refused. Narrowing against the spawner's own holdings waits for grants: tools aren't grants (a captain holds no hands tools, yet spawns workers), so checking a child's tools against its spawner's would forbid the seeded pattern.
- **AgentDO stores the expanded spec** at spawn, so editing a template changes only later spawns. `template` is shown and labels the agent's inbox posts (`<template>:<agent>`); nothing decides on it.
- **Storage:** a row that doesn't parse (a later release's shape, a hand edit) is logged and skipped, so it can't stop spawning from the other templates. The tables are bounded by what I write ([data](../../../data/#retention)).
- **Deploying it is one-way:** a new Durable Object class means `wrangler rollback` can't cross the release that adds it ([deploy](../../../../dev/deploy.md)). For one release AgentDO and WorkstreamDO also write the previous release's fields (`role`, `grants`, `captain`), derived from the new ones, so a forward revert (the previous release's code deployed again) still reads every record.
- **Escalation, until channels exist:** `escalate_to` is `workstream` (a question becomes a `needs_input` event on the [workstream channel](../../../orchestration/workstreams/#the-interim-workstream-channel), which wakes its subscriber) or `user` (the user-notification queue). The design's default, the spawner's inbox, waits for `agent_spawn`.

**Not built:** `mcp` and `api` sources, capability parameters (`messaging{peers}`, `spawning{budget}`), grants and their attenuation against a spawner's (no agent spawns yet), backend, budget, priority and labels in a template.
