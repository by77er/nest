# CatalogDO

One instance (`catalog`): the [templates and capabilities](../../../agents/capabilities/) I edit, stored as data. Spawning reads it; nothing else does.

- **Capability:** `{tools, rules, prompt, spawn?, mcp?, brokered?}` (`mcp`: [mcp capabilities](../../../agents/capabilities/mcp/); `brokered`: [brokered actions](../../../agents/capabilities/brokered/), copied into the spec at spawn like `mcp`): platform tools from the registry (`platform-tools.json`), the runner's permission rules they need (the per-tool rules grants will replace), and a prompt section. `spawn` names the templates its `agent_spawn` may spawn from (the spawn grant; the spec's `spawn` is the union, and it isn't checked against existing templates, which may come later). A row stored without `spawn` has none; a stored `params` or `grants` is ignored.
- **Template:** `{capabilities, launch, hands: required | forbidden | optional, credential, repos?, read_repos?, ephemeral?, sandbox_idle_ttl_ms?, share_sandbox?}`. `repos` is its agents' push allowlist, `read_repos` the repos they may only read ([read-only repos](../../../sandbox/networking/egress/policy/#read-only-repos)). The last three are [lifetimes](../../../agents/#lifetimes): its agents end themselves when done; the idle TTL of a sandbox `agent_spawn` makes for them (absent: the cell default); a spawner may attach one to its own sandbox (`sandbox: share`). `credential` names a Claude setup token in [BrokerDO](../broker/) (`claude_oauth_token` or `claude_oauth_token:<name>`, nothing else: its value goes to a brain host).
- **Seeded once** with the current seed: templates `worker` (hands required; Claude Code's task and web tools only, `TaskCreate`, `TaskGet`, `TaskUpdate`, `TaskList`, `WebSearch`, `WebFetch`, no `TodoWrite` or `Agent`: [runner](../../../agents/runner/)) and `captain` (no hands; `management`, `spawning`, `memory`). Seed version 1 (`SEED_CATALOG_V1`, frozen) is what catalogs seeded first hold; it differs where the design moved on (`worker` with `subagents` and other built-ins, `captain` without `spawning`, `management` with tools the registry lacks, and the capabilities later steps remove). A catalog seeded earlier keeps its entries until I edit them (`PUT` with the `GET /v1/admin/catalog` body changed). An entry I delete stays deleted.
- **Seed migration:** each later seed version (`SEED_STEPS` in `lib/spec.ts`, pure: `seedMigration`; versions strictly increase, each release appends the next) runs once on a catalog seeded earlier (no `seed_version`: version 1), and the version reached (`kv.seed_version`) is recorded in the same synchronous step; a release rolled back to sees a version past its own and adds nothing, so it can't bring back what a later step removed.
  - **Adding** puts a new entry in only where the name is free, and never edits an entry: an entry I delete afterwards stays deleted, and an operator's entry of the same name stays theirs. Version 4 adds `egress` (`egress_policy`), version 5 `spawning` (`agent_spawn`, `agent_stop`; `spawn: [worker]`); neither goes into existing templates. Putting one there is my step (`PUT /v1/admin/templates/<name>` with the capability appended), not done in place because a template listing a capability whose tools the previous release lacks doesn't expand under it, so a forward revert would stop spawning from it. Versions 2 and 3 add nothing.
  - **Removing** does edit templates, because a template naming a capability that doesn't exist doesn't expand. A step deletes the named capabilities whoever wrote them, drops them from every template's list (keeping the others in order) with any template parameter only they read, and strips named tools and fields from every other capability, all on the raw row (`pruneTemplate`, `pruneCapability`), so fields this release doesn't know survive; a row that isn't JSON is left alone. Version 6 removes `tasks` and `tasks-admin` (and the `ledger` parameter); version 7 removes `channels` and `messaging-tree`, their tools and the `grants` field; version 8 removes `messaging` and `events`, their tools and the stubs in `management` that no handler served (`CHANNEL_*` and `MESSAGING_*` in `lib/spec.ts` name them). The previous release reads the pruned rows as ordinary ones.
  - **Prompts:** a step may replace a seed capability's prompt, only where the stored one is still that seed's text exactly (an edit of mine stays). Version 7 replaces `spawning`'s, which promised that a child's events reach its spawner.
  - **Compat (one release):** every template row written (a `PUT` or a fresh seed) also carries `escalate_to: user` and `subscribe: []`, which the release before workstreams left required (no default for `escalate_to`); no rollback reaches it now, so the writes are removable ([deploy](../../../../dev/deploy.md#rollout-rules)). This release strips both on read.
- **Checked on write:** a capability names only registry tools (on expansion a stored one naming a tool the registry lacks is read without it), a template only existing capabilities, each once; a capability a template lists can't be deleted, nor changed so that a template listing it no longer holds together (409). Routes: `GET /v1/admin/catalog`, `PUT|DELETE /v1/admin/capabilities/<name>`, `PUT|DELETE /v1/admin/templates/<name>`.
- **Client namespaces** ([API clients](../../api/clients/#the-clients-catalog)): an entry may be named `<client-name>/<entry>`, and templates and `spawn` lists may name such entries. A client sees the operator's entries and its own; everything written into its namespace, and every expansion in its subtree, is held to its grant (`ClientScope`: refused at write and at spawn, 403). Routes: `GET /v1/catalog`, `GET|PUT|DELETE /v1/catalog/{templates,capabilities}/<client-name>/<entry>`. A deleted client's namespace is deleted with it. The previous release's schema refuses a template or capability naming a `/` entry, so after a rollback it skips those rows (logged).
- **A launch's `model` and `effort` are plain tokens** (`LAUNCH_ARG`, `launchProblem` in `lib/spec.ts`). They become arguments of the brain's command (`--model <m>`, `--effort <e>`, [runner](../../../agents/runner/)), so each is letters, digits and `. _ : @ / [ ] -`, starting with a letter or digit (never `-`, which would read as an option), at most 100 characters.
  - **Checked where a launch is written and where it's used,** for every writer alike, in expansion (`expandTemplate`, `expandSpec`): a template put (the operator's or a client's), a spawn from a template, and the operator's `launch` on a spawn. Refused with `invalid_message` (400).
  - **An agent's stored launch is checked when a start is issued** (AgentDO's `processIntent`): one that fails starts no brain, and the agent is `errored` with why (`start_error`). A running brain isn't condemned for such a start: a restart or move of it is refused with the reason, and it keeps running.
  - **A stored template is still read as it is.** The wire schema (`LaunchConfig`) is unchanged. A template written before the rule still lists, and doesn't block a write of a capability it names; nothing spawns from it until it's written again.
- **Expansion is a pure function** (`lib/spec.ts`, unit- and property-tested): the template's hands rule against whether a sandbox is given; tools as the union of its capabilities' (in registry order), narrowed by `overrides.tools` and never widened; rules as the capabilities' in order, each once (or `overrides.rules`); the system prompt as the template's text followed by each capability's prompt (or `overrides.launch`); `credential` from the template unless overridden.
- **Two kinds of overrides.** `OperatorOverrides` (the admin API only: the operator holds the root) may replace the launch or the rules, narrow the tools, and pick the setup token. `SpawnerOverrides`, for any spawn an agent makes, can only narrow: a subset of the template's tools, and `deny` or `ask` rules placed before the template's (first match wins); anything else (launch, built-in tools, credential, an `allow` rule) is refused. Lifetimes only shorten: `ephemeral: true` may be added, never cleared, and `sandbox_idle_ttl_ms` is the shorter of the spawn's and the template's (the cell default when the template has none: the template is the operator's, and may give longer). `share` (the spawner's own sandbox) needs `share_sandbox`. The operator's overrides may also set `ephemeral` either way. The operator's `repos` and `read_repos` replace the template's; a spawner's narrow them (`read_repos` to the template's read-only repos or its allowlist: reading a repo it may push to is less). A spawner narrowing the allowlist to none drops the unscoped GitHub grants it scoped, rather than leaving them on any repo. The push allowlist narrows against the template's, not the spawner's: the spawn grant on the template is the operator's authorization for what it gives, as for tools. Narrowing against the spawner's own holdings waits for grants: tools aren't grants (a captain holds no hands tools, yet spawns workers), so checking a child's tools against its spawner's would forbid the seeded pattern.
- **AgentDO stores the expanded spec** at spawn, so editing a template changes only later spawns. `template` is shown and labels the agent's inbox posts (`<template>:<agent>`); nothing decides on it.
- **Storage:** a row that doesn't parse (a later release's shape, a hand edit) is logged and skipped, so it can't stop spawning from the other templates. The tables are bounded by what I write ([data](../../../data/#retention)).
- **Deploying it is one-way:** a new Durable Object class means `wrangler rollback` can't cross the release that adds it ([deploy](../../../../dev/deploy.md)).

**Not built:** the `api` source, capability parameters (`spawning{budget}`), grants beyond the spawn list, and their attenuation against a spawner's, backend, budget, priority and labels in a template.
