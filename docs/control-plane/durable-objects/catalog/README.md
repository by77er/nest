# CatalogDO

One instance (`catalog`): the [templates and capabilities](../../../agents/capabilities/) I edit, stored as data. Spawning reads it; nothing else does.

- **Capability:** `{tools, rules, prompt, params}`: platform tools from the registry (`platform-tools.json`), the runner's permission rules they need (the per-tool rules grants will replace), a prompt section, and the spawn parameters its tools read (only `ledger` exists: the [task ledger](../tasks/) of `tasks` and `tasks-admin`).
- **Template:** `{capabilities, launch, hands: required | forbidden | optional, credential, escalate_to, subscribe}`. `credential` names a Claude setup token in [BrokerDO](../broker/) (`claude_oauth_token` or `claude_oauth_token:<name>`, nothing else: its value goes to a brain host). `subscribe: [workstream]` makes the new agent its workstream channel's subscriber. `params` gives parameter defaults (e.g. `{ledger: <name>}`).
- **Seeded once** with the current seed, and migrated once per later seed version. Seed version 1 (`SEED_CATALOG_V1`, frozen) is `worker` and `captain` as the roles were: the same tools, launch, rules and setup token. Version 2 adds the capabilities `tasks` and `tasks-admin`, and in a new catalog `worker` lists `tasks` and `captain` both. An entry I delete stays deleted.
- **Seed migration (`seed_version` in `kv`; none means 1):** a catalog seeded by an earlier version gains each later version's new entries whose names are free, once, and records the version it reached, so an entry deleted afterwards stays deleted and an operator's entry of the same name stays theirs. It never edits an existing entry: adding `tasks` to an existing `worker` or `captain` is my step (below). Why not edit unedited templates in place: a template listing `tasks` doesn't expand under the previous release (its registry lacks the `task_*` tools), so a forward revert would stop spawning from `worker` and `captain`; and the tools do nothing without a `ledger` param, which only a spawn gives.
- **My step after the release that adds the ledger:** `PUT /v1/admin/templates/worker` and `/captain` with `tasks` (and `tasks-admin` for `captain`) appended to `capabilities` (`GET /v1/admin/catalog` gives the bodies), then spawn with `overrides.params.ledger`.
- **Checked on write:** a capability names only registry tools, a template only existing capabilities, each once, and parameter defaults only those capabilities take; a capability a template lists can't be deleted, nor changed so that a template listing it no longer holds together (409). Routes: `GET /v1/admin/catalog`, `PUT|DELETE /v1/admin/capabilities/<name>`, `PUT|DELETE /v1/admin/templates/<name>`.
- **Expansion is a pure function** (`lib/spec.ts`, unit- and property-tested): the template's hands rule against whether a sandbox is given; tools as the union of its capabilities' (in registry order), narrowed by `overrides.tools` and never widened; rules as the capabilities' in order, each once (or `overrides.rules`); the system prompt as the template's text followed by each capability's prompt (or `overrides.launch`); `credential` and `escalate_to` from the template unless overridden; `params` as the template's, each replaced by `overrides.params`, and every one must be declared by one of the template's capabilities.
- **Two kinds of overrides.** `OperatorOverrides` (the admin API only: the operator holds the root) may replace the launch or the rules, narrow the tools, pick the escalation and the setup token, and give capability parameters. `SpawnerOverrides`, for any spawn an agent makes, can only narrow: a subset of the template's tools, and `deny` or `ask` rules placed before the template's (first match wins); anything else (launch, built-in tools, credential, escalation, capability parameters, an `allow` rule) is refused. A spawner's child also gets no parameters from the template's defaults (its spec's `params` is empty), so it never reaches a ledger through a template that names one; it gets `tasks-admin` only from a template that lists it, never by override. Narrowing against the spawner's own holdings waits for grants: tools aren't grants (a captain holds no hands tools, yet spawns workers), so checking a child's tools against its spawner's would forbid the seeded pattern.
- **AgentDO stores the expanded spec** at spawn, so editing a template changes only later spawns. `template` is shown and labels the agent's inbox posts (`<template>:<agent>`); nothing decides on it.
- **Storage:** a row that doesn't parse (a later release's shape, a hand edit) is logged and skipped, so it can't stop spawning from the other templates. The tables are bounded by what I write ([data](../../../data/#retention)).
- **Deploying it is one-way:** a new Durable Object class means `wrangler rollback` can't cross the release that adds it ([deploy](../../../../dev/deploy.md)). For one release AgentDO and WorkstreamDO also write the previous release's fields (`role`, `grants`, `captain`), derived from the new ones, so a forward revert (the previous release's code deployed again) still reads every record.
- **Escalation, until channels exist:** `escalate_to` is `workstream` (a question becomes a `needs_input` event on the [workstream channel](../../../orchestration/workstreams/#the-interim-workstream-channel), which wakes its subscriber) or `user` (the user-notification queue). The design's default, the spawner's inbox, waits for `agent_spawn`.

**Not built:** `mcp` and `api` sources, capability parameters other than `ledger` (`messaging{peers}`, `spawning{budget}`, several ledgers), grants and their attenuation against a spawner's (no agent spawns yet), backend, budget, priority and labels in a template.
