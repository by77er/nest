# ClientDO

One instance per [API client](../../api/clients/), named by its id (`cli_…`), one more, `directory`, for the names, and one more, `operator`, for the operator's idempotency keys.

- **The record:** name, grant, the token's hash (SHA-256 of `nest-client-token/<token>`; the token itself is shown once, at create and rotate), created and rotated times. The Worker hashes a bearer token and ClientDO compares the hash in constant time. A deleted or unknown client answers 401.
- **The directory:** name → id, unique, with the client's phase, and the list of clients. The row decides where a client stands; its record follows it.
- **Names** (decided 2026-11-06, `control-plane/src/lib/client-names.ts`, pure, each decision applied in one synchronous step): a client's phase is one of `reserved`, `live`, `deleted` (a tombstone) or `purged` (no row: the name is free). A row from before phases is `live`.
  - **Create** (`POST /v1/admin/clients`): `reserveName` (409 when taken, saying when a deleted client's name frees), then the record, then `confirmName` (reserved → live), and only then is the token handed out. Confirm is idempotent, so an answer lost on the way is asked for again (up to 3 tries) and a confirmed name answers the same. A create whose record write fails gives the reservation back at once (`abandonName`).
  - **A dead create:** a reservation not confirmed within `RESERVE_TTL_MS` (2 min) is stale, because its token never went out. A new create of the name takes it over, or the sweep drops it.
  - **An orphan record purges itself:** at its hourly prune, a record the directory doesn't hold under its name (`phaseOf` answers `purged`) and older than 2 min, with nothing of its subtree live or reserved, deletes its storage and alarm (one with any keeps it). That covers a create that died before confirming, and a delete of the previous release that stopped after releasing the name. A deleted record's prune doesn't re-arm: it waits for its purge.
  - **Delete:** the name becomes a tombstone for `TOMBSTONE_MS` (15 min), and no client can take it meanwhile. Then the directory's `sweep` alarm deletes the client's catalog namespace, its secrets and its record once more, and frees the name. So a catalog or secret write by a request that authenticated before the delete and landed after it is removed, and no later client of the name inherits it. A tombstone owns no namespace (`lookup` answers only live names).
  - **Compat, for one release:** `claimName` (reserve and confirm at once) and `releaseName` (a tombstone) serve a Worker of the previous release mid-deploy.
- **The subtree's registry** (`members`): each agent and sandbox in the client's subtree, with its cell, owner, labels and state (`reserved`, `live`, `ended`). It is what `max_agents` and `max_sandboxes` count and what the client lists (`GET /v1/agents`, `GET /v1/sandboxes`, and the agents whose open asks `GET /v1/asks` reads). It's an index: the records (AgentDO's `client`, SandboxDO's `client`) decide.
- **Counting:**
  - A create (`POST /v1/agents`, `POST /v1/sandboxes`, `agent_spawn` and the sandbox it makes) first calls `admit`. That checks the cell against the grant and the count against the maximum, and inserts the row as `reserved`, all in one synchronous step, so parallel creates can't pass the maximum.
  - A retry with the same id finds its row. A create that fails for good gives its place back (`release`).
  - The object then reports itself from its own alarm, retried until ClientDO answers: AgentDO from its `registry` deadline (live, then ended once its end is done), and SandboxDO from its `client` deadline (live, then destroyed, armed in the destroy decision's step). Ended is final.
  - A report for a row that isn't there (the reconcile dropped it) inserts the row, so the count never misses an object that exists.
  - **Every state change goes through one pure step** (`memberStep`, `control-plane/src/lib/members.ts`: state and event in, the next state, no row, or `refuse` out; 2026-11-09), applied to the row as it is in that step (`ClientDO.move`), so nothing acts on what it saw before an await. `ended` is final (a late live report or check never retakes a place); only a reservation is released; a check never creates a row; and a reservation that became live while the reconcile asked about it is left to the hourly recheck. The recheck re-reads the same way: it judges only a row that is still live after its question.
  - **A purged client keeps no registry:** a report retried after the purge is answered and records nothing, so no row is left in an empty object that no alarm would remove.
- **Reconcile:** a row still `reserved` `RESERVE_CHECK_MS` (10 min) after `admit` is checked against its object. One that was never created goes; one that exists is counted as it stands. A failure to ask counts as live.
- **Recheck:** the hourly prune reads up to 100 live rows against their objects, least recently checked first, so an end or destroy whose report never came (a rollback ran meanwhile) frees its place.
- **Retention:** ended rows 7 days (hourly prune). The record lives until the client is deleted.
- **Delete:** `markDeleted` is refused (409) while any row is reserved or live. Otherwise no token works and nothing more is admitted. The Worker then makes the name a tombstone, deletes the catalog namespace and the secrets, and `purge` empties the object. It's idempotent: a delete whose record is already purged finds the name by id in the directory (`nameOf`) and finishes, so a name whose create lost its answer can always be deleted.
- **Events** ([events to the owner](../../api/clients/#events-to-the-owner)):
  - `kv` holds the webhook (`{url, secret, set_ms}`) and delivery's state (`{failures, dropped, last_error, failed_ms}`), so the retry schedule survives a restart.
  - `outbox` is the backlog, in arrival order, with the event's `id` unique: `enqueue` (an agent's or sandbox's hand-off) inserts in one synchronous step and never waits on a delivery, so a hand-off retried after a lost answer is stored once. Past 10,000 rows the oldest go, counted in `dropped`. Without a webhook nothing is kept.
  - The `deliver` deadline sends the oldest event, one request at a time, deleting it on a 2xx, up to 100 a run. The first failure (another status, a network error, or no answer within 10 s, `AbortSignal`) stops the run and arms the next one `1 s · 2^(failures-1)` later, at most 5 min; an `enqueue` doesn't advance a deadline that is waiting out its backoff.
  - The hourly prune arms `deliver` again for a backlog with no deadline (a rolled-back release has no handler for it).
  - **An event waits at most 7 days** (`EVENT_MAX_AGE_MS`, `outbox.queued_ms`): the hourly prune drops older ones and counts them in `dropped`, so none waits for ever on a receiver that never answers. A row from before the column takes, at the first prune that sees it, the earliest time among the rows queued after it (else that prune's time), so queue order stays age order. The backlog cap's drop never takes the event an attempt is out for (`delivering`), so none is counted dropped and then delivered; this age drop runs from the alarm, between attempts.
  - **The delivery state changes through one pure step** (`deliveryStep`, `control-plane/src/lib/client-events.ts`; 2026-11-09): the state (`failures`, `dropped`, the last error) and an event (`delivered`, `failed`, `webhook_set`, `dropped`) in; the next state and when the next attempt is due out. A success or a new webhook clears the failures; a failure counts one more and waits from that count; dropping events changes no schedule; `dropped` is only ever added to.
- **Idempotency keys** ([decisions](../../api/#idempotency-keys), `control-plane/src/lib/idempotency.ts`): `idempotency_keys`, one row per key of this principal (a client in its own instance, the operator in `operator`, which holds nothing else and has no alarm): the request's digest, the id it was given, `pending` or `done`, the answer's status, and the claim holding it with when. `claimKey`, `finishKey` and `abandonKey` are each one synchronous step, so two requests with one key can't both claim it fresh. Rows go 24 h after their first use, at the next claim (100 at a time) and in a client's hourly prune.
- **Deploying it was one-way:** a new class ([deploy](../../../../dev/deploy.md)).
