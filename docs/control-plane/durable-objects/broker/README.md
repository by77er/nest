# BrokerDO

The only DO that stores secret values. Platform keys live elsewhere: the proxy root CA key in AWS KMS, and AWS credentials, the host-token secret and the operator-token hashes as Worker secrets. See [../../../security/credentials/](../../../security/credentials/).

- **References, not values:** other DOs ask BrokerDO for a reference (`$nest-secret:<name>`) and pass that around. FleetDO resolves references when it sends a command to a host. Missing or expired secrets are logged; in `agent_start` they resolve to empty, and in `secrets_update` the entry is left out (2026-11-02), so nest-proxy refuses the binding's placeholder instead of substituting an empty credential.
- **Resolution is scoped by purpose:** FleetDO resolves only two slots, `agent_start.oauth_token` (names `claude_oauth_token` and `claude_oauth_token:*`) and `secrets_update.secrets[].value` (`inject:*` and API clients' `client-secret:*`), and `resolveRefs` takes that allowlist. A reference anywhere else in a command, such as a launch prompt, goes out as literal text. `binding_key:*`, `access:*`, `cap:*`, `hook:*`, `http:*`, `github_app` and `github_user` are never resolvable into a command, whatever the caller asks.
- **Claude setup tokens:** `claude_oauth_token`, plus named ones (`claude_oauth_token:<name>`, e.g. `:captain`) that a spawn spec's `credential` picks. A credential naming any other secret is refused. They end up only in the Claude Code process environment on a brain host, never on a sandbox host. **Which one a start names never crosses authority** (decided 2026-11-06, `credentialFor` in `control-plane/src/lib/credentials.ts`, called by `credentialRef`):
  - **The operator's agents:** the named token if stored and unexpired, else `claude_oauth_token`. The operator holds every credential, so falling back stays within its authority.
  - **An [API client](../../api/clients/)'s agents:** exactly the named token, only while the client's grant (read at each start, not at spawn) names it and an unexpired value is stored. Never the default or another token, whatever the grant also names: a fallback would run the client's agent on a credential it never chose, maybe the operator's own subscription. Otherwise the start is refused (409): the agent is `errored` with `start_error` on its record, and its client is sent `agent.error` (`start_refused`) naming the credential. AgentDO also refuses any reference but the spec's own for a client's agent, so a BrokerDO of the previous release (which ignores the client and falls back) can't either.
- **Deleting a secret** (built 2026-11-09): `DELETE /v1/admin/secrets/<name>` (admin token) removes the row, value and all; before it, a secret could only be overwritten. What named it resolves to nothing from then on. Deleting `github_app` also drops every cached installation token. BrokerDO refuses its own keys (`binding_key:*`) and API clients' secrets (`client-secret:*`: theirs to delete). Audited as `secret_deleted`, by name, never a value. **Nothing is revoked upstream:** deleting `github_app` or an `inject:*` secret only stops nest using it. Installation tokens GitHub already issued live out their hour, and the App's key or the injected credential stays valid at its provider until it's rotated there. An mcp capability's OAuth tokens aren't in `secrets`: they're revoked with [their own route](../../../agents/capabilities/mcp/#oauth).
- **Injected secrets:** static ones the operator stores, `inject:<binding>:<sandbox>` or `inject:<binding>` (`inject:<binding>:<workstream>`, with the sandbox's compat `workstream` value, is still read: secrets stored under it before the sandbox key may exist, and nothing new is keyed by it), and minted ones ([below](#injection-minting)), sent to nest-proxy for placeholder substitution. Putting a binding in a sandbox's policy needs a grant on it. They're pushed with the policy version they were resolved for; nest-proxy checks them against the epoch only (a policy acknowledgement with a content hash is designed, not built: [injection](../../../sandbox/networking/egress/injection/)).
- **Serving a secret is checked twice.** Before fetching or minting a value for a push, BrokerDO reads the target's state: the sandbox's epoch, its policy version and sha256, and the binding's grant. It reads the same state again once the value is in hand, and **discards the value if anything changed**, so a revocation, fence or policy edit that lands during a slow GitHub call never ships a credential. SPACE does the same ([credential_injection_authority.rs](https://github.com/perplexityai/space/blob/main/crates/libs/credential/mgr/server/src/credential_injection_authority.rs)).
- **Capability credentials:** `cap:<capability>` holds the bearer token or OAuth tokens for an `mcp` or `api` [capability](../../../agents/capabilities/#sources), and `cap:metrics` the Analytics Engine read token. The control plane uses them for each call; they never reach a host or a sandbox. **Built for `mcp`:** a bearer token stored with `PUT /v1/admin/secrets/cap:<name>`, read only by AgentDO's MCP client through `capabilityToken` ([mcp capabilities](../../../agents/capabilities/mcp/)); `cap:` stays in the never-resolved list, so no host command can carry one. **OAuth** ([mcp OAuth](../../../agents/capabilities/mcp/#oauth)) keeps its tokens in its own tables (`oauth_grants`, `oauth_flows`, `oauth_clients`), never in `secrets`, so `capabilityToken` and `resolveRefs` can't return one. AgentDO gets an access token through `mcpOAuthToken`, which refreshes as needed, one refresh at a time per record. The refresh token, the PKCE verifier and any client secret never leave BrokerDO. A pre-registered client's JSON is an ordinary `cap:` secret, read at each token request.
- **GitHub App:** holds the App's private key and mints installation tokens per binding: a JWT signed with the key, then an access-token request narrowed to the binding's repos and permissions. Tokens last an hour and are cached for 50 minutes. A binding is one use, such as a worker's sandbox injection (push and open PRs) or a reviewer's brokered actions (post a check), so each token carries only what that use needs. **Built for brokered actions** (`githubToken`, [brokered](../../../agents/capabilities/brokered/)): the App's credentials are one secret, `github_app` = `{"app_id", "private_key"}` (the PEM GitHub hands out, PKCS#1, or PKCS#8), checked when stored. A token is minted for one repo (looked up with `GET /repos/{owner}/{repo}/installation`, cached a day per App and repo) and the action's permissions, reused while it has 10 minutes left (`github_tokens`, keyed by the App's `app_id` too, so a replaced `github_app` never hands out the old App's tokens), and handed only to AgentDO for that call. **A stale installation** (decided 2026-11-06, `lib/github.ts`): a status alone never says so, since GitHub answers 422 for an ordinary refusal too (permissions the installation wasn't granted). A mint with a cached installation refused 401, 404 or 422 (`retryMintFresh`) looks each repo it covered up afresh (`installationVerdict`). Only if one now has another installation or none (the App uninstalled and installed again, a repo moved) is it stale: the cache takes the fresh ids, every token minted from the old installation goes, and the mint is tried once more. Still the same installation: the refusal is real and stands, the cache and every cached token stay, and nothing is minted again, so one client's refusal never costs another its token. A refusal of a freshly looked-up installation is final. The same holds for a sandbox's injection mint, whose held token is also keyed by the App, so the next push after a `github_app` swap mints under the new App. Expired tokens go at every mint. The JWT is RS256 with `iat` 60 s back and `exp` 9 minutes on ([GitHub](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app); [token](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app)). `GITHUB_API_URL` points it at a fake (a loopback one only with `ALLOW_LOOPBACK_BROKERED=1`). **Built for API clients** (`clientGithubToken`, [GitHub tokens](../../api/clients/#github-tokens)): the same mint for one repo and exactly the repository permissions a client asked for, after the Worker has held the request to its grant. BrokerDO checks the shape again (a `cli_` client, at least one permission, each from `GITHUB_REPO_PERMISSIONS`), so no caller gets a token for every permission. Its tokens are cached per App and client (`github_tokens` keys `app:<app_id>|client:<id>|…`) and leave nest, to the client. Minting for sandbox injection: [below](#injection-minting). **The App's identity** (`githubApp`, built 2026-11-02): its numeric id and slug, from `GET /app` with the App's JWT ([GitHub](https://docs.github.com/en/rest/apps/apps#get-the-authenticated-app)), kept a day per configured `app_id` (`github_app_identity` table), one lookup at a time, for API clients to pin a required check to the App. When GitHub doesn't answer (5 s): what it said before, else the configured `app_id` if it is the numeric id (GitHub also takes the client id as the JWT's issuer), each kept 10 minutes; else nothing, and no lookup for 10 minutes. Not secret.
- **API clients' secrets** ([secrets](../../api/clients/#secrets), built 2026-11-02): each value in `secrets` as `client-secret:<cli>:<name>`, what anyone may see of it in `client_secrets` (description, size, created, updated, last injected), never a value out. `putClientSecret` checks the grant's `secrets` (count and size) and writes in one step; `deleteClientSecret`, `clientSecrets` (metadata), and `deleteClientSecrets` at a client's delete. `clientInjectionRefs(client, sandbox, bindings)` answers references only under that client's id, for the secrets it has, audits the push (`client_secret_injected`) before answering, and marks `last_injected_ms`. The admin secrets route refuses the prefix.
- **The operator's GitHub user token** (`github_user`), read only by AgentDO's `github.fork` (`githubUserToken`): the App can't fork from an account it isn't installed on ([forks](../../../agents/capabilities/brokered/#forks)). Never resolvable into a host command.
- **Brokered-action credentials:** `http:<name>`, an http profile's secret, read only by AgentDO's brokered pipeline (`brokeredSecret`). `scanSecrets(strings)` answers which stored secrets' values (raw, base64, long strings inside a JSON value, a PEM's body lines; 8 characters at least) appear in a brokered call's arguments: names only, so no value leaves BrokerDO.
- **The binding signing key** (`binding_key:<cell>`): an ECDSA P-256 private key per cell, generated on first use and stored as a JWK that rests nowhere else. BrokerDO signs every binding (`signBinding`) and hands FleetDO only the public keys (`bindingPublicKeys`); the admin secrets route refuses the `binding_key:` prefix, so the key can't be replaced from outside ([gateway](../../../interfaces/gateway/)). Rotation (a second listed key) isn't built.
- **Caller identity keys** ([below](#caller-identity-keys)): the Ed25519 keys that sign `Nest-Identity`.
- **The Access service token** (`access:gateway`) that fronts the sandbox hosts' tunnel hostnames: stored by me through the admin secrets route as JSON `{"client_id", "client_secret"}`, read by SandboxDO's `resolve` into the `edge` of every target that points at a host's tunnel, so a runner holds it only inside a target in memory. Never a sandbox ([gateway](../../../sandbox/gateway/)). Not built: a `nest` login that hands it to the CLI for terminals.
- **The api-loop API key** (deferred), used only inside the control plane.

The Cloudflare API token that creates and deletes per-host tunnels and DNS records is a Worker secret, like the other platform keys, not a BrokerDO secret.

## Caller identity keys

**Built (2026-11-02)** for [caller identity](../../api/clients/#caller-identity-for-mcp-servers) (`signIdentity`, `identityJwks`; `src/lib/identity.ts`):

- **Algorithm: Ed25519 (EdDSA).** Workers' WebCrypto supports `Ed25519` for `sign`, `verify`, `generateKey`, `importKey` and `exportKey` ([Cloudflare](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), as the Secure Curves API names it), so no ES256 fallback is needed.
- **Storage:** `identity_keys`, one row per key: `kid` (RFC 7638 thumbprint), the private and public JWK, `signs_from_ms`. The private JWK never leaves BrokerDO; the admin secrets route can't reach the table.
- **Schedule** (`keyPlan`, pure): the signer is the newest key whose `signs_from_ms` has come. A key signs 30 days. The next key is made a day before that and signs only after it has been published a day; if nothing signed or read the JWKS that day, it is made at the next use and the current key signs on until it has been published a day. A retired key stays published a day after the next one took over (a token lives 5 minutes, the JWKS is cacheable 5), then its row is deleted. The first key signs at once (no token can exist yet).
- **No alarm:** every sign and JWKS read applies the schedule. A key generated across an await is inserted only if the re-read schedule still wants one, so concurrent first uses make one key.
- **Signing:** the caller passes the subject (`aud`, `sub` and the optional claims, a strict schema); BrokerDO adds `iss` (`PUBLIC_BASE_URL`), `iat` and `exp` (5 minutes), so lifetime and issuer are decided here only.

## Injection minting

**Built for the GitHub App** (`injectionSecret(target, source, caller)`, generic in its shape: a target `{sandbox, epoch}` and a source, today only `{kind: github_app, binding, repos}`):

- **What:** an installation token for exactly the sandbox's [push allowlist](../../../sandbox/networking/egress/policy/#repo-allowlists), with `contents: write` and `pull_requests: write` (`SANDBOX_TOKEN_PERMISSIONS` in `lib/github.ts`), stored as the secret `inject:github:<sandbox>` with its expiry; the push carries the reference, which FleetDO resolves when it sends `secrets_update`, fenced by the sandbox's epoch as every secret push is.
- **Read-only repos** (built 2026-11-02, `readInjectionSecret`): the same mint for exactly the sandbox's [read-only repos](../../../sandbox/networking/egress/policy/#read-only-repos), with `contents: read` and `metadata: read` (`SANDBOX_READ_TOKEN_PERMISSIONS`), stored as `inject:github_read:<sandbox>`; SandboxDO pushes its reference under `github_read`, and under `github_read_default` too when the sandbox has no push allowlist; when the read-only repos empty it asks again with none, which deletes it. A method of its own rather than a field of the source: a BrokerDO of the previous release would ignore such a field and mint a push token, where a method it lacks is refused (and retried in 2 minutes). Its reuse key names its access, so a push token and a read-only one never stand in for each other.
- **`workflows: write`** (built 2026-11-02, [workflow files](../../api/clients/#workflow-files)): a push token's source may say `workflows: true`; the token then has exactly `{contents: write, pull_requests: write, workflows: write}`, and its reuse key names it, so a token with it and one without never stand in for each other. A read-only token never has it. A BrokerDO of the previous release ignores the field and mints without it: narrower.
- **Reused** while it has 20 minutes left and the same repos (`injections` table); SandboxDO pushes again 15 minutes before expiry (its `inject_refresh` deadline), so a refresh always mints. A GitHub that didn't answer is tried again in 2 minutes; nothing mintable, in an hour or at the next policy change.
- **One installation per token** (GitHub's token request names repos of one installation): repos spread over several get the installation holding most of them; the others, and repos the App isn't installed on, are refused and audited, and the [guards](../../../sandbox/networking/egress/policy/#github) still let pushes to them through (GitHub refuses them without a credential).
- **Nothing mintable** (no App, none of the repos installed, an allowlist emptied): the sandbox's earlier token is deleted, so a narrowed allowlist never keeps a wider token. The binding stays in the policy, so a request with the placeholder gets `injection_unavailable`. A destroyed sandbox's tokens are deleted (`forgetInjections`); expired ones are pruned at the next mint.
- **Checked twice (built for this path):** SandboxDO reads the sandbox's epoch, host and allowlist before asking and again when the answer is in hand, and drops the push if any changed; BrokerDO stores nothing for a request a newer one for the same sandbox overtook while GitHub answered, so a slow, stale mint can't replace the value a newer push's reference resolves to. The general double check (the policy hash and the binding's grant) waits for the policy acknowledgement.
- **Audited** like the brokered mints, before the value is stored: `event: github_installation_token`, `repos`, `permissions`, `installation`, `expires_ms`, `target: {sandbox, epoch}`, `binding`, `caller: SandboxDO`, or `refused` with the reason.

**Built:** secret storage and references, purpose-scoped resolution, setup tokens, injected secrets (keyed by sandbox), the binding signing key, the caller identity keys, the Access service token, MCP OAuth, GitHub App minting for brokered actions, sandbox injection and API clients, the operator's GitHub user token, http profile credentials, the argument scan, and the issuance audit of MCP OAuth and GitHub mints. **Not built:** the general double check when serving a secret, and the audit of static secret pushes and binding mints.

## Issuance audit

Every installation-token mint, every secret push to a host and every refusal is written to R2 with the audit log. A record holds the binding, repos, permissions, expiry, the target `(sandbox, epoch)`, the caller (the DO or principal that asked) and, for a refusal, the reason. **Never a value.** Binding mints (`signBinding`, including ones through the operator route) are audited the same way. **Built for MCP OAuth:** each flow start, registration, authorization, refused callback, refresh, failed refresh and refused token hand-out is one JSON object under `audit/broker/<day>/<ms>-<id>.json`, with the capability, record, resource, issuer, client id, scope, expiry, caller and reason. It is written in the background, so a failed write is logged and doesn't fail what it records. **Built for GitHub mints:** one record per mint or refusal under the same prefix (`event: github_installation_token`, `repos`, `permissions`, `installation`, `expires_ms`, the caller's agent and call key, an API client's `caller: {client}`, or, for a sandbox's token, its `target` and `binding`, or `refused`). Unlike OAuth's, it is awaited before the token is handed out, so a mint whose record can't be written is never used. A reused cached token isn't a mint. Nothing else is audited yet.
