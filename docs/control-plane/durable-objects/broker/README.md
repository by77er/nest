# BrokerDO

The only DO that stores secret values. Platform keys live elsewhere: the proxy root CA key in AWS KMS, and AWS credentials, the host-token secret and the operator-token hashes as Worker secrets. See [../../../security/credentials/](../../../security/credentials/).

- **References, not values:** other DOs ask BrokerDO for a reference (`$nest-secret:<name>`) and pass that around. FleetDO resolves references when it sends a command to a host. Missing or expired secrets resolve to empty and are logged.
- **Resolution is scoped by purpose:** FleetDO resolves only two slots, `agent_start.oauth_token` (names `claude_oauth_token` and `claude_oauth_token:*`) and `secrets_update.secrets[].value` (`inject:*`), and `resolveRefs` takes that allowlist. A reference anywhere else in a command, such as a launch prompt, goes out as literal text. `binding_key:*`, `access:*`, `cap:*`, `hook:*`, `http:*` and `github_app` are never resolvable into a command, whatever the caller asks.
- **Claude setup tokens:** `claude_oauth_token`, plus named ones (`claude_oauth_token:<name>`, e.g. `:captain`) that a spawn spec's `credential` picks; a named one not configured falls back to `claude_oauth_token`. A credential naming any other secret is refused. They end up only in the Claude Code process environment on a brain host, never on a sandbox host.
- **Injected secrets:** `inject:<binding>`, sent to nest-proxy for placeholder substitution. Putting a binding in a sandbox's policy needs a grant on it. They're pushed with the policy version they were resolved for; nest-proxy checks them against the epoch only (a policy acknowledgement with a content hash is designed, not built: [injection](../../../sandbox/networking/egress/injection/)).
- **Serving a secret is checked twice.** Before fetching or minting a value for a push, BrokerDO reads the target's state: the sandbox's epoch, its policy version and sha256, and the binding's grant. It reads the same state again once the value is in hand, and **discards the value if anything changed**, so a revocation, fence or policy edit that lands during a slow GitHub call never ships a credential. SPACE does the same ([credential_injection_authority.rs](https://github.com/perplexityai/space/blob/main/crates/libs/credential/mgr/server/src/credential_injection_authority.rs)).
- **Hook secrets:** `hook:<hk_…>` for each [webhook](../../../channels/sources/). BrokerDO verifies signatures itself (`verify(ref, scheme, headers, body)`), so the secret is never returned to anyone after it's created; brokered actions such as `github.create_webhook` send it straight to the provider.
- **Capability credentials:** `cap:<capability>` holds the bearer token or OAuth tokens for an `mcp` or `api` [capability](../../../agents/capabilities/#sources), and `cap:metrics` the Analytics Engine read token. The control plane uses them for each call; they never reach a host or a sandbox. **Built for `mcp`:** a bearer token stored with `PUT /v1/admin/secrets/cap:<name>`, read only by AgentDO's MCP client through `capabilityToken` ([mcp capabilities](../../../agents/capabilities/mcp/)); `cap:` stays in the never-resolved list, so no host command can carry one. **OAuth** ([mcp OAuth](../../../agents/capabilities/mcp/#oauth)) keeps its tokens in its own tables (`oauth_grants`, `oauth_flows`, `oauth_clients`), never in `secrets`, so `capabilityToken` and `resolveRefs` can't return one. AgentDO gets an access token through `mcpOAuthToken`, which refreshes as needed, one refresh at a time per record. The refresh token, the PKCE verifier and any client secret never leave BrokerDO. A pre-registered client's JSON is an ordinary `cap:` secret, read at each token request.
- **GitHub App:** holds the App's private key and mints installation tokens per binding: a JWT signed with the key, then an access-token request narrowed to the binding's repos and permissions. Tokens last an hour and are cached for 50 minutes. A binding is one use, such as a worker's sandbox injection (push and open PRs) or a reviewer's brokered actions (post a check), so each token carries only what that use needs. **Built for brokered actions** (`githubToken`, [brokered](../../../agents/capabilities/brokered/)): the App's credentials are one secret, `github_app` = `{"app_id", "private_key"}` (the PEM GitHub hands out, PKCS#1, or PKCS#8), checked when stored. A token is minted for one repo (looked up with `GET /repos/{owner}/{repo}/installation`, cached a day) and the action's permissions, reused while it has 10 minutes left (`github_tokens`), and handed only to AgentDO for that call. The JWT is RS256 with `iat` 60 s back and `exp` 9 minutes on ([GitHub](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app); [token](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app)). `GITHUB_API_URL` points it at a fake (a loopback one only with `ALLOW_LOOPBACK_BROKERED=1`). Not built: minting for sandbox injection.
- **Brokered-action credentials:** `http:<name>`, an http profile's secret, read only by AgentDO's brokered pipeline (`brokeredSecret`). `scanSecrets(strings)` answers which stored secrets' values (raw, base64, long strings inside a JSON value, a PEM's body lines; 8 characters at least) appear in a brokered call's arguments: names only, so no value leaves BrokerDO.
- **The binding signing key** (`binding_key:<cell>`): an ECDSA P-256 private key per cell, generated on first use and stored as a JWK that rests nowhere else. BrokerDO signs every binding (`signBinding`) and hands FleetDO only the public keys (`bindingPublicKeys`); the admin secrets route refuses the `binding_key:` prefix, so the key can't be replaced from outside ([gateway](../../../interfaces/gateway/)). Rotation (a second listed key) isn't built.
- **The Access service token** (`access:gateway`) that fronts the sandbox hosts' tunnel hostnames: stored by me through the admin secrets route as JSON `{"client_id", "client_secret"}`, read by SandboxDO's `resolve` into the `edge` of every target that points at a host's tunnel, so a runner holds it only inside a target in memory. Never a sandbox ([gateway](../../../sandbox/gateway/)). Not built: a `nest` login that hands it to the CLI for terminals.
- **The api-loop API key** (deferred), used only inside the control plane.

The Cloudflare API token that creates and deletes per-host tunnels and DNS records is a Worker secret, like the other platform keys, not a BrokerDO secret.

**Built:** secret storage and references, purpose-scoped resolution, setup tokens, injected secrets, the binding signing key, the Access service token, MCP OAuth, GitHub App minting for brokered actions, http profile credentials, the argument scan, and the issuance audit of MCP OAuth and GitHub mints. **Not built:** the double check when serving a secret, hook secrets and `verify`, minting for sandbox injection, and the audit of secret pushes and binding mints.

## Issuance audit

Every installation-token mint, every secret push to a host and every refusal is written to R2 with the audit log. A record holds the binding, repos, permissions, expiry, the target `(sandbox, epoch)`, the caller (the DO or principal that asked) and, for a refusal, the reason. **Never a value.** Binding mints (`signBinding`, including ones through the operator route) are audited the same way. **Built for MCP OAuth:** each flow start, registration, authorization, refused callback, refresh, failed refresh and refused token hand-out is one JSON object under `audit/broker/<day>/<ms>-<id>.json`, with the capability, record, resource, issuer, client id, scope, expiry, caller and reason. It is written in the background, so a failed write is logged and doesn't fail what it records. **Built for GitHub mints:** one record per mint or refusal under the same prefix (`event: github_installation_token`, `repos`, `permissions`, `installation`, `expires_ms`, the caller's agent and call key, or `refused`). Unlike OAuth's, it is awaited before the token is handed out, so a mint whose record can't be written is never used. A reused cached token isn't a mint. Nothing else is audited yet.
