# BrokerDO

The only DO that stores secret values, apart from each API client's webhook signing secret (in its [ClientDO](../client/)). Platform keys live elsewhere: the proxy root CA key in AWS KMS, and AWS credentials, the host-token secret and the operator-token hashes (not built; today one `ADMIN_TOKEN`) as Worker secrets. See [../../../security/credentials/](../../../security/credentials/).

- **References, not values:** other DOs ask BrokerDO for a reference (`$nest-secret:<name>`) and pass that around. FleetDO resolves references when it sends a command to a host. Missing or expired secrets are logged; in `agent_start` they resolve to empty, and in `secrets_update` the entry is left out (2026-11-02), so nest-proxy refuses the binding's placeholder instead of substituting an empty credential.
- **Resolution is scoped by purpose:** FleetDO resolves only two slots, `agent_start.oauth_token` (names `claude_oauth_token` and `claude_oauth_token:*`) and `secrets_update.secrets[].value` (`inject:*` and API clients' `client-secret:*`), and `resolveRefs` takes that allowlist. A reference anywhere else in a command, such as a launch prompt, goes out as literal text. `binding_key:*`, `access:*`, `cap:*`, `hook:*`, `http:*`, `github_app` and `github_user` are never resolvable into a command, whatever the caller asks (`github_app`, the GitHub App's key the kernel once minted with, and `github_user`, the operator's own GitHub token, have no reader; a stored value may remain until the operator deletes it).
- **Claude setup tokens:** `claude_oauth_token`, plus named ones (`claude_oauth_token:<name>`, e.g. `:captain`) that a spawn spec's `credential` picks. A credential naming any other secret is refused. They end up only in the Claude Code process environment on a brain host, never on a sandbox host. **Which one a start names never crosses authority** (decided 2026-11-06, `credentialFor` in `control-plane/src/lib/credentials.ts`, called by `credentialRef`):
  - **The operator's agents:** the named token if stored and unexpired, else `claude_oauth_token`. The operator holds every credential, so falling back stays within its authority.
  - **An [API client](../../api/clients/)'s agents:** exactly the named token, only while the client's grant (read at each start, not at spawn) names it and an unexpired value is stored. Never the default or another token, whatever the grant also names: a fallback would run the client's agent on a credential it never chose, maybe the operator's own subscription. Otherwise the start is refused (409): the agent is `errored` with `start_error` on its record, and its client is sent `agent.error` (`start_refused`) naming the credential. AgentDO also refuses any reference but the spec's own for a client's agent, so a BrokerDO of the previous release (which ignores the client and falls back) can't either.
- **Deleting a secret** (built 2026-11-09): `DELETE /v1/admin/secrets/<name>` (admin token) removes the row, value and all. BrokerDO's next lookup of that name finds nothing. It doesn't reach what was already handed out: a value a sandbox's proxy already holds lives until it expires or that sandbox's next secrets push replaces it. BrokerDO refuses its own keys (`binding_key:*`) and API clients' secrets (`client-secret:*`: theirs to delete). Audited as `secret_deleted`, by name, never a value. **Nothing is revoked upstream:** deleting an `inject:*` secret only stops nest injecting it; the credential stays valid at its provider until it's rotated there. An mcp capability's OAuth tokens aren't in `secrets`: they're revoked with [their own route](../../../agents/capabilities/mcp/#oauth).
- **Injected secrets:** static ones the operator stores, `inject:<binding>:<sandbox>` or `inject:<binding>` (`inject:<binding>:<workstream>`, with the sandbox's compat `workstream` value, is still read: secrets stored under it before the sandbox key may exist, and nothing new is keyed by it), and API clients' ([below](#client-secret-pushes)), sent to nest-proxy for placeholder substitution. Putting a binding in a sandbox's policy needs a grant on it. Each push (`secrets_update{sandbox, epoch, secrets}`) carries the sandbox's epoch and no policy version; nest-proxy checks the epoch only (a policy acknowledgement with a content hash is designed, not built: [injection](../../../sandbox/networking/egress/injection/)).
- **Serving a secret is checked twice** (designed; a partial form is built: SandboxDO re-reads the sandbox's epoch, host and client bindings once the references are in hand, and drops a push if any changed). Before fetching a value for a push, BrokerDO reads the target's state: the sandbox's epoch, its policy version and sha256, and the binding's grant. It reads the same state again once the value is in hand, and **discards the value if anything changed**, so a revocation, fence or policy edit that lands during a slow call never ships a credential. SPACE does the same ([credential_injection_authority.rs](https://github.com/perplexityai/space/blob/main/crates/libs/credential/mgr/server/src/credential_injection_authority.rs)).
- **Capability credentials:** `cap:<capability>` holds the bearer token (or a pre-registered OAuth client's JSON) for an `mcp` or `api` [capability](../../../agents/capabilities/#sources), and `cap:metrics` the Analytics Engine read token. The control plane uses them for each call; they never reach a host or a sandbox. **Built for `mcp`:** a bearer token stored with `PUT /v1/admin/secrets/cap:<name>`, read only through `capabilityToken` by the MCP proxy (AgentDO's calls, McpConnectorDO's tool lists) ([mcp capabilities](../../../agents/capabilities/mcp/)); `cap:` stays in the never-resolved list, so no host command can carry one. **OAuth** ([mcp OAuth](../../../agents/capabilities/mcp/#oauth)) keeps its tokens in its own tables (`oauth_grants`, `oauth_flows`, `oauth_clients`), never in `secrets`, so `capabilityToken` and `resolveRefs` can't return one. The MCP proxy gets an access token through `mcpOAuthToken`, which refreshes as needed, one refresh at a time per record. The refresh token, the PKCE verifier and any client secret never leave BrokerDO. A pre-registered client's JSON is an ordinary `cap:` secret, read at each token request.
- **API clients' secrets** ([secrets](../../api/clients/#secrets), built 2026-11-02): each value in `secrets` as `client-secret:<cli>:<name>`, what anyone may see of it in `client_secrets` (description, size, created, updated, last injected), never a value out. `putClientSecret` checks the grant's `secrets` (count and size) and writes in one step; `deleteClientSecret`, `clientSecrets` (metadata), and `deleteClientSecrets` at a client's delete. `clientInjectionRefs(client, sandbox, bindings)` answers references only under that client's id, for the unexpired secrets it has, each with its `expires_ms`, audits the push (`client_secret_injected`) before answering, and marks `last_injected_ms`. `writeClientSecret` stores an expiry with the value in `secrets.expires_ms` (`putClientSecret`, without one, stays for a Worker of the previous release). A write or delete is pushed at once ([below](#client-secret-pushes)). The admin secrets route refuses the prefix.
- **Brokered-action credentials:** `http:<name>`, an http profile's secret, read only by AgentDO's brokered pipeline (`brokeredSecret`). `scanSecrets(strings)` answers which stored secrets' values (raw, base64, long strings inside a JSON value, a PEM's body lines; 8 characters at least) appear in a brokered call's arguments: names only, so no value leaves BrokerDO. Exact values only, no credential shapes (2026-11-12).
- **The binding signing key** (`binding_key:<cell>`): an ECDSA P-256 private key per cell, generated on first use and stored as a JWK that rests nowhere else. BrokerDO signs every binding (`signBinding`) and hands FleetDO only the public keys (`bindingPublicKeys`); the admin secrets route refuses the `binding_key:` prefix, so the key can't be replaced from outside ([gateway](../../../interfaces/gateway/)). Rotation (a second listed key) isn't built.
- **Caller identity keys** ([below](#caller-identity-keys)): the Ed25519 keys that sign `Nest-Identity`.
- **The Access service token** (`access:gateway`) that fronts the sandbox hosts' tunnel hostnames: stored by me through the admin secrets route as JSON `{"client_id", "client_secret"}`, read by SandboxDO's `resolve` into the `edge` of every target that points at a host's tunnel, so a runner holds it only inside a target in memory. Never a sandbox ([gateway](../../../sandbox/gateway/)). Not built: a `nest` login that hands it to the CLI for terminals.
- **The api-loop API key** (deferred), used only inside the control plane.

The Cloudflare API token that creates and deletes per-host tunnels and DNS records is a Worker secret, like the other platform keys, not a BrokerDO secret.

**No GitHub App** (decided 2026-11-12, [principle 10](../../../README.md#principles); built 2026-11-15): BrokerDO mints nothing. The projects app holds its own App and keeps the tokens it mints as API clients' secrets. What the kernel's minting stored stays for one release, read and written by nothing: the `github_*` tables and `injections`. BrokerDO empties `injections` at each start, with the secrets `inject:<binding>:<sandbox>` it names (a sandbox's destroy, `forgetInjections`, does it for that sandbox), so an operator binding of that name never resolves to a token minted before, the sandbox placed or not. A later release drops them ([rollout](../../../../dev/rollout/2026-11-15-kernel-github-minting.md)).

## Caller identity keys

**Built (2026-11-02)** for [caller identity](../../api/clients/#caller-identity-for-mcp-servers) (`signIdentity`, `identityJwks`; `src/lib/identity.ts`):

- **Algorithm: Ed25519 (EdDSA).** Workers' WebCrypto supports `Ed25519` for `sign`, `verify`, `generateKey`, `importKey` and `exportKey` ([Cloudflare](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), as the Secure Curves API names it), so no ES256 fallback is needed.
- **Storage:** `identity_keys`, one row per key: `kid` (RFC 7638 thumbprint), the private and public JWK, `signs_from_ms`. The private JWK never leaves BrokerDO; the admin secrets route can't reach the table.
- **Schedule** (`keyPlan`, pure): the signer is the newest key whose `signs_from_ms` has come. A key signs 30 days. The next key is made a day before that and signs only after it has been published a day; if nothing signed or read the JWKS that day, it is made at the next use and the current key signs on until it has been published a day. A retired key stays published a day after the next one took over (a token lives 5 minutes, the JWKS is cacheable 5), then its row is deleted. The first key signs at once (no token can exist yet).
- **No alarm:** every sign and JWKS read applies the schedule. A key generated across an await is inserted only if the re-read schedule still wants one, so concurrent first uses make one key.
- **Signing:** the caller passes the subject (`aud`, `sub` and the optional claims, a strict schema); BrokerDO adds `iss` (`PUBLIC_BASE_URL`), `iat` and `exp` (5 minutes), so lifetime and issuer are decided here only.

**Built:** secret storage and references, purpose-scoped resolution, setup tokens, injected secrets (keyed by sandbox), the binding signing key, the caller identity keys, the Access service token, MCP OAuth, http profile credentials, the argument scan, and the issuance audit of MCP OAuth and API clients' secret pushes, and API clients' secret expiry and push on write. **Not built:** the general double check when serving a secret, and the audit of static secret pushes and binding mints.

## Client secret pushes

**Built (2026-11-12):** a client secret's write or delete reaches the sandboxes using it at once, not at their 15-minute push.

- **Who asked:** `clientInjectionRefs` records, before its first await, each secret the sandbox's bindings name for that client (`client_secret_sandboxes`), stored or not. A secret stored after its binding is pushed the same way. Additive only: pushes overlap, and a stale one finishing last must not take a newer one's secrets off the record.
- **Notices:** `writeClientSecret` and `deleteClientSecret` queue one row per (sandbox, client) in `client_secret_pushes` and arm BrokerDO's alarm in that step. The alarm calls each SandboxDO's `clientSecretsChanged(client)`, at most 50 at once, each call bounded at 10 s so one hung sandbox can't hold the run and every notice queued behind it, and deletes the row once answered, only if no newer write re-queued it (`seq`). A burst of writes is one notice per sandbox. A BrokerDO that starts with notices waiting and no alarm (after a previous release ran it) arms it again.
- **The sandbox:** arms its own `client_secrets` deadline at once, which pushes all its secrets again (`pushSecrets(true)`). A key of its own, so a push already in flight, which re-arms `inject_refresh` 15 minutes on, can't swallow it: the write that raced a refresh is pushed again after it.
- **Value and expiry together:** FleetDO resolves each reference when it sends (`resolveRefsExpiring`) and stamps the expiry read with the value on the entry, so a push in flight while a token is replaced carries the new value with its own expiry, never the old one's.
- **Failures:** a notice that fails or times out is tried again after 1 s, doubling, ten times (about 8.5 minutes), then dropped; a push that fails in the sandbox after 2 s, doubling, eight times (about 4 minutes), then left to `inject_refresh`. A failed read of the client's grant or references inside a push already retries in 2 minutes. The 15-minute push is the backstop for all of them.
- **Forgetting:** a sandbox's destroy forgets it (`forgetClientSecretSandbox`). A notice's answer forgets what the sandbox no longer asks for, only rows recorded before the notice went: `gone` (destroyed or never made) everything, `unbound` (none of that client's bindings apply) the client's, and `push` or `idle` (not on a host; a placement pushes) the client's names its bindings don't name now. A deleted client's rows go with it.
- **Cost:** one secret bound into N sandboxes costs N notices and N pushes, each a ClientDO grant read, a `clientInjectionRefs` call (and its awaited audit record) and a `secrets_update`; batches of 50 keep one alarm run bounded. Bind a widely shared secret only where it's used. The record grows with binding churn (each name a sandbox's bindings have named) until a notice's answer or the sandbox's destroy prunes it: bounded by the distinct names that sandbox has bound.
- **The operator's view:** each secret's `expires_ms` and `sandboxes` (how many asked for it) in `GET /v1/admin/clients/<cli>/secrets`; notices and failures in the logs.

## Issuance audit

Every secret push to a host and every refusal is written to R2 with the audit log. A record holds the binding, expiry, the target `(sandbox, epoch)`, the caller (the DO or principal that asked) and, for a refusal, the reason. **Never a value.** Binding mints (`signBinding`, including ones through the operator route) are audited the same way. **Built for MCP OAuth:** each flow start, registration, authorization, refused callback, refresh, failed refresh and refused token hand-out is one JSON object under `audit/broker/<day>/<ms>-<id>.json`, with the capability, record, resource, issuer, client id, scope, expiry, caller and reason. It is written in the background, so a failed write is logged and doesn't fail what it records. **Also audited:** an API client's secret push (`client_secret_injected`, awaited before its references are answered, so a push whose record can't be written doesn't happen), and, in the background, secret deletes (`secret_deleted`) and API clients' secret writes and deletes (`client_secret_put`, `client_secret_deleted`, `client_secrets_deleted`).
