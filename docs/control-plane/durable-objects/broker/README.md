# BrokerDO

The only DO that stores secret values. Platform keys live elsewhere: the proxy root CA key in AWS KMS, and AWS credentials, the host-token secret and the operator-token hashes as Worker secrets. See [../../../security/credentials/](../../../security/credentials/).

- **References, not values:** other DOs ask BrokerDO for a reference (`$nest-secret:<name>`) and pass that around. FleetDO resolves references when it sends a command to a host. Missing or expired secrets resolve to empty and are logged.
- **Resolution is scoped by purpose:** FleetDO resolves only two slots, `agent_start.oauth_token` (names `claude_oauth_token` and `claude_oauth_token:*`) and `secrets_update.secrets[].value` (`inject:*`), and `resolveRefs` takes that allowlist. A reference anywhere else in a command, such as a launch prompt, goes out as literal text. `binding_key:*`, `access:*`, `cap:*` and `hook:*` are never resolvable into a command, whatever the caller asks.
- **Claude setup tokens:** `claude_oauth_token`, plus named ones (`claude_oauth_token:<name>`, e.g. `:captain`) that a spawn spec's `credential` picks; a named one not configured falls back to `claude_oauth_token`. A credential naming any other secret is refused. They end up only in the Claude Code process environment on a brain host, never on a sandbox host.
- **Injected secrets:** `inject:<binding>`, sent to nest-proxy for placeholder substitution. Putting a binding in a sandbox's policy needs a grant on it. They're pushed with the policy version they were resolved for; nest-proxy checks them against the epoch only (a policy acknowledgement with a content hash is designed, not built: [injection](../../../sandbox/networking/egress/injection/)).
- **Serving a secret is checked twice.** Before fetching or minting a value for a push, BrokerDO reads the target's state: the sandbox's epoch, its policy version and sha256, and the binding's grant. It reads the same state again once the value is in hand, and **discards the value if anything changed**, so a revocation, fence or policy edit that lands during a slow GitHub call never ships a credential. SPACE does the same ([credential_injection_authority.rs](https://github.com/perplexityai/space/blob/main/crates/libs/credential/mgr/server/src/credential_injection_authority.rs)).
- **Hook secrets:** `hook:<hk_…>` for each [webhook](../../../channels/sources/). BrokerDO verifies signatures itself (`verify(ref, scheme, headers, body)`), so the secret is never returned to anyone after it's created; brokered actions such as `github.create_webhook` send it straight to the provider.
- **Capability credentials:** `cap:<capability>` holds the bearer token or OAuth tokens for an `mcp` or `api` [capability](../../../agents/capabilities/#sources), and `cap:metrics` the Analytics Engine read token. The control plane uses them for each call; they never reach a host or a sandbox. **Built for `mcp`:** a bearer token stored with `PUT /v1/admin/secrets/cap:<name>`, read only by AgentDO's MCP client through `capabilityToken` ([mcp capabilities](../../../agents/capabilities/mcp/)); `cap:` stays in the never-resolved list, so no host command can carry one.
- **GitHub App:** holds the App's private key and mints installation tokens per binding: a JWT signed with the key, then an access-token request narrowed to the binding's repos and permissions. Tokens last an hour and are cached for 50 minutes. A binding is one use, such as a worker's sandbox injection (push and open PRs) or a reviewer's brokered actions (post a check), so each token carries only what that use needs.
- **The binding signing key** (`binding_key:<cell>`): an ECDSA P-256 private key per cell, generated on first use and stored as a JWK that rests nowhere else. BrokerDO signs every binding (`signBinding`) and hands FleetDO only the public keys (`bindingPublicKeys`); the admin secrets route refuses the `binding_key:` prefix, so the key can't be replaced from outside ([gateway](../../../interfaces/gateway/)). Rotation (a second listed key) isn't built.
- **The Access service token** (`access:gateway`) that fronts the sandbox hosts' tunnel hostnames: stored by me through the admin secrets route as JSON `{"client_id", "client_secret"}`, read by SandboxDO's `resolve` into the `edge` of every target that points at a host's tunnel, so a runner holds it only inside a target in memory. Never a sandbox ([gateway](../../../sandbox/gateway/)). Not built: a `nest` login that hands it to the CLI for terminals.
- **The api-loop API key** (deferred), used only inside the control plane.

The Cloudflare API token that creates and deletes per-host tunnels and DNS records is a Worker secret, like the other platform keys, not a BrokerDO secret.

**Built:** secret storage and references, purpose-scoped resolution, setup tokens, injected secrets, the binding signing key and the Access service token. **Not built:** the double check when serving a secret, hook secrets and `verify`, OAuth capability credentials (a static bearer is built), GitHub App minting and the issuance audit.

## Issuance audit

Every installation-token mint, every secret push to a host and every refusal is written to R2 with the audit log. A record holds the binding, repos, permissions, expiry, the target `(sandbox, epoch)`, the caller (the DO or principal that asked) and, for a refusal, the reason. **Never a value.** Binding mints (`signBinding`, including ones through the operator route) are audited the same way. **Not built:** no audit record is written yet.
