# Autoscaling and spot

- **Scale to zero.** FleetDO launches hosts only when there's runnable work queued. **Built** for sandbox hosts (`AWS_CELLS`, [control plane](../../../control-plane/README.md)):
  - A sandbox no connected host can take launches one spot host from the cell's launch template, unless a launch is pending or the cell is at `max_hosts`.
    - **One pass of attempts:** each type on spot, in `instance_types` order. Then each type on demand, in `on_demand_types` order: cheapest first, since the cell stack sorts it by its verified price table (`on_demand_types_priced`). So an on-demand host is never dearer than the cheapest type with room. This changed on 2026-11-04: before, only the first type went on demand.
    - **Where a pass stops:**
      - at the first launch;
      - at a spent quota on demand (`VcpuLimitExceeded`, `InstanceLimitExceeded`). The same quota on spot skips the rest of spot and goes on to on demand;
      - at any other error that isn't EC2 having no room (an IAM refusal, a throttle). That attempt is kept and repeated by the tick, and no later type is tried.
    - **A pass with no room anywhere, or a spent on-demand quota,** starts a backoff for that host kind in FleetDO: 60 s, doubling to 15 min (5 min for brain hosts, under the 12 min a brain waits), cleared by a launch.
      - Until it lapses, no demand starts a pass: not another waiting sandbox, not a brain waiter, not the tick.
      - It decays: once the last backoff lapsed more than 30 min ago, the next pass with no room waits 60 s again.
      - So a pass makes at most twice as many RunInstances calls as there are types, and a backoff stands between passes. Each RunInstances attempt is recorded before it is sent, and one whose answer was lost is repeated with the same client token until EC2 answers or `enroll_timeout_ms` passes, so its instance is recorded and none is launched twice; only demand plans a new one.
  - **Idle grace:** a launched host that holds no lease and no agent for `idle_grace_ms` (10 min) is marked dead, then terminated; the grace keeps conversations with several turns fast. Suspended sandboxes don't keep a host up: a retired host's suspended sandboxes are evicted (lease dropped; their head is in S3) and wake lazily elsewhere.
  - A launch that hasn't enrolled within `enroll_timeout_ms` is terminated, and so is a launched host that enrolled but never said hello within `enroll_timeout_ms` of its enrollment (dead, its leases reassigned).
  - **Enrolment breaker** (decided 2026-11-06, `control-plane/src/lib/enroll-breaker.ts`, pure, table-tested). Launches of one instance type that keep never enrolling, such as a type without KVM (a sandbox host refuses its role there and shuts down), would otherwise relaunch every `enroll_timeout_ms` for good while sandboxes wait. So FleetDO keeps a breaker per host kind and type (`kv enroll_breaker:<kind>`):
    - 3 consecutive launches of a type that end `enroll_timeout` open it for 30 min. A pass skips the type meanwhile and tries the next.
    - After the cool-down, one more launch is let through. If it fails too, the breaker opens again for twice as long, up to 6 h.
    - The first enrolment of the type closes it and clears its count. A host that enrolls but never says hello isn't counted: its enrolment already reset the type.
    - With every type of a kind open, the kind launches nothing until the earliest cool-down ends. That isn't "no room", so no backoff starts.
    - The operator sees it as an error in the logs (once per opening, and once per kind-wide opening) and in the fleet view (`GET /v1/admin/fleet`'s `enroll_breakers`: kind, type, failures, `open_until_ms`, `open`).
    - Launch rows record their type for it (`launched.type`); a row from before that counts for nothing.
    - **Closing them early,** so a fixed release doesn't wait out a cool-down:
      - **A new host image closes them all at the next demand.** Each launch records the host image it was built from (the cell's `/imagebuilder/nest-<cell>/host-ami` parameter, which the launch template resolves; `launched.image`). The breakers keep the image their first failure was launched from, so failures under an image already replaced are cleared at once. A pass that finds an open breaker reads the parameter again; a read is reused for a minute (memory only), so passes don't each call SSM. An unreadable parameter changes nothing.
      - **The operator can close them:** `POST /v1/admin/fleet/enroll-breakers/reset?cell=<cell>` with an optional `{role, type}` closes every breaker, a kind's, or one type's, and answers `{cleared: [{role, type}]}`.
    - **Known bounds** (accepted trade-offs, each self-limiting):
      - The image a launch records can be up to a minute stale (the cached read), while the launch template resolves the parameter at launch time. So a launch in the minute after an image change may be credited to the old image: at most about one cool-down's extra launches.
      - A pass filters with the breakers it read before an uncached image read. A breaker that `scaleDown` opens during that read is missed for that pass: at most one extra launch.
      - A new image clears the breakers only while one is open. Failure counts below the threshold from an old image carry over until the new image's failures open the breaker, which the next pass then clears.
    - **A waiting sandbox says why** while every type its kind would launch is open: `GET /v1/sandboxes/<id>` shows `placement_wait {reason, until_ms, ms}`, for example "launches paused: consecutive enrolment failures for c8id.large (3), c8i.large (3); next probe at …". An agent's hands resolve refuses with the same text. SandboxDO notes it each time a placement finds no room (FleetDO's `launchPause`) and drops it when placed or when launches resume. The dashboard's attention list shows each open type as a warning.
  - The packing, launch and retirement decisions are pure functions (`pickSandboxHost`, `scaleUpPlan`, `idleStep` in `control-plane/src/lib/placement.ts`); the last two are shared by both host kinds.
  - Evidence: on EC2 (use1, 2026-10-17) a cell went from zero hosts to a running sandbox and back to zero.
- **EC2 Fleet** (designed, not built): spot requests across the 8i family (C8i, M8i, R8i, preferring `d` variants) with the **price-capacity-optimized** allocation strategy, as AWS recommends ([docs](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-fleet-allocation-strategy.html)), falling back to on-demand.
- **Pack, then consolidate:** placement fills hosts before opening new ones (see [FleetDO](../../control-plane/durable-objects/fleet/)), so idle hosts empty out. A host that's emptying is drained gently, then terminated.
- **Drain:** stop placing on the host, suspend its sandboxes to S3, then terminate it once FleetDO's [drain gate](../../control-plane/durable-objects/fleet/) passes (every resident's head is the host's last commit, and no upload is pending).
  - **Gentle** (consolidation, upgrades; not built): residents keep running and suspend at their next idle point, under the usual [idle rule](../../control-plane/durable-objects/sandbox/#activity-and-idle). After 30 min the drain turns forced.
  - **Forced** (spot notices): suspend every resident now. One that was busy (an agent mid-turn, an ingress guard or a hold) is placed elsewhere at once; the rest wait until something needs them. **Built:** nestd polls IMDS `spot/instance-action` every 5 s and reports `spot_notice`; FleetDO stops placing on the host, suspends its running sandboxes and evicts each as it reports `suspended`; a sandbox with an agent mid-turn is placed again at once (ingress guards and holds aren't known to the control plane yet). A draining host doesn't count toward `max_hosts`, and one with no leases left is terminated. Evidence: AWS FIS spot interruptions on EC2 (use1, 2026-10-17) moved a sandbox with an agent mid-turn to a new host through S3 within about 90 s of the notice, its files intact, and the agent finished its re-queued turn.
  - **Moves keep state:** a paused sandbox is snapshotted as it is, without running again, and a move keeps memory unless no host could load it (an [ABI-changing upgrade](../provisioning/#upgrades)).
  - **Size:** each host is capped so a forced drain finishes in about 90 s at its measured upload bandwidth, inside the 2-minute spot notice.
- **Moves are checkpoint and restore,** like every sandbox provider; no one offers live migration.
- **Optional stopped warm host:** a stopped instance with the image already on disk, costing about $2/mo for EBS. Starting it is faster than a fresh launch. (Auto Scaling warm pools can't use spot in mixed-instance groups; [docs](https://docs.aws.amazon.com/autoscaling/ec2/userguide/ec2-auto-scaling-warm-pools.html).)
- **Spot interruption** gives 2 minutes' notice; what a sandbox host does with it is in [state](../../sandbox/state/#spot-notice-2-minutes).
- **Brain hosts scale the same way, in brains.** **Built:** a brain no connected [brain host](../brain-hosts/) can take launches one from the cell's brain-host launch template (the `brain` section of `AWS_CELLS`: its instance types on spot, then each on demand cheapest first, with the same backoff, as for sandbox hosts, up to `brain.max_hosts`, 3 by default, about 12 brains; one pending launch at a time; while agents wait, the tick launches too); a launched host with no brain indexed for `brain.idle_grace_ms` (30 min) is terminated. A launch is only for a real lack of capacity (`brainHostNeeded`): never while a brain host with room is merely reconnecting, and a brain host of the previous release doesn't count toward the cap. A spot notice drains a brain host as forced at once. **Designed, not built:** for an upgrade a brain host drains gently: no new brains are placed on it, running ones finish their turn and exit at idle, and after 30 min the drain is forced: the brains are killed and AgentDO starts them elsewhere with `--resume`. No sandbox is touched, since none lives there, and no drain gate applies, since a brain host uploads nothing ([upgrades](../provisioning/#upgrades)).
