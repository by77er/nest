# Gateway

**The only network door into a sandbox.** One unprivileged process per sandbox host (`crates/nest-gateway`). Previews, terminals and hands are three routes behind the host's one tunnel hostname, so a brain, a person's terminal and a browser all enter the same way, from wherever they run. Wire contract: [../../interfaces/gateway/](../../interfaces/gateway/); the feed from nestd: [nestd-gateway](../../interfaces/host-internal/nestd-gateway/). **Built:** the `/hands` route, bindings, the nestd link, the runner reaching the guest only this way (proven on the e2e harness with the gateway on loopback), the per-host tunnel (verified on AWS on 2026-10-23: spike item 13) and the Access credential in every tunnel target (demanded by the edge since 2026-10-24: [setup](../../setup/#later-not-needed-to-start-testing)), and the host's systemd unit. **Not built:** `/pty` and `/ingress/<port>` (the gateway answers 501), and the gateway's own user and socket group.

```
brain host · AgentDO ─► Cloudflare Access (service token) ─► Tunnel ─► cloudflared on the sandbox host
   ─► gateway: verify the binding, pin (sandbox, epoch) on every frame
   ─► Firecracker vsock unix socket: "CONNECT 1025" (hands, call_status) · "CONNECT 10000" (PTY, ingress) ─► guest agent
```

- **Routes:** `/hands` (one WebSocket per hands call, and `call_status`), `/pty` (terminal attach and reattach), `/ingress/<port>` (previews, `nest port-forward`). Each is one connection per call or stream, forwarded to the guest's vsock port; the [host-guest](../../interfaces/host-guest/) frames pass through verbatim.
- **What it checks.** Cloudflare Access admits only holders of the service token at the edge. The gateway verifies the binding (a listed key, the signature, expiry, scope, and a client in the sandbox's attached set) and that its epoch is the sandbox's current epoch, checks the first frame's agent, epoch and version against the binding, and forwards nothing until every check passes; the guest checks the epoch again. Two checks, one rule. A binding for an older epoch gets `stale_epoch`; a sandbox that isn't on this host gets `moved`; the precedence is in the [contract](../../interfaces/gateway/#error-codes). A connection that hasn't finished its upgrade and `bind` within 5 s is dropped, and at most 256 may be in that phase at once.
- **Cancel is a close.** A dropped WebSocket closes the vsock side, and the guest kills the call's cgroup: a hangup is a cancel, whoever hung up (the brain, a network partition, a gateway restart). When a sandbox leaves the host mid-call (a fence, a lost nestd link, the gateway stopping on SIGTERM) the gateway closes the call with code 4409 and the client treats the outcome as unknown. Terminals keep the 60 s detach grace the [guest agent](../guest-agent/#terminals) gives them.
- **No state, no secret.** The gateway stores nothing and holds only public keys. nestd feeds it over `/run/nest/gateway.sock`: the cell's verification keys (from FleetDO's `binding_key`) and, per sandbox, the epoch, the vsock socket, the attached clients and the guest's version, replayed in full on every connection and as deltas after ([nestd-gateway](../../interfaces/host-internal/nestd-gateway/)). Revocation is the client set and the epoch: a detached client or an older epoch is refused, with nothing to store. nestd tombstones a fenced epoch so no late update re-adds it, and the gateway refuses (and logs) an update whose epoch is older than the one it holds, so a regression can neither cut current calls nor re-admit old bindings; only a removal, or a lost nestd link, lets a sandbox return at a lower epoch. nestd forgets a suspended sandbox so a client resolves again instead of retrying `busy`. The gateway runs as a separate process that connects to nestd, like nest-proxy (the e2e starts it in `inner.sh`; `nest-gateway.service` on a host), with file permission on the VMs' vsock sockets and nothing else. Losing the nestd link cuts every open call and refuses every bind as `moved` until the link is back; the keys survive it, the sandboxes don't. A restart cancels open calls through the hangup; bindings are unaffected, since they're verified, not stored.
- **Addressing.** Clients learn the gateway's URL from `resolve`. The control plane is the authority: at a sandbox host's enrollment the Worker creates one Cloudflare Tunnel (`nest-<host>`), its ingress to `http://127.0.0.1:18790`, and one proxied CNAME `<host>-gw-nest.<zone>` to `<tunnel-id>.cfargotunnel.com` on a route no Worker handles ([setup](../../setup/#hostnames), [remote tunnel API](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/get-started/create-remote-tunnel-api/)), records them on the host's row, and answers `resolve` with `wss://<that hostname>` once the host reports the tunnel `connected` (nestd polls cloudflared's `/ready` and reports `none`, `connecting` or `connected` in its hello and as `tunnel_state` events); while it reports `connecting`, `resolve` answers `sandbox_not_ready` with a retry hint, and a host that has a hostname but reports `none` (an old nestd, no binary) falls back to the URL its hello advertises, logged as an error, which works only while every brain runs beside its sandbox. The enrollment response carries the tunnel token and that URL. nestd keeps the token in its credentials file and runs cloudflared with it in the process environment (`TUNNEL_TOKEN`), never on a command line; cloudflared dials Cloudflare outbound on port 7844 (QUIC, falling back to HTTP/2; [tunnel ports](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/configure-tunnels/tunnel-with-firewall/)) and keeps the connection open, and the host accepts no inbound connection. FleetDO deletes the tunnel and record when the host dies, and a daily sweep removes leaks, touching only tunnels and records with nest's names. Without all three of `NEST_DOMAIN`, `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_TUNNEL_API_TOKEN` (the harness, a cell without a zone) no tunnel exists and the URL is what nestd advertises in its fleet hello from configuration (`gateway_url`, `ws://127.0.0.1:18790` on the harness, and the loopback fallback on a real host while every brain runs beside its sandbox). **Tunnel-only to start:** a VPC endpoint for same-cell brain hosts is a latency shortcut, added only if a measurement asks for one. A client needs only outbound HTTPS, so a brain host in any VPC and a Durable Object reach a sandbox the same way.
- **Auth layers:** the Access service token at the edge, the binding at the gateway, the epoch in the guest. The token rests in BrokerDO (`access:gateway`); `resolve` puts it, as `edge`, in every target that points at a host's tunnel, so the runner sends it on each upgrade, and never in a target that points at a gateway directly; a tunnel target cannot be minted without it (`resolve` fails, not retryably, until the secret is stored); a sandbox never holds it. The Access applications that demand it (`*-gw-nest.<zone>` with a Service Auth policy on the token; `*-preview-nest.<zone>` with an Allow policy for the owner) are created by hand, never by the control plane, which only stores the token ([setup](../../setup/)). The gateway logs each admitted call `bound … via=edge` when the upgrade carried a `cf-ray` header (it came down the tunnel) and `via=direct` otherwise: the evidence that calls take the edge path.
- **Versions.** `resolve` reports the guest's `protocol_version` and `capabilities` as nestd last heard them, and `bound` carries the authoritative ones, so a client sends only what the guest advertised ([host-guest versions](../../interfaces/host-guest/#versions-v2)); a `bind` for another guest version is `unsupported_version`, on which a client resolves again once, since the target may predate a guest upgrade. The gateway's own protocol has a served range and `bound` echoes the version chosen, so a brain host and a sandbox host can be one release apart in either direction. Frames stay within the host-guest 16 MiB limit, exactly one per message; nothing is chunked.
- **What it must not know:** which backend drives a client, its model or prompt, whether the client is an agent or a person, where the client runs or which path it took, and which grants led to the binding. It knows a client id, an epoch and a scope.
- **Failure.** A Cloudflare edge or tunnel outage takes every route down; sandboxes keep running and clients wait. An unreachable control plane changes nothing for open bindings until they expire (about an hour).

**Not built:** the `/pty` and `/ingress/<port>` routes, so previews, terminals and port-forwards have no router yet; a `nest` login that hands the CLI the Access token; an unprivileged user and socket group for the gateway (the host unit runs it as root beside nestd for now); key rotation beyond accepting a list. `crates/nest-gateway/README.md`, `crates/nestd/README.md` and `control-plane/README.md` list the gaps.
