# Firecracker driver

- **Isolation:** each VM runs under the jailer with `--netns`, so it's in its own network namespace. Every tap device is named `tap0`, so a snapshot restores anywhere. See [../../networking/](../../networking/).
- **Memory:** regular 4 KB pages today, demand-paged and capped per VMM cgroup ([memory](../../state/memory/)). With memory snapshots (designed, not built): **2 MB hugetlbfs** pages, whose restore **requires UFFD** (a file-backed restore fails with an error); full snapshots only, since dirty-page tracking cancels the benefit of hugepages; and no traditional balloon, because it can't free hugetlbfs memory (free page reporting works at 2 MiB, with the UFFD handler processing `UFFD_EVENT_REMOVE`).
- **Guest kernel** boots with `init_on_free=1` once memory snapshots exist, so freed pages are zeroed and compress to nearly nothing. Until then it's off: on a nested 8i host it made a 1-vCPU guest zero all its memory at boot, and boots stalled past a minute (soft lockups in `pgdatinit`, 2026-10-18). Whether it's affordable with snapshots on nested hosts is open.
- **VMGenID** reseeds randomness after a fork. vsock connections reset on restore, and the guest agent reconnects.
- **Nested virtualization is outside Firecracker's tested matrix** (it tests `.metal` instances; 8i hosts are supported on host kernels 6.1 and 6.18, per its [README](https://github.com/firecracker-microvm/firecracker/blob/main/README.md)). The overhead on AWS is unmeasured; "10% or more" is GCP's figure, and AWS recommends bare metal for performance-sensitive work ([AWS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/amazon-ec2-nested-virtualization.html)). The first spike measures nested against `.metal`.
- **Hugepages** (for the snapshot path) reduce the cost of rebuilding page tables after a restore; Firecracker's docs report boot times up to 50% faster.
- **Version:** the 1.17 line, for `huge_pages` on snapshot load and `sync_snapshot_files` ([changelog](https://github.com/firecracker-microvm/firecracker/blob/main/CHANGELOG.md)), **pinned by binary digest, patch level included.** A patch release can change the snapshot format: SPACE reports that 1.16.2 writes format 11.0.0 and can't restore the format-10 snapshots of 1.16.0 and 1.16.1 ([runtime-manager-catalog.md](https://github.com/perplexityai/space/blob/main/docs/runtime-manager-catalog.md)). The digest is part of the [restore ABI](../../state/memory/#restore-abi).
- **Memory restore is qualified per (Firecracker, guest kernel) pair.** A pair that boots isn't thereby fit for snapshots; until the first spike qualifies nest's pair, hosts make disk-only generations ([restore ABI](../../state/memory/#restore-abi)).
- **Drives** keep the default `Unsafe` cache mode, so a guest flush stops at the host page cache, where nestd's read (and, designed, its reflink cut) sees it ([disk](../../state/disk/#flush-before-commit)). They keep the default `Sync` io_engine, whose writes all land before a pause returns: the unchanged-disk check relies on it (`pause_quiesces_disk`). The reflink cut (M2) needs the `Async` engine and turns that check off ([disk](../../state/disk/#m2-cut-with-a-reflink-while-the-vm-runs-designed-not-built)).
- **Rate limiter** on every drive (not built): 10,000 ops/s and 100 MiB/s with a 30 s burst by default ([I/O limits](../../state/disk/#io-limits)).

**Built and verified** (EC2 `c8i-flex.large`, nested virtualization, Firecracker 1.17.0, 2026-10-18): a 1-vCPU, 1 GiB guest boots from `nest-base` in seconds; a real Claude Code turn ran its tools in it; egress went through nest-proxy (allowed 200, denied 403); the disk committed at turn end, and after a host reboot the sandbox restored on epoch 2 with the file intact.
- **Jailer:** each VM runs as uid 900 in its own jail (`<sandbox>-<random>`: the jailer accepts only alphanumerics and `-`, and a retry must never share a jail being torn down); nestd removes a stopped VM's jail and, at start, any a crash left. The tap is owned by the jail's user. Once the VM has started, nestd gives the gateway's group the vsock socket (`0660`) and search on the jail root (`0710`); the API socket and the hard-linked disk are the jail user's alone (`0600`) ([gateway](../../gateway/)).
- **Memory:** no hugepage pool; each VMM's cgroup gets `memory.max` at the declared size plus 128 MiB, and bootstrap clears any pool an older AMI reserved (2026-10-24, [memory](../../state/memory/)).
- **Disk:** a fresh sandbox's disk is a copy of `nest-base`, extended to its size and grown offline by nestd before boot (the guest can't resize its own root).
- **Guest image** (`images/guest/`; **decided 2026-10-22**): the kernel is Firecracker's **prebuilt** CI build from the **6.18 longterm line** (`vmlinux-6.18.54`, pinned by SHA-256), never one nest builds itself. Firecracker supports 6.18 guests from 1.16.1 with a minimum end of support of 2028-06-01, while 6.1's minimum ended 2026-09-02 ([kernel policy](https://github.com/firecracker-microvm/firecracker/blob/main/docs/kernel-policy.md)); 6.18 is also kernel.org's current longterm line. The rootfs is Firecracker's Ubuntu 24.04 CI squashfs plus apt packages (git, `gh`, build tools, python3) and the GitHub placeholder for git's credential helper and `GITHUB_TOKEN` ([injection](../../networking/egress/injection/#github)); init exports `/etc/environment` into nest-guest's environment, which every command inherits. `nest-base` is the only image, built on a disposable EC2 builder; init brings up `eth0` on the sandbox network and runs nest-guest on vsock. Sandboxes **cold-boot** it: memory snapshots wait for a measured need ([memory](../../state/memory/)).
- **Not built:** memory snapshots (UFFD; deferred by decision), ublk, the rate limiter. A snapshot load re-creates the vsock device, which binds a fresh socket with the VMM's umask mode: the restore path must give it to the gateway's group again (`gateway_access`), as `start` does.
