# nest projects

A task board for GitHub repos, run by agents on nest: an app with its own Worker and Durable Objects, built only on nest's [API clients](../docs/control-plane/api/clients/) interface. nest knows nothing of projects, tasks or reviews. A feature here that seems to need one of nest's internals means that interface is wrong: fix it there, generically, and build this on the result.

**Status:** designed (2026-11-02, the owner's request). **Built:** the core: the Worker, the three Durable Objects, the catalog sync, the JSON API, the MCP servers and nest's webhook ([below](#built-the-core)), the UI ([below](#the-ui)), attaching a repo and the review pipeline ([below](#built-the-review-pipeline)), auto-merge ([below](#auto-merge)), workers carrying their PRs to merge ([below](#pr-upkeep)), and routines and memory ([below](#routines)). **Not built:** setting nest's webhook at first start. Builds on API clients, caller identity and events to the owner, and on its own GitHub App ([GitHub tokens](#github-tokens)).

## What it does

- **Projects.** A project is attached to one GitHub repo the owner owns: one the GitHub App's installation reaches, on the App owner's account or one the operator adds ([repo authority](#repo-authority)).
- **The manager.** One agent per project, the one the owner talks to. It keeps the board, specs each task as it's created, and assigns tasks when the project is set to assign automatically.
- **Tasks.** The owner or the manager creates them, and the manager specs them. They're assigned by hand from the board, or automatically. An assigned task gets a worker of its own: one agent, which sees only that task and opens one PR for it.
- **Review.** Every PR on the repo gets a review by a reviewer agent, asynchronously. The review judges correctness, quality and architectural cohesiveness, and sets a required check. Branch protection, which the app sets up, makes merging wait for that check.
- **Done.** A task is done when its work is finished: for a task with a PR, when the PR is merged, which needs the review check to pass. Only a task with no PR and no live worker is marked done by hand.

## Pieces

| Piece | What it holds or does |
|---|---|
| Worker `projects` | The UI (Vite + React), the JSON API behind it, the MCP servers agents call (`/mcp/board`, `/mcp/task`, `/mcp/review`, `/mcp/routine`), and two webhook endpoints: nest's (`/hooks/nest`) and GitHub's (`/hooks/github`) |
| `DirectoryDO` (one) | Projects, repo → project (the repo's binding, and its name: the only copy anything reads, [below](#the-repos-binding)), agent → project and role, the events and deliveries already handled, the app's catalog sync state, the GitHub App's id |
| `ProjectDO` (one per project) | The project's settings and its repo's attachment, the board (tasks, specs, assignments, the history of each), the chat with the manager, PR → task, the routines and their runs, the memory notes |
| `ReviewDO` (one per project) | The review queue: one job per PR head, its reviewer agent, its check run, its verdict. It's an asynchronous process of its own, with its own alarm and an optional concurrency cap (none by default) |

All state is the app's. nest holds the agents, their sandboxes and their transcripts, and labels each agent with `project`, `role` and, for a worker, `task`, for a reviewer, `pr` and `sha`, or for a routine run, `routine` and `run`; a manager's, worker's or reviewer's agent and sandbox also carry `start`, its start attempt. The app finds its agents by those labels after losing track of one.

## How it uses nest

Only the client interface. One client, `projects`, has this grant:
- `cells`, and `credentials: [claude_oauth_token]`;
- `repos`: only for starts frozen before B3 (nest's repos, [the sandboxes' GitHub access](#the-sandboxes-github-access)) and the live agents they made until B4 converges them; new spawns send none, and no template names one. B4 narrows it away;
- `github.repos` and `github.permissions`: nest's own tokens, the fallback's only ([GitHub tokens](#github-tokens)). The App's installations must have the same permissions: `checks: write` (check runs), `administration: write` and `metadata: read` (branch protection, the default branch, the repo's "Allow auto-merge"), `pull_requests: write` and `contents: write` (auto-merge on task PRs, and reading the repo's merge settings; [below](#auto-merge)), which also cover reading PRs to attach them (`pull_requests: read`; [below](#prs)). Each call's token asks only for what that call needs. The PRs live workers own are read with `pull_requests: read` and `checks: read` ([PR upkeep](#pr-upkeep)). Otherwise a PR's number, head, base, title and node id come in its webhook, and the reviewer reads the code in its sandbox;
- `mcp_urls: [https://projects-nest.bitcru.sh/mcp/]`;
- `egress_hosts`: the hosts the [Network page](#network) may open for its agents (nest's `egress_hosts`, needs nest PR #134), and the GitHub hosts the app opens for every sandbox: `api.github.com` (required: nest's base layer doesn't open it), `github.com` and `*.githubusercontent.com` ([the sandboxes' GitHub access](#the-sandboxes-github-access));
- `max_agents` and `max_sandboxes`;
- `secrets: {max_count, max_bytes}`, `inject_hosts` and `github_push: {workflows}`: what the owner may give its agents ([below](#secrets)). `inject_hosts` must also have `github.com` and `api.github.com`, and `max_count` room for two secrets per project, for the project's own GitHub tokens ([the sandboxes' GitHub access](#the-sandboxes-github-access)); `github_push` is for starts frozen before B3 only.

## GitHub tokens

The owner's decision (2026-11-12, [the plan](../docs/README.md#settled-decisions), principle 10's row, phase B1): the GitHub App belongs to this app, not to nest's kernel. Its id and private key are the Worker's secrets `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` (the PKCS#1 PEM GitHub hands out), and the app mints its own tokens (`src/github-app.ts`).

- **The JWT:** RS256 with WebCrypto, the PKCS#1 key wrapped as PKCS#8 (ported from nest's `control-plane/src/lib/github.ts`); `iss` the App's id, `iat` a minute back, `exp` 9 minutes on, signed again with a minute left ([GitHub](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)).
- **The installation:** `GET /repos/{o}/{r}/installation` with the JWT ([GitHub](https://docs.github.com/en/rest/apps/apps#get-a-repository-installation-for-the-authenticated-app)). Kept 10 minutes per repo, and looked up afresh for every read of [the repo's binding](#the-repos-binding) (attach, a sync, Re-read, a refused event), so the binding never takes a cached answer. None (404): the App isn't installed there, a refusal.
- **The token:** `POST /app/installations/{id}/access_tokens` narrowed to the one repo (by name) and exactly the permissions the call needs (`PERMISSIONS` in `src/github.ts`; [GitHub](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app)). The App's installation must have been granted them (the [setup](#setup-the-operators)).
- **The cache** (per Worker isolate, memory only): tokens keyed by installation id, then repo and permissions; one is handed out again while it has more than 10 minutes left (as nest's own reuse). It never outlives its installation:
  - a lookup that answers another installation (the App reinstalled, the repo moved) drops every token of the old one;
  - GitHub answering a token 401, or 404 where a 404 isn't the expected answer (an unprotected branch, no such user or PR), drops it and the repo's lookup, so the next call looks the installation up and mints again (the call itself fails, and is retried as any GitHub failure is);
  - a mint refused 404 (the installation gone) drops the installation.
  So nest's reuse after a reinstall (#253: up to about 50 minutes of the old installation) doesn't apply: the binding follows a reinstall at the next refused event, sync or Re-read.
- **GitHub's to refuse:** the repos a token reaches and the permissions it may have are the App's installation's, on an account the app may act on ([repo authority](#repo-authority)): a repo it doesn't select fails the lookup (404) or the mint (422), an installation on another account fails the lookup's check (refused as not covered), and a permission the owner didn't grant the App fails the mint (422, naming the permissions asked for). nest's grant isn't asked (B1 asked it before each mint; B2 dropped that). A cached token under a cached lookup is handed out without asking GitHub: a repo dropped from the installation's selection reaches it at its next 404 or mint.
- **Failures:** the secrets unset, a key that isn't one, or GitHub refusing the JWT is an outage (503, retried with the rest), never a refusal, and says which secret to check. No token, JWT or key is ever logged or put in an error.
- **The fallback, for one release:** `GITHUB_TOKEN_SOURCE=nest` (a Worker secret or var) takes every token from nest's `POST /v1/clients/self/github-token` again, as before B1: nest mints from the same App, so the binding's installation ids, the App's id and its bot are the same either way. It needs no App secret. Unset (or anything else): the App's own. Removed with nest's route (phase C).
- **Rollback:** setting `GITHUB_TOKEN_SOURCE=nest` (`wrangler secret put GITHUB_TOKEN_SOURCE`, no deploy; a secret survives deploys, a dashboard var doesn't) is the way out of a key problem. Rolling the Worker back to the release before B1 does the same, with no state to undo: nothing new is stored.

## Repo authority

The owner's decision (2026-11-12, [the plan](../docs/README.md#settled-decisions), principle 10's row, phase B2): which repos the app may act on is GitHub's to say, by the App installation's own repo selection. nest's grant keeps only generic ceilings for the app (`inject_hosts`, `egress_hosts`, `secrets`, `max_agents`, `max_sandboxes`); its GitHub fields (`repos`, `github`) stop bounding the app's own GitHub calls, and go with phase C.

- **Listed** (`GET /api/repos`, `src/installations.ts`): the App's installations on the accounts the app acts for (`GET /app/installations` with its JWT, filtered by each one's `account.id`, [GitHub](https://docs.github.com/en/rest/apps/apps#list-installations-for-the-authenticated-app)), then each one's repos (`GET /installation/repositories`, [GitHub](https://docs.github.com/en/rest/apps/installations#list-repositories-accessible-to-the-app-installation)) with a token of that installation for all its repos and `metadata: read` alone, minted for the listing and revoked after. 100 a page; at most 10 pages of installations and an installation's first 1000 repos (`complete` false past that). An installation whose repos can't be listed is named (`unlisted`, its account), not dropped. The answer names the App (`app: {slug, install_url}`, from `GET /app`): the form links its installation page, `https://github.com/apps/<slug>/installations/new`, where it's installed on an account or an installation's repos are chosen, for a repo that's missing (and for none at all). A repo the list may not show (an installation it couldn't read, or past the cap) can be typed instead, and is checked at create. Always the App's own listing, even in the fallback (it needs the App's key; failing, the form takes a typed name).
- **Checked:** creating a project (`POST /api/projects`) and applying a rename look the repo's installation up afresh (its account checked, below) and mint a token narrowed to it (`metadata: read`), never a cached one, then revoke it. GitHub refusing either (404: not installed, or on another account; 422: not selected) refuses the create (403) or keeps the rename waiting; any other failure is an outage (502, or retried), never a refusal. In the fallback, nest's token decides instead (its grant).
- **Not asked:** nest's `/v1/clients/self/grant/repos` (neither route): the app no longer calls it.
- **A transfer is followed** once the App reaches the repo's new name, by the repo's id: a repo moved to another account the app acts for, whose installation selects it, is read there, and its binding takes that installation ([the repo's binding](#the-repos-binding)). Before B2, nest's grant had to name the new name. Only the repo's admin can transfer it; a name taken over by another account is another repo id, and never binds by itself.
- **The accounts the app acts for** (decided 2026-11-12, from B2's security review): the account that owns the App (`owner.id` of `GET /app`), and the account ids the Worker var `GITHUB_ACCOUNTS` adds (comma or space separated ids; there is no wildcard, and nothing turns the check off). Every installation lookup checks the installation's `account.id` against them, so create, rename, following a transfer and every mint fail closed (as not covered, 404) for another account's installation, and nothing of it is cached; the listing leaves such installations out. So a public App installed on a stranger's account gives the app nothing there. The App's owner comes from `GET /app` (kept for the isolate): when that fails, or answers no `owner.id` (not kept), every check fails closed as GitHub's trouble (502), never as allowed. A binding with no installation known yet (bound before installations were stored) takes an event only when its repo's owner (`repository.owner.id`) is one of these accounts; others are refused and counted like another installation's (not checked in the fallback, where nest's grant decides). Keeping the App installable only on its owner's account is still wise (unverified for the live App).
- **Since B3,** nest's grant `repos` bounds nothing new: templates name no repo and new spawns send none, so a repo the App reaches is attachable and its agents run whatever the grant's `repos` say. Only a start frozen before B3 still sends nest's repos (and the live agents those made, until B4).

### The sandboxes' GitHub access

The owner's plan (2026-11-12, [the plan](../docs/README.md#settled-decisions), principle 10's row, phase B3): the agents' git and gh reach the project's repo through nest's generic client primitives, never its kernel repos. `src/github-access.ts` (pure) builds it; ProjectDO keeps the tokens.

- **Two tokens per project,** installation tokens of the app's own App for the bound repo by its id (`repository_ids`, [GitHub](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app); trust is anchored to repo ids, [the repo's binding](#the-repos-binding)), from the binding's installation (`AppTokens.sandboxToken`: looked up, its account checked, and refused unless it's the binding's `installation_id`, which waits for a re-read), minted afresh, never cached or handed to another call, from the App's key even with `GITHUB_TOKEN_SOURCE=nest`:
  - **push** (workers): `contents: write`, `pull_requests: write`, and `workflows: write` only while "Workers may change CI workflows" is on;
  - **read** (the manager, reviewers, routine runs): `contents: read`, `metadata: read`.

  Each is a client secret, `gh-push-<project>` and `gh-read-<project>` (apart from the owner's, `<project>-<name>-<generation>`), written with the token's own `expires_at` (`PUT /v1/clients/self/secrets/<name>`, nest's [expiry](../docs/control-plane/api/clients/#secrets)), so nest-proxy refuses its placeholder once it expires, and nest pushes each write to every sandbox bound to it within seconds.
- **Only while something holds it:** each try of a start that has it (frozen with it, any role) writes it first when it has 10 minutes left or less, or carries `workflows: write` otherwise than the setting (not once the start's agent exists: its layer holds it then); then ProjectDO's alarm writes it again 30 minutes before it expires (`REFRESH_BEFORE_MS`), while a live agent started with it (its layer: the manager, workers, reviewers) or a routine run of the app's holds it. With none, it lapses (nest refuses its placeholder once it expires), and the next holder schedules it again. The manager always holds the read token. One refresh per kind at a time, per generation: a workflows toggle or a rebind never reuses one in flight before it, but runs after it. The token written before is left to expire (a proxy may still hold it until the push lands), never revoked then.
- **Within the grant's limits, checked first:** before a token's first write, `GET /v1/clients/self`'s `secrets.max_count` must have a place for it (two per project), and every write `max_bytes` room; otherwise the start waits, saying the operator must raise it. nest checks again.
- **Tokens are kept only to revoke them** (`gh_tokens`, until each expires): GitHub revokes an installation token only by the token itself (`DELETE /installation/token`, [GitHub](https://docs.github.com/en/rest/apps/installations#revoke-an-installation-access-token)). These are the app's own short-lived credentials, minted from the App key the Worker already holds; the owner's secrets are still never in a table ([Secrets](#secrets)). Revoked:
  - **workflows turned off:** every push token that had `workflows: write` at once (a lapsed one too, which the next start then replaces), and the push token is written again without it. A refresh in flight from before the toggle (or a rebind) never leaves its token in the secret: found stale before its write it isn't written, after it it's revoked, and the toggle's own refresh runs after it;
  - **the repo out of the App's reach** (GitHub refusing it twice running: 404, not installed or another account's; 422, not selected): both secrets deleted from nest, every token revoked, and the owner told once in the chat ("The GitHub App can't reach <repo>: the App isn't installed on it (404) / the repo isn't selected in its installation (422), so agents' GitHub tokens were revoked and new agents wait to start. Install the App on the repo, or give its installation access to it. …"); looked for again every 30 minutes, written again once the App reaches it, and the owner told it's back (`settings.gh_unreachable`). One refusal takes nothing away (retried soon);
  - **the repo rebound** to another repo: ProjectDO keeps the repo id its access follows (`settings.gh_repo_id`) and each token secret the id its token was minted for (`gh_access.repo_id`). Every read of the binding compares DirectoryDO's id with it (the operator's bind and each sync's, `readBinding`; each start; each refresh), so a notice that failed is made good at the next: on another id, every token is revoked, both are written again for the new repo, and every live layer is owed again, so the guards follow the repo's name. A start never takes a token minted for another repo than the one followed. A rename (the same id) owes every live layer again too;
  - **the project removed:** every token revoked and both secrets deleted, retried from the alarm until nest takes it (a refresh whose write lands after that deletes its secret again, whatever is left of its rows);
  - a token minted for a write that failed.

  GitHub refusing the installation a permission the token needs (422, "not granted"): the owner is told so once ("The GitHub App's installation doesn't grant everything the workers' push token needs (contents: write, pull_requests: write; GitHub doesn't say which is missing). Give the GitHub App those permissions in its settings if it lacks them, then accept them in its installation settings on GitHub. …"), it's tried again every 30 minutes, and nothing is revoked: agents keep the token written last until it expires. Turning workflows on writes the push token again with it; where the App's installation can't grant it (422), it's written without (`wf_refused`): the owner is told once in the chat, and Settings says it under the toggle and beside each live worker (Failed, with why; `workflows_refused` in `GET /api/projects/:id/secrets`). Live workers follow at once: they share the project's push token.
- **Each role's sandbox** (`sandboxSpec`, frozen per start attempt with its Idempotency-Key) gets, at its create:
  - the binding of its token, `gh_push` or `gh_read`, on `github.com` and `api.github.com`, as a bearer token and a Basic password whose username nest-proxy writes itself (`x-access-token`, nest #273: a Basic field is nest's whole for the guards' `at` only then, since git sends whatever username its helper answers, and GitHub takes a token as the username too). These names are reserved from the owner's secrets;
  - `GH_TOKEN` holding its placeholder (`nest-ph.<client>.gh_push.`; gh reads it before the image's `GITHUB_TOKEN`, [gh](https://cli.github.com/manual/gh_help_environment)), and git's helper for `https://github.com` from the environment (`GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`/`_VALUE_n`, [git](https://git-scm.com/docs/git-config#Documentation/git-config.txt-GITCONFIGCOUNT)): first emptied (an empty helper resets the list, so the guest image's `git-credential-nest`, which answers nest's kernel placeholder, is never asked), then a shell helper answering `get` with `x-access-token` and `$GH_TOKEN`. The helper reads the variable when git runs it, so no value but `GH_TOKEN`'s holds a placeholder (nest refuses one that isn't exactly a binding's). nest-proxy swaps the placeholder in the Basic password, or gh's `token`, for the token. These variables are reserved from the owner's secrets too;
  - the GitHub hosts the grant's `egress_hosts` covers (`api.github.com` is required);
  - the app's own guards, the sandbox's own (`POST /v1/sandboxes {guards}`), so they hold for as long as it lives: before its agent is made, and after it ends. Ported from nest's kernel constructor: `github-push` (receive-pack and its discovery on github.com only into the repo, for push; none for read), `github-write` (other github.com writes only to the repo for push, besides fetches and LFS downloads, each anchored at a repo, `/*/*/…`, as nest's constructor now is), `github-api-write` (writes on every `*.github.com` only under `/repos/<repo>/` for push, and GraphQL only with the sandbox's own binding written whole into `Authorization`: `{injected, at: authorization}`), `gist-write` and `githubusercontent-write` (none). git asks its helper only after discovery's 401, so discovery can't require nest's credential; nest's own guards then require one for the push itself ([GitHub](../docs/sandbox/networking/egress/policy/#github)).

  The brief says git and gh are signed in to the repo (and whether they push), never the placeholder: the manager's, a worker's, a reviewer's and a routine run's.
- **Its sandbox ends with it:** nest leaves a sandbox up after its agent ends, with its bindings and guards, so on `agent.exited` (any role) ProjectDO destroys it (`sandbox_ends`: the sandbox from its layer, else nest's view of the agent; gone already, 404 or 409, is done; retried with backoff, given up after 12 tries to nest's idle TTL, and its row forgotten).
- **nest's repos narrowed to none** in every such spawn (`overrides.repos: []`, `read_repos: []`): a shared template the catalog sync hasn't rewritten since the deploy still names every project's repo, and nest would otherwise give the agent its own GitHub token for them, and refuse the app's `GH_TOKEN` beside it. Goes with nest's repos (phase C).
- **Live sandboxes keep it:** a layer write (`clientLayerFor`, from the Network or Secrets page, or Settings) puts the GitHub binding, its variables and hosts back beside the owner's secrets and the role's rules (`layers.github`), within the grant as read then (out of `inject_hosts`, the binding and variables go), with the guards for the repo by its name now (they stay whatever the grant: they only refuse; a layer that only removes keeps them all), and never nest's push opt-in, which would refuse `GH_TOKEN`. Up to 15 of the owner's secrets then, nest's limit of 16 bindings less the GitHub one.
- **A start waits, shown, never dropped:**
  - while the grant lacks the GitHub hosts (`inject_hosts` `github.com` and `api.github.com`; `egress_hosts` `github.com`, `api.github.com` and `*.githubusercontent.com`, as the [setup](#setup-the-operators) says), its error naming what the operator must add (a routine run doesn't count it among its 8 attempts);
  - while a sandbox host of the cell doesn't apply client guards yet (nest's 409 `hosts_not_ready`, nest #274; a nest from before it said `conflict`, told apart by its words, "needs every sandbox host of cell …", for one release: `NestError.hostsNotReady`), its error saying it waits: nothing is made (the sandbox's create carries the guards); a worker's and the manager's start are retried with backoff, a reviewer's job keeps its attempt, and a routine run doesn't count it (its time budget still runs). The same attempt goes on once the hosts apply them, its guards sent each time.
- **Needs nest's #271 and #273:** without #271, nest's own GitHub guards refuse every write in a sandbox with no repos of nest's own, the app's binding's included; without #273, nest refuses a Basic location's `username`.
- **Starts frozen before B3** keep nest's repos: their retries send the same request (`overrides.repos` or `read_repos`, the project's template written with the repo, `github_push`), and their agents' layers keep nest's opt-in. A routine run already tried when this release came is marked so by its migration (`routine_runs.nest_repos`). A start from a shared template (a reviewer's, a routine run's) frozen so fails once the catalog sync has taken the templates' repos away, and the next attempt is the app's.
- **The guards' seam:** `protocol/fixtures/control/egress_policy/egress_policy.app_github_{push,read}.json` (a vitest asserts the app builds them), evaluated by nest-proxy's own evaluator in `crates/nest-proxy/tests/app_github_guards.rs`. The environment runs through the real git and gh in `test-node/git-credential.test.ts`.

## The repo's own guidance

The owner's decision (2026-11-10): guidance is layered, and each layer owns its own.

- **nest's kernel** knows no repo conventions: its prompts cover hands, taint and grants.
- **The app** owns its roles' guidance: the prompts in `src/catalog.ts`.
- **The target repo** owns its own: its `AGENTS.md` (or `CLAUDE.md`) and `.claude/skills/`, untouched by the app.
- **The join is the app's.** Every role that works on the repo's code (manager, worker, reviewer and routine runs: each template with hands) is told, in one generic line, to read the repo's `AGENTS.md` (or `CLAUDE.md` if there is none) and follow it, and to list `.claude/skills/` and follow the skill that fits its work. It says when: once the repo is checked out, and again whenever the guidance is no longer in context (after a resume or compaction): brains restart with `--resume` after an idle exit or a host loss, and the template is the system prompt, which a resume applies again. The manager is among them, since it specs tasks from the repo.
  - **The manager, workers and routine runs** (`REPO_GUIDANCE`) read it with the hands Read tool from their task branch or the default branch, never from a pull request's or a fork's branch they look at (a worker reading an attached fork PR takes none of that PR's guidance).
  - **The reviewer** (`REVIEWER_GUIDANCE`) reads it from the PR's base branch, never its head (`git show origin/<base>:AGENTS.md`, the skills listed with `git ls-tree` and read with `git show` from there): the PR under review can write those files, and the reviewer's verdict is its check. Its prompt says the PR's own changes to `AGENTS.md`, `CLAUDE.md` or `.claude/skills/` are part of the diff under review, never instructions. A PR can retarget its base to any existing branch of the target repo, so at worst the reviewer's guidance is a worker's `task/*` branch's (agents push only those; anyone else needs write access to the repo).
  - **These are prompt instructions, not enforcement:** nothing stops an agent that disobeys from reading the head's files. What enforces is elsewhere: the review gate holds untrusted PRs for the owner's approval, and a reviewer can't write to the repo. A dreaming run has no hands and isn't. No template carries repo-specific text. The runner doesn't read the repo's `CLAUDE.md` itself ([runner](../docs/agents/runner/README.md)).
- **Reaching nest's catalog:** the shared templates change at the next catalog sync: the operator presses **Sync catalog** on the Admin page (creating a project runs one too). A project's own templates on its models are written again at each start, so they follow by themselves.

## The MCP server: agents see only their own work

- **One URL per role:** `/mcp/board` for the manager, `/mcp/task` for a worker, `/mcp/review` for a reviewer, `/mcp/routine` for a routine run ([routines](#routines)). nest lists a server's tools over one session shared by every agent on it, so a role's tool list is its URL's. Which data a call may touch is decided per call, from the caller's identity.
- **Every request** must carry a valid `Nest-Identity`:
  - signed by a key from nest's JWKS;
  - `aud` is that URL, and `iss` is nest;
  - `client` is the app's own client id;
  - **`owner` is also the app's client id.** Only agents the app created itself are trusted. A spawned agent's labels are whatever its spawner chose, so they mean nothing here.
  - There is no bearer secret: the capabilities name no `auth`, so nest sends no `Authorization`, and the identity is the credential.
- **Scope comes from the labels:**
  - The manager reads and writes the board of its `project`.
  - A worker reads its `task`, posts progress on it, marks it blocked or clears that, says when its PR is open, asks for a secret it needs, and reads the project's memory. It sees no other task.
  - A reviewer reads its `pr` at its `sha`, and submits one verdict per dimension (correctness, quality, architectural cohesiveness) with a summary.
  - A routine run acts only while its `run` is live and is this very agent's (its `routine` and `run` labels): it reads the board and recent work, proposes tasks and keeps memory ([routines](#routines)).
- **`tainted`** is recorded with each write and shown on the board. It gates nothing: a worker and a reviewer read repo content by design.

## Flows

- **Attaching a repo.** The owner picks a repo from those the App's installations reach. The create form lists them (`GET /api/repos`, `src/installations.ts`) from GitHub's answer ([repo authority](#repo-authority)). The app never matches names itself. A repo already a project's is shown but can't be picked; an installation whose repos couldn't be listed is named. If the list can't be had at all, the name is typed. Either way, `POST /api/projects` asks GitHub first and refuses (403) a repo the App doesn't reach, so no project is made that could never attach (and would hold the name). A rename is applied once the App reaches the new name. The app then, in this order:
  1. mints a token with `administration: write` and `metadata: read`, and reads the default branch;
  2. makes the check `nest-projects/review` required on it, with nothing else changed. A branch with no protection gets a minimal one: that check alone, `strict: false`, `enforce_admins: false`, no required reviews, no restrictions;
  3. only then starts the project's manager.

  A failure is shown on the project (`attach_error`), with the manager not started. A refusal that will repeat (the App not installed, the repo not among its installation's repos, no admin) waits for the owner's `POST /api/projects/:id/attach`; anything else is retried from the alarm. An attach owed while one runs (the owner's retry, the App's id learned) is a new generation (`attach_gen`): the running one's outcome doesn't clear it, so it runs after.
- **A task:**
  1. It's created (`draft`).
  2. The manager specs it (`ready`).
  3. It's assigned (`assigned`), by the owner from the board, by the manager, or automatically. Automatic assignment takes `ready` tasks in board order while the project's live workers are fewer than its `max_workers`.
  4. The app starts a worker labelled with the task (`in_progress`).
  5. The worker pushes a branch `task/<task-id>` and opens a PR (`in_review`). The PR's branch maps it to the task. The owner or the manager may attach more ([below](#prs)).
  6. The worker owns its PR until it merges: told when it fails review, has a failing check or conflicts with its base, it fixes it and pushes ([PR upkeep](#pr-upkeep)).
  7. All its attached PRs merged (`done`), and the worker is ended.
  
  A worker that exits before opening a PR leaves the task `stalled`, shown on the board, to be reassigned. Cancelling a task stops its worker. [The task machine](#the-task-machine) has every move.
- **Review:**
  1. GitHub's `pull_request` events (`opened`, `synchronize`, `reopened`) reach `/hooks/github`, which checks the signature. Every PR is reviewed, a task's or not.
  2. ReviewDO queues a job for the PR's head SHA. A newer head replaces a queued job and stops a running one, whose check is cancelled.
  3. Each job creates a check run (`in_progress`) and starts a reviewer.
  4. The reviewer's verdict completes the check: `success` only if all three dimensions pass, else `failure`, with the summary as the check's output. A `failure` on a task's PR reaches its live worker with the findings ([PR upkeep](#pr-upkeep)).
  5. A reviewer that ends without a verdict (it exits, or its 60 minutes pass: every running job has a deadline) is stopped and started again, twice, then the check completes as `action_required` with the reason, and the job's slot frees. A reviewer nest has no room for (the grant's `max_agents` or `max_sandboxes`) isn't a failure: the job waits, queued, and starts once there's room ([below](#built-the-review-pipeline)). Not `neutral`: a required check accepts `success`, `skipped` and `neutral` ([GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging)), so `neutral` would let the PR merge unreviewed. A `check_run` `rerequested` queues the job again.
- **Merging** is GitHub's, gated by the required check. With the project's auto-merge on, the app enables GitHub's auto-merge on each task PR ([below](#auto-merge)); it never merges itself. A `pull_request` `closed` event with `merged: true` marks the PR merged, and its task `done` once every attached PR has, ending its worker; closed without merging, the PR is detached, noted in the task's history, and the task leaves review if it was the last ([the task machine](#the-task-machine)). Marking done by hand doesn't get past this gate: it's refused for a task holding an open PR, whatever its state, and for one with a live worker (cancelled instead).

## The task machine

The owner's request (2026-11-06): a task's state, its worker, its PRs and the comments queued for its worker move as one machine, so no mix of webhooks, nest's events and the owner's moves leaves a task where the flow has no way out.

- **One pure function,** `step(facts, event)` in `src/tasks.ts`. The facts are the state, the open and merged attached PRs, whether a worker of its own is live, whether its start is owed, and how many comments wait for its brief. It answers the new state and facts and what else to do, or why not.
- **ProjectDO applies it and nothing else writes these.** `move` reads the facts from its tables, steps, then writes in one step:
  - the PR row the event is about;
  - the state and the history line;
  - the worker's columns: a new start, started, failed, exited, or a stop owed;
  - the queued comments: queued, sent after the brief, or dropped (recorded).

  The start's retry schedule (attempts, next try, last error) is the outbox's, not a move.
- **The UI's buttons** come from the same `step`, over the task's state, PRs and `worker_live`, so it never offers a move the Worker refuses.
- **States:** `draft`, `ready`, `assigned` (a worker starting), `in_progress`, `in_review`, `stalled`, `done`, `cancelled`.
- **Events and moves:**

  | Event | From | To | With it |
  |---|---|---|---|
  | `spec` | draft; ready, assigned, in progress, in review | ready; the same | its live worker is told |
  | `assign` | ready, stalled (no live worker) | assigned | a new start owed |
  | `started` | assigned | in review with an open PR, else in progress | queued comments sent after the brief |
  | `start_failed` | assigned | stalled | no worker; queued comments dropped |
  | `start_abandoned` | assigned | assigned | a new start attempt |
  | `worker_exited` | a live worker's state | in review with an open PR, else stalled | queued comments dropped |
  | `pr_attached` | not over | in review from in progress, else the same | |
  | `pr_merged` | an open PR | done when it was the last open one | the worker stopped |
  | `pr_detached` | an open PR | the last open one: done if any merged, else in progress (worker live) or stalled, from in review | the worker stopped, if done |
  | `done` | draft, ready, stalled; no open PR, no live worker | done | a stale worker stopped |
  | `cancel` | not over | cancelled | the worker stopped; queued comments dropped |
  | `revise` | ready, in review, stalled; no live worker | assigned | a new start owed; the comment queued |
  | `input_queued` | assigned | assigned | the comment queued |

- **Invariants,** checked after every step of a seeded random walk over the machine (`test/machine.test.ts`): `done` has no open PR and no worker of its own; `in_review` has an open PR or a live worker; `stalled`, `draft` and `ready` have no live worker; a start is owed exactly in `assigned`; comments are queued only while a start is owed.
- **"Live"** is a worker of its own, starting or running. One being stopped for a task that's over still counts toward `max_workers` until nest has stopped it, but isn't the task's.
- **What the sweep found, fixed here:**
  - **Done with a PR open (B2).** A ready or stalled task can hold an open PR, so marking done by hand is refused for any task holding one, and a worker started for a task with an open PR (a revise) starts in review.
  - **In review with no way out (B3).** The last open PR closed unmerged, or detached, with no worker running, stalls the task. With the worker running, the task goes back to in progress.
  - **Comments outliving their worker (B8).** These are dropped when the start fails or the worker exits before its brief, and recorded as dropped.
  - **A close handled twice** merges an open PR only once, so the routines' counters count it once.
- **Deleting a draft (B4)** is refused while it holds an open PR: detach it first. Detaching turns the PR's auto-merge off on GitHub, a write a delete shouldn't make unseen, and the owner sees the PR they're letting go.
  - Everything else that names the draft goes in the same step: tasks waiting on it stop waiting (noted on each), its own dependencies, detached PR rows, and the manager's waits on it. A draft never had a worker, so it has no queued changes or comments to leak.
  - An issue it was made of returns to triage, to be accepted or declined afresh.

## Outboxes

The owner's request (2026-11-06): the app's retry queues as one machine, so each shows its real state and treats a failure the same way.

- **One pure function,** `outboxStep(row, event)` in `src/outbox.ts`, over each queue's `next_ms`, `attempts` and `error`.
  - **States:**
    - `owed`: not tried yet;
    - `retrying`: tried, or waiting for something it needs, and due again;
    - `failed`: refused for good, or out of attempts; shown, and tried again only when asked;
    - `done`.
  - **Events:**
    - `sent`;
    - `failed`, transient or permanent by one verdict (`verdict`: nest's or GitHub's refusal that will repeat);
    - `wait`: nothing to send it to yet; due again, never counted, never failed;
    - `retry`: only a failed row changes, so asking twice sends once.
  - **Pruning by age** (`pruneBefore`). Tested on its own, with a seeded random walk (`test/outbox.test.ts`).
- **The queues on it:**

  | Queue | On failure | Kept once ended |
  |---|---|---|
  | `chat` (the owner's messages to the manager) | permanent: failed, with Retry | always (it's the log) |
  | `messages` (to agents) | permanent: failed | a week from when it was sent or failed |
  | `stops` (ending agents) | retried until it goes, except nest's own refusal (failed stops, below) | never once failed: kept until resolved |
  | `issue_closes` | permanent: failed; tried again on the owner's retry, or (the fallback) a grant gaining `issues: write` | always (the task's record) |
  | client `layers` | permanent: failed, shown on the Network page | while the agent lives |
  | `templates` (a stale [model template](#models)'s delete) | permanent, or 30 attempts: failed, among the project's errors | until its template is written again |
  | ReviewDO's `check_updates` (a check run's update on GitHub) | permanent, or 30 attempts: given up, said on the review job | until sent or given up |
  | ReviewDO's `stops` (ending reviewers) | retried until it goes, except nest's own refusal: kept, said on the job, not tried again | until nest says the agent ended |
  | ReviewDO's `ended` (a finished review, told to the project for the manager's waits) | 30 attempts: given up, said on the job (the wait ends by its timeout) | until taken or given up |
  | a review job's own step (its check, its reviewer, the brief) | permanent: the job fails, with why; otherwise retried within the job's deadline. No room in nest for its reviewer isn't permanent: the job waits, queued ([the review pipeline](#built-the-review-pipeline)) | with the job |
  | a held job's check | permanent, or 30 attempts: shown on the job, which waits for the owner all the same | with the job |

  A reviewer's refused stop isn't among the Network page's failed stops (those are ProjectDO's): it shows on its review job (a follow-up, if it ever happens).
- **Failed stops.** A failed stop may leave an agent running, with its sandbox and its credentials, so it's never quiet.
  - **Only a real refusal fails a stop.** That's nest's own refusal of the request, in its JSON error body (400, 409; `stopRefused`). An auth failure (401, 403), or a page that isn't nest's (a proxy's, Access's), may pass, so it's retried.
  - **A failed stop is shown everywhere it matters:**
    - in its task's history (`stop_failed`);
    - on the Network page, with **Retry stop** (`POST /api/projects/:id/stops/:agent/retry`) and **Dismiss** (`DELETE …/stops/:agent`, confirmed);
    - in a message to the manager;
    - among the project's errors.
  - **Its place stays counted** toward `max_workers` until the stop goes, the owner dismisses it, or nest's `agent.exited` says the agent ended. Any agent's exit counts here: a worker's, a routine run's or a manager's.
  - **A failed stop is never pruned.** Its agent may still be running.
  - **Nothing in it is due before the owner acts.** Its next try is set to never, so the alarm never spins on it.
  - **Nothing is said for an agent that exited during the refused try.** Its stop is gone already, so there's no notice and no row.
  - **The Network page names what each one was for:** its task, by title; its routine, by name; and why it was stopped, in words ("A routine run timed out").
- **The chat (B9).**
  - **States.** Each message carries `status` (`ChatMessage.status`). A message waiting for the manager, or retried after an outage, reads "Sending…" or "Retrying…" with why, quiet; the words always carry the state. One spinner at most shows in the log, beside the most recent message in flight, and only once that message has been in flight on the page for 300 ms (an ordinary send never flashes one), in room kept beside the word from the start so nothing moves; with reduced motion there is none. Only a failed one reads "Not delivered" (a warning badge with an icon), with Retry. A change in a message's delivery is announced to screen readers once (held up, not delivered and that Retry is there, sent again, delivered after a hold-up); an ordinary send and what was already so when the chat opened are not.
  - **Retry.**
    - On a failed message, Retry is `POST /api/projects/:id/chat/:seq/retry`, which leaves any message that isn't failed as it is.
    - On a message the page never had an answer for, Retry posts it again under the same `request_id`, the page's id for that message (`POST …/chat {text, request_id}`). The Worker keeps request ids (`chat_request`), so a post whose answer was lost is one message, not two.
- **One-off cleanup.** The migration that adds `chat_request` also drops PR rows whose task is gone: nothing updates them, and a PR in one couldn't be attached again.

## The manager lifecycle

The owner's request (2026-11-06), after the state-machine sweep (B11): a manager that ended mustn't stay the project's manager, with its brief and the owner's chat retried against a dead inbox.

- **A pure step,** `managerStep` in `src/manager.ts`. ProjectDO applies it in one step (`managerMove`), and nothing else writes these settings.
  - It works over the manager's agent, when a start is due, the recent automatic restarts (`settings.manager_restarts`), and why it isn't running.
- **Ended: replaced by itself, up to a cap.** The manager counts as ended when:
  - nest's `agent.exited` arrives for it;
  - the Manager page's read of nest finds it ended or gone, so a missed exit still counts;
  - its brief is refused for good after it was made (404, 409, 410).

  A new one starts with backoff, up to 3 times an hour (`MANAGER_RESTARTS`). Past that, nothing is started: the page shows it ended, and the owner restarts it.
- **The replaced manager:**
  - its sandbox is destroyed: a stop is owed (`manager replaced`), which ends the agent and then destroys its sandbox through the sandbox API, since stopping an agent that already ended destroys nothing. Its successor starts only once that stop has been tried. With nest refusing it for good, the successor starts anyway (the stop is failed, shown on the Network page);
  - its pending waits end, unannounced, since the new one never made them;
  - the next start gets a start number of its own, so its creates' keys aren't the old one's;
  - if it exits by itself while that stop is still owed (or failed), the stop stays owed until its sandbox is gone;
  - **it loses its voice:** only the current manager's turns are recorded as the manager's chat, and an ask from a manager that isn't current is labelled "The previous manager" in "Needs you" (its question shown as plain text);
  - **it loses the board:** the board's tools answer only `settings.manager`. A replaced manager still holds its token and labels for a while (its stop owed, or refused), and gets 403.
- **A start is of one generation.** `manager_starts` as read when it began. Every move bumps it (an exit, the owner's Restart), so a start that lands after one is stale:
  - an agent it made goes;
  - its final write (manager started, nothing owed) applies only to its own generation;
  - an exit during its brief, or a second Restart, leaves that move's start owed.
- **The owner's Restart** (`POST /api/projects/:id/manager/restart`; **Restart manager** on the page when it ended or errored) stops the current manager and starts a new one now. Asking while one is already starting changes nothing.
- **Chat during a restart.** The owner's chat messages wait for a manager ("Retrying…"), and go as soon as one has started. Each change is noted in the chat. While the manager has ended or errored, the composer offers no Stop and doesn't say it's waiting for the owner's reply; on a phone, where the page's notice scrolls away, it also says so ("The manager isn't running", with Restart manager).
- An exit of a manager that isn't the current one changes nothing.

## Models

The owner's request (2026-11-09): "allow me to select the model for the manager and the workers. Default manager = Fable 5.2, worker = Opus 5.5."

- **Two settings per project,** `manager_model` and `worker_model` (`PATCH /api/projects/:id/settings`; the Models panel in Settings).
  - **Defaults:** the manager on `claude-fable-5-2`, workers on `claude-opus-5-5` (`DEFAULT_MODEL` in `src/models.ts`). A project with no models set reads as the defaults.
  - **Offered by name:** Fable 5.2, Opus 5.5, Sonnet 5.5 (`claude-sonnet-5-5`), Haiku 5.5 (`claude-haiku-5-5`), and **Custom**: any id or alias Claude Code's `--model` takes.
  - **A model id is one argument of a command,** so it's letters, digits and `. _ : @ / [ ] -`, starting with a letter or digit (never `-`, which would read as an option), at most 100 characters. Checked in the form, the API and ProjectDO.
- **Through nest's generic interface only.** A client's spawn can't override a template's launch (nest answers 400: a different launch is a template in the client's namespace, [clients](../docs/control-plane/api/clients/)). So each choice is a template of the app's own:
  - `projects/<role>-<project>-<model>` (`modelTemplateEntry`), the role's template with `launch.model` (which nest passes to Claude Code as `--model`, [runner](../docs/agents/runner/)) and only that project's repo.
  - An id that isn't already a legal entry name (capitals, dots, brackets, too long) is cut down and ends `--<hash of the whole id>`. A plain id never holds `--`, so no plain id can take a hashed id's template. Two hashed ids would share one only if their 32-bit hashes collided, which the owner's own typing won't arrange.
  - ProjectDO writes it before each start that names it (`templateFor`): the same body every time, so writing it again changes nothing.
- **Stale templates are cleaned up** (`sweepModelTemplates`, from the alarm). The project records each template it writes and the template each agent started from.
  - One is deleted from nest's catalog (`DELETE /v1/catalog/templates/projects/<entry>`) once it's neither the role's current setting nor the template a live agent started from. Whether nest reads a live agent's template again is unverified, so it's kept while that agent lives.
  - Nothing is swept while a start is owed, since it may be about to name one.
  - A template's delete is an [outbox](#outboxes) row. One nest can't take now is tried again with backoff, from the alarm, not at every drain. One nest refuses for good, or can't take 30 times, is recorded among the project's errors (`template_delete_failed`) and not tried again; the template stays in nest's catalog.
  - A template that's kept again (the setting came back to it, or a start wrote it) is owed no delete: what a failed one left is cleared, and it's no reason for the alarm. Each delete is decided afresh after the last one's answer, and a row a start wrote while its delete was at nest is left to that start.
  - A project that's gone (a create that couldn't be finished) takes all of its with it. Deletes nest couldn't take then are tried again from the project object's own alarm, which does nothing else once the project is gone, and is set only after a sweep ran and while a delete is still to be tried.
- **A start freezes its model** with its attempt (`start_specs`), so its retries name the same template under the same idempotency keys.
- **Workers:** a change applies to workers started after it; running ones keep theirs.
- **The manager switches now** (the owner's request, 2026-11-10: "Switching the manager agent model should take effect immediately"). Saving a new manager model moves the running manager onto it, keeping its conversation:
  - **How:** nest restarts the same agent on the new model, resuming its session (`POST /v1/agents/<id>/start {restart: true, launch: {model}}`, `restartAgent`). The answer names the launch as stored; one without it (a nest release before the route) wasn't applied: the chat says so, and the manager runs on until its next start, which takes the new model.
  - **Between turns:** the restart is asked with `when: "idle"`, so nest restarts the manager only while no turn runs, and answers 409 `busy` otherwise. Then the switch waits for its `turn_completed` (and asks again every minute, should that be missed). Settings says "Running <model>; switches to <model> after this turn" meanwhile.
  - **A nest before `when`** refuses the field (400). The app then looks at the manager's state itself (`working`, `waiting_permission`, `compacting`, `quota_parked`, `stalled` mean a turn) before restarting. If a turn starts just as it switches, that turn starts again on the new model.
  - **nest giving up an accepted restart** (its `agent.error` `restart_refused`, after 5 failed tries, about 2.5 minutes with the manager's turns held): the brain runs on its old model.
    - **Which switch:** the event names no restart, so the app reads the agent's `restart_error` (`GET /v1/agents/<id>`). A later restart asked clears it, so a late refusal of an earlier switch finds none and changes nothing. Each give-up (its `ms`) counts once, however many events name it.
    - **Tried again, backed off:** the chat says "The switch to <model> didn't complete (nest couldn't restart the manager): trying again in 5 minutes.", then 10. A lasting cause (no room for a brain) would otherwise keep the manager's turns mostly held.
    - **Given up at the third:** "Couldn't switch to <model>: it takes effect when the manager next starts." (nest keeps the stored model). Settings says "Couldn't switch the running manager: takes effect when it next starts." under the manager's model until then, or until the setting changes; it isn't tried again meanwhile. Another model setting starts a count of its own, and is tried at once. A new manager starts with none counted.
    - **Said on acceptance:** "Switched to <model>" is said when nest accepts the restart, not when the new brain starts: the simpler of the two, and a refusal is said when it comes.
  - **The chat** shows "Switched to <model>." when it's done.
  - **The last change wins:** the switch reads the setting when it runs, so two quick changes end on the second; a change back to the model it runs on cancels it. A change (or a change back) while a restart is at nest: what nest answers it runs is recorded, and a switch onto the setting as it is then is owed.
  - **No running manager** (a start pending, or it ended): nothing to switch; its next start takes the setting's model. A start frozen before the change runs the old model, then is switched once it's started.
  - **Race-safe:** a switch made stale by a move of the manager (an exit, the owner's Restart) writes nothing. A switch nest refuses for good is said in the chat and not tried again until the setting changes; one it can't take now is retried with backoff.
  - A start frozen with no model keeps the role's shared template (`projects/manager`, `projects/worker`), which carry the defaults.
- **Reviewers and routine runs are unchanged:** their templates name no model, so they run on nest's and Claude Code's default. Choosing theirs is a later setting if it's wanted.
- nest doesn't check that a model exists or that the credential may use it (`LaunchConfig.model` is any string). How a wrong id shows (Claude Code failing its first turn, so nest's `agent.error` among the project's errors) is unverified.

## The repo's binding

A security follow-up (2026-11-09, once the repo was public): a project's repo is bound by GitHub's ids, read from GitHub, not learned from an event.

**One owner for each fact** (the owner's principle, 2026-11-11: eliminate duplicate data that can go stale; read state through from its source of truth, events being nudges only; keep only real decision records: the app's own intent, audit history and idempotency):
- **The repo's name** is DirectoryDO's (`projects.repo`) alone. ProjectDO, ReviewDO and the Worker read it from there whenever they call GitHub, start an agent or brief one, so a rename applied reaches them all at once. ProjectDO's `settings.repo` and ReviewDO's `repo` setting are still written (at create, at a rename, and again at every catalog sync), only for the previous release to read after a rollback; nothing reads them ([rollout](../dev/rollout/2026-11-12-repo-identity-read-through.md)).
- **The repo's owner** is GitHub's. A trust decision takes it from the signed event it decides (`repository.owner`, in every event about a repo), or, with no event, from GitHub then (an import of issues, "Use the repo owner"). No copy decides anything: one kept from attach would leave the account a repo was transferred away from trusted ([the review gate](#the-review-gate), [triage](#triage)).
  - **Only for the bound repo.** An event's owner counts only when the event was routed by the repo's id read from GitHub (`bound: github`): one routed by its name alone (no id yet, or one learned from an event) may be another account's repo under that name now (a login taken over), and its owner is nobody's to trust. A read by name (an import, "Use the repo owner", Settings' display) is checked against the bound id, and refused (or shown as nobody) when GitHub's repo for the name is another.
  - **Shown** in Settings as GitHub answers, read through by the API, kept a minute per Worker instance (a failed read too), since the page polls.
  - **For a rollback,** ProjectDO's `repo_owner_*` columns are written at attach, at "Use the repo owner", and again at every sync from GitHub's last answer for a binding read from GitHub (DirectoryDO's owner and its kind), so a rolled-back release trusts the owner now, not the one at attach.
- **The binding** (below) is the app's own decision record: which repo id and installation the project acts for.

- **What's bound** (DirectoryDO's `projects`): the repo's GitHub id (`repo_id`), how it was learned (`github`, or `event` for a project from before ids were read) and when, the name GitHub last gave the repo when that isn't the project's (`renamed_to`), why the last read didn't bind it, the bound repo's owner and its kind as GitHub answered at the binding's last read (none for one learned from an event; a record of that read, shown to the operator, compared at a mismatch and copied for the previous release, never trusted), and the App installation's id (`installation_id`, from the App's own lookup of the repo's installation, [GitHub tokens](#github-tokens); nest's token answer in the fallback).
- **Events from the project's installation only.** The installation is a decision record, kept: GitHub signs every installation's events with the App's one secret, so a repo moved to another account where the App is installed would otherwise drive the project from there. Once a project's installation is stored, `/hooks/github` refuses an event whose `installation.id` is another, or that names none: it acts on nothing and notes nothing (no rename), and answers why. Each refusal is counted on the binding (which installation, how many, when), and the Admin page shows it ("Events refused").
  - **It follows GitHub's answer** (2026-11-12; the App's own lookup since B1): an event refused for naming another installation has the binding read again (at most once a minute per project, `INSTALLATION_CHECK_EVERY_MS`), and the binding takes the App's installation on the repo as GitHub answers it now, looked up afresh ([GitHub tokens](#github-tokens)); if that's the event's, the event is routed again and acts. GitHub's lookup decides which installation is the repo's, never the event. A sync reads again every binding with refusals, too.
  - **At once after a reinstall** (since B1): the lookup is never a cached one, so the first event from the new installation is taken (its read finds it), and a token cached from the old installation is dropped with it. Before B1, nest's token reuse kept answering the old installation for about 50 minutes. In the fallback (`GITHUB_TOKEN_SOURCE=nest`) that window is back: press Re-read once it has passed.
  - **Only a lookup by the repo's own name** gives its installation: one by an old name (the App not reaching the new one yet), or by a name GitHub answers with another (`full_name`: the repo moved, no event naming the new name yet), may be another account's installation, and is never stored (`ownInstallation`, `src/github.ts`).
  - A project with none stored (bound before nest named it) takes events as before, from a repo owned by an account the app acts for ([repo authority](#repo-authority)), until a sync reads it: a sync reads every binding that has no installation yet. A nest that doesn't name it leaves the stored one as it is; another repo chosen at a re-read takes its own (none, when nest doesn't say).
- **Read from GitHub** (`GET /repos/{owner}/{repo}` with a metadata token of the App's, `src/binding.ts`):
  - **at attach,** so a new project is never without one;
  - **at every catalog sync,** for a project that has none, was bound from an event, has a rename noted or events refused (a sync runs at each project's creation and from the Admin page). One whose id matches is confirmed. One that doesn't is kept as it is, and its error says that events still go to the bound repo and what to check (renamed, transferred, or deleted and its name taken);
  - **by the operator's Re-read** (Admin page, `POST /api/admin/bindings/<project>`). It binds a project with no id and confirms one that matches. It never changes an id by itself: when GitHub's repo for the name is another, nothing is written and both are answered (name, id, owner, and whether GitHub's has the bound one's owner, as the binding last read it; unknown for one learned from an event). Only the operator's explicit choice binds that one (`POST …/<project>/bind {repo_id}`, behind a confirmation naming it), with the id they were shown: if GitHub's answer changed since, it's refused. It reads by the name GitHub last gave the repo, so an old name taken since by another repo isn't read.
  - An id learned from an event is recorded as `event` (with no owner), so the next sync reads it from GitHub.
  - A repo id another project holds is never bound: the binding says whose it is. A read that fails changes nothing.
  - **A binding not read from GitHub yet** (no id, or one learned from an event) is bound by a sync, an attach or a refused event's read only to a repo whose owner (by id) is the one recorded for it: the binding's last read's, else the owner ProjectDO recorded at attach. Another owner means the name may be another account's repo now (a login taken over): nothing is bound, the binding says why, and the operator's Re-read shows both repos to choose from (as for another id). With no owner recorded (an organization's repo from before ids were read), it binds as before.
- **Until it's read,** a project with no id is found by the name it was created with, and takes the id of the first event that names it.
- **A rename or transfer:**
  - An event routed by the id names the repo's new name: it's kept as `renamed_to`.
  - It's applied (the directory's guarded rename, which every reader reads through; then the catalog synced) by a sync or a Re-read, once the App reaches the new name ([repo authority](#repo-authority)). A sync reads the binding again first, so its owner and installation are GitHub's for the new name. Until then the project calls GitHub by the old name, which GitHub redirects (unverified for every call after a transfer, and for a token minted by the old name). Never onto a name another project has.
  - Agents running keep what they started with; new ones get the new name.
- **The Admin page** lists each binding (project, repo, id, installation, how it was learned, a rename not applied yet, why it didn't bind) with Re-read: a table from `sm`, a card per binding below it. Every problem a binding has is badged, the most urgent first: "Mismatch", "Events refused", "Not bound", "Rename pending". A failed re-read is said in its row, which offers Retry; a mismatch is badged "Mismatch" and shows both repos side by side (in columns from `sm`), with "Bind to this repo" as a quiet danger action: last in a card, after Re-read and set apart.

## Creating a project

The owner's request (2026-11-06), after the sweep (B10): a failure partway through creating a project mustn't leave one that answers 404, with its repo taken.

- **A recoverable sequence** (`src/creation.ts`, DirectoryDO):
  1. The directory row is created **pending**, holding the create's body.
  2. `finishProject` runs, and each of its steps is idempotent: the catalog sync (whose failure doesn't stop it), `ReviewDO.init`, then `ProjectDO.init`.
  3. The row is marked **ready**, and the project's first drain runs (its own alarm retries what fails there).
- **Pending.**
  - The project's routes answer 503 ("still being created").
  - The list shows it "Being created", with nothing to open.
  - GitHub's events for its repo reach nothing.
  - The same repo asked for again resumes it rather than being refused.
- **Resumed by the alarm.**
  - If the Worker's request fails or dies, DirectoryDO's alarm resumes the create: after a minute, then with backoff, as an outbox row (`src/outbox.ts`).
  - A create that can't be finished (8 attempts, a failure that will repeat, or a body that can't be read) is removed, and its repo is free again.
- **A project's object acts only once DirectoryDO lists it ready** (`settings.listed_ms`, asked until it does):
  - while the create is pending, its alarm checks again every 30 s and nothing is drained;
  - one removed (its `init` succeeded, the rest didn't) leaves its object inert, its settings gone: no attach, no manager.

**What the build settled** (2026-11-02):
- **Using nest's interface:**
  - **The cell goes where nest takes one:** in a create's body (`NEST_CELL`), and as a listing's filter. Nothing else sends it.
  - **The MCP capabilities name no `auth`:** nest sends no bearer, the grant covers no secret for them, and Nest-Identity is the only credential.
  - **The app's client id is its token's** (`nest_cli_<id>_…` → `cli_<id>`), the way nest itself reads it.
- **Agents:**
  - **Every agent gets a sandbox of its own,** made first (`POST /v1/sandboxes`) with the agent's labels, and ended with it (`stop {end: true, destroy_sandbox: true}`). An agent create nest refuses for good destroys the sandbox made for it (`Nest.startAgent`), so a refused start leaves nothing behind; not on a 409, whose key's earlier create may have landed (an agent may be using the sandbox). The manager has one too, to read the code it specs. The agent clones the repo itself.
  - **Repo access:** no template names a repo. Each start brings its project's GitHub access ([the sandboxes' GitHub access](#the-sandboxes-github-access)): the worker's pushes to its project's repo; the manager's and the reviewer's only read it, so their sandboxes' pushes and REST writes (comments, reviews) are refused and their token is only `contents: read`.
  - **Labels:** `project`, `role`, `task` for a worker, and `start`, the task's (or the manager's) start count. They find the app's agents again after a gap (`GET /v1/agents?label=…`).
  - **Creates are idempotent:** each start attempt sends `Idempotency-Key: <project>/<task or manager>/<start>/{sandbox,agent}` with its creates, so a retry after a lost answer gets the same sandbox and agent back. A key nest is still handling (a retryable 409) is retried like a 503; a key bound to another request (a 409 that isn't) is a refusal for good.
  - **First input:** the worker's brief (title, body, spec, repo, branch) and the manager's go to their inbox with a request id, so a retry posts once. A brief for a task any tainted session wrote is posted as relayed text (`from: "projects/board"`), so the worker's session is tainted too.
  - **Retries:** ProjectDO owes nest its manager, workers, stops and chat messages, each retried from its alarm (5 s doubling to 5 min); a retryable 503 or 409 is also retried within the call. A worker nest refuses for good (a 4xx other than a retryable one, a 408 or a 429) stalls its task with the reason; the manager is retried until it starts.
- **The board:**
  - **States** (`src/tasks.ts`; a task with a live worker may be re-specced, [below](#task-changes)): `draft` → `ready` (specced) → `assigned` → `in_progress` (worker started) → `in_review` (PR reported) → `done`, with `stalled` and `cancelled`. A task is assigned only once specced. The owner may mark done only a task with no open PR and no live worker (`draft`, `ready`, `stalled`; [the task machine](#the-task-machine)); a draft may be deleted (not while it holds an open PR), anything later is cancelled.
  - **A spec** is a goal, acceptance criteria, the files it likely touches and a test plan.
  - **`max_workers`** caps auto-assign and the manager's `assign_task`; the owner's assign by hand isn't capped (nest's `max_agents` still is). A worker counts from its assignment until it exits or the app has stopped it.
  - **History:** every change records who (the owner, the app, or an agent), what, when, and whether the session was tainted.
- **The MCP servers:** no sessions (no `Mcp-Session-Id`), JSON answers only. A worker's tools take no task id: its labels name its task. Every write is answered once per call key (`_meta["nest/call"]`) that begins with the caller's own id, kept 24 h. The reviewer's are in [the review pipeline](#built-the-review-pipeline).
- **Events:** deduplicated by id (DirectoryDO, 7 days) and idempotent besides. An event for an agent the app hasn't recorded is routed by that agent's labels (`GET /v1/agents/<id>`), only if the app is its client and owner; any other agent is remembered as not the app's and acknowledged. A failure answers 5xx, so nest delivers again.

## Built: the review pipeline

**Code:** `src/github-hook.ts` (`/hooks/github`), `src/github.ts` (the signature, the REST client, the branch-protection rules, the check's output), `src/do/review.ts` (ReviewDO), attaching in `src/do/project.ts`. Tests: `test/review.test.ts`, `test/attach.test.ts`, `test/github.test.ts`, against a fake GitHub in `test/fake-nest.ts`.

**What the build settled** (2026-11-02), against GitHub's docs for [webhook signatures](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), [events](https://docs.github.com/en/webhooks/webhook-events-and-payloads), [check runs](https://docs.github.com/en/rest/checks/runs) and [branch protection](https://docs.github.com/en/rest/branches/branch-protection):
- **The webhook:**
  - `X-Hub-Signature-256` is checked over the raw bytes in constant time: missing or wrong is `401`.
  - Deduplicated by `X-GitHub-Delivery` (DirectoryDO, 7 days); routed by `repository.id` to its project (`projectForRepo`), so a repo that's renamed or transferred keeps its project, and its old name, registered again by someone else, reaches no project. The id is read from GitHub ([the repo's binding](#the-repos-binding)); a project from before that is found by its name until it's read. A PR's head is the repo's own, not a fork's, by id too. An unknown repo, `ping` and other events are a `2xx`. The owner's PR comments: [below](#pr-comments).
  - It only records: ReviewDO and ProjectDO write one step each and arm their alarms, so it answers within GitHub's 10 s.
  - GitHub doesn't redeliver by itself (unverified: its docs offer manual redelivery only). A lost `pull_request` leaves the head without the check, which blocks merging until the next push or a redelivery.
- **The queue:**
  - One job per PR head. An event with an older `updated_at` than the PR's last is ignored, since deliveries aren't ordered. A head moving back to a reviewed commit, or a reopened PR, queues that commit again.
  - **`max_concurrent_reviews`**: per project, unset (no cap) by default, set with `PATCH /api/projects/:id/settings`. Jobs start from ReviewDO's alarm, oldest first, while running ones are fewer. A `PATCH` that changes it with other settings is all or nothing: ProjectDO's part first (its refusals come before it writes), then this.
  - **Retries:** every call to GitHub or nest is retried from the alarm (5 s doubling to 5 min). A refusal that will repeat fails the job with the reason, its check `action_required`. A check-run create whose answer was lost is found again by its `external_id`, not made twice.
  - **No room in nest** (the owner's direction, 2026-11-11: agents run on their own, and the owner is asked only for real decisions): nest refusing the reviewer because the app is at its grant's `max_agents` or `max_sandboxes` isn't a refusal that will repeat. The job waits, queued, as one over `max_concurrent_reviews` does, its slot freed, and starts once there's room: tried again 5 s doubling to 5 min (its own count, `room_waits`, apart from the job's step's errors, so once it starts a failed brief backs off from 5 s), never given up, and when one of the project's reviewers ends (stopped, or its exit), the oldest waiting job tries at once: only that one, since under `max_agents` each try makes a sandbox that nest's refusal of the agent then destroys. Its check stays `in_progress`, saying once that it waits for room ("Waiting for room to start a reviewer"), and says "Reviewing" again once its reviewer starts. Each try is a new start (`<start>` in its keys): what the refused one made, nest undid (`Nest.startAgent` destroys the sandbox made for an agent nest refuses). It was cleared to run (trusted, or approved), so waiting changes nothing of the review gate's: a held job never waits for room, and room freeing starts only queued jobs.
    - **A long wait is the owner's to see.** The grant's limits are per client, across every project, and a worker stays live until its PR merges, which needs its review: managers and workers can fill `max_agents` so that every review waits and no worker ever ends. So a job waiting 45 minutes (`ROOM_TELL_AFTER_MS`, from when this wait began) is recorded once among the project's errors (`review_waiting_for_room`), saying what's full and what the owner can do: raise the grant's `max_agents` or `max_sandboxes` (a real decision, theirs), or free a place (cancel a task whose worker can wait, stop a routine run). It's removed once the wait ends: the review starts, or the job ends otherwise (a newer head, the PR closed). ReviewDO tells the project from its drain, marking the tell before the call so a tell whose answer was lost is still cleared, and backs off (5 s doubling to 5 min, never given up) while the project can't be reached, its alarm never due at once for it.
    - **How it's told apart:** nest from nest#248 on answers it with its own code, `at_capacity` (429, retryable), for `max_agents`, `max_sandboxes` and a spawner's live children; `Nest.call` retries only a retryable 503 or 409 itself, so the 429 reaches the job, which waits. A nest from before #248 answers it as any refusal of the grant (403 `forbidden`, not retryable), told apart by ClientDO's words ("<client> has <n> live sandboxes, its grant's max_sandboxes"): that text match is the fallback for such a nest, removed a release after #248 (`atCapacity` in `src/nest.ts`). Any other refusal (another 403, a 4xx) still fails the job, its check `action_required`. A review's try at capacity is spent: the sandbox made for it goes (each try is a new start), whichever form nest answers in. A worker's start, which retries a transient refusal under the same keys, keeps its sandbox and gets it back by its key.
  - **Reviewers:** made as workers are (`Nest.startAgent`, `Idempotency-Key: <project>/review/<pr>/<sha>/<start>/{sandbox,agent}`), labelled `project`, `role=reviewer`, `pr`, `sha`, `start`, reading the repo but unable to push or write to it (the read token and guards, above), and ended with their sandboxes (`stop {end, destroy_sandbox}`) on a verdict, a newer head, a closed PR, an exit, or the run's deadline. Ephemeral: a reviewer ends itself once its turn is done, verdict or not (from the next catalog sync, which writes the template; until then the deadline covers it). Two more starts after one ends without a verdict.
  - **The job's states** are one table (`src/review-job.ts`): queued → running → done, failed, superseded or closed, and back to queued on a re-run or to wait for room in nest; and, for a PR the project doesn't trust, `held` or `overflow` → queued (approved) or `dismissed` ([the review gate](#the-review-gate)). Every change of a job's state goes through it, only from the state the row has (so an ended job never ends twice, and its check completes once). A running job always has a deadline (`REVIEW_DEADLINE_MS`, 60 minutes per reviewer): past it, the attempt is spent as an exit's is.
  - **The brief** has only what the app knows from GitHub's routing (repo, number, head, base), none of the PR's own text. `review_get` gives the title.
- **The check:** `nest-projects/review`, created `in_progress` at the head with `details_url` the project's board. On completion:
  - a verdict: `success` only if all three pass, else `failure`. The title names the failed dimensions, the summary is the reviewer's, the text holds each dimension's notes, the reviewer and whether its session was tainted. Clipped to GitHub's 65535 characters (the title to 255; GitHub documents no limit for it);
  - no verdict: `action_required` (above);
  - superseded or closed: `cancelled`.
- **The verdict** (`/mcp/review`): `review_get` and `submit_review {correctness, quality, architecture: {verdict: pass|fail, notes}, summary}`. The caller's `pr` and `sha` labels name its job; only that job's current reviewer may submit, once, while the job runs. A retry with the same call key gets the first answer. The taint is recorded with the verdict.
- **Attaching:**
  - **Required checks that exist** change only their lists (`PATCH …/required_status_checks`), and only when the check is missing or not yet pinned to the App; `strict` and everything else stay. A second attach writes nothing.
  - **A branch protected without required checks** gets its protection written back whole with them (`PUT`, from what `GET` answers). Required signatures aren't in that body (unverified that `PUT` leaves them).
  - **The App's id:** the check is required from the App (`checks: [{context, app_id}]`) from the first attach, so no other app or commit status can pass it. The id is the App's own (`GITHUB_APP_ID`, [GitHub tokens](#github-tokens)); in the fallback, the `app_id` of nest's token answer ([nest's GitHub tokens](../docs/control-plane/api/clients/#github-tokens)). If that has none (nest can't tell), the check is required from any source (`contexts`, or `checks` without `app_id` where other entries are pinned, which keeps their pins), and the first check run's `app.id` then pins it: the project attaches again. Another entry's `app_id: null` (any source) is sent back as `-1`, GitHub's "any app".
  - Rulesets aren't read or changed: a repo protected by rulesets alone gets branch protection besides.
- **Tasks and PRs:** a `pull_request` from the repo's own branch `task/<id>` (not a fork's) links the PR to its task (`pr_opened`) if the worker hadn't reported it. Merged, the task is `done` (through `pr_opened` first if it was still `in_progress`) and its worker ended.

## The review gate

**Code:** `src/review-trust.ts` (the decision, pure), ReviewDO's `held` and `overflow` states, `src/github-hook.ts`. Tests: `test/review-gate.test.ts`. Decided 2026-11-09.

A review starts an agent on the PR's code, on the owner's subscription and hosts, so on a public repo it starts by itself only for a PR the project trusts:
- **Trusted:** the head is a branch of the repo itself (not a fork: pushing there needs write access), and the author is, by `pull_request.user.id` of the signed webhook, the project's comments user ([PR comments](#pr-comments)), the repo's owner, or the App's own bot (workers' task PRs). Ids only, never logins.
  - **The repo's owner is the one the event names** (`repository.owner.id`, when its `type` is `User`; 2026-11-12, by the owner's principle in [the repo's binding](#the-repos-binding)), never a copy: once a repo is transferred, its events name the new owner, so the account it left is trusted no longer by having owned it. An organization owner trusts no one by ownership, and neither does an event routed by the repo's name alone (its binding not read from GitHub yet).
  - **The comments user is the owner's choice** and stays whatever happens to the repo. Its default at attach (the repo's owner then) is cleared when the repo's owner is another account ([PR comments](#pr-comments)), so a transfer leaves the account the repo left trusted by neither.
  - **The bot's id** is looked up (`GET /users/<app_slug>[bot]`, the slug from `GET /app` with the App's JWT, or nest's token answer in the fallback) whenever a bot's PR from the repo doesn't match the id kept in DirectoryDO (none yet, or a stale one), and kept. A lookup that fails holds that PR.
  - **Decided again at every PR event:** jobs waiting for approval whose author the project trusts by now (the bot's id learned, a comments user set) start then. Never a fork's.
- **Anything else is `held`:** a job in the table's `held` state, with a check completed as `action_required` ("Waiting for the owner's approval"). No reviewer, no sandbox, and none of the PR's text or diff reaches any agent. It shows in "Needs you" and on the Reviews page (pinned first) with **Review this PR** and **Dismiss** (`POST /api/projects/:id/reviews/:pr/:sha/approve` and `/dismiss`).
- **An approval is for one head commit and one run.** Approving queues that commit's review, if it is still the open PR's head. A push to the PR makes a new job, held again. A PR closed and reopened, or pushed away from and back to a commit, is held again, approved before or not. A dismissed job can still be approved.
- **GitHub's "Re-run"** of the check never starts a review of a head that needs approval and hasn't had it, whatever state its job is in (the job records `needs_approval`); it re-runs a review that was approved or needed none.
- **Bounded:**
  - at most 50 held jobs per project (`MAX_HELD`). A head past that waits as `overflow`: its check says the review queue is full, it isn't in "Needs you", the Reviews page lists it right after the held ones (approvable there), and it becomes held, the longest waiting first, as slots free (an approval, a dismissal, a close, a newer head);
  - at most 500 overflow jobs (`MAX_OVERFLOW`). A head past that gets no job and no check, so nothing can start its review; it is kept with its PR, "Needs you" says how many such PRs wait, and each gets its job (overflow, as untrusted as it was), the longest waiting first, as room frees;
  - at most one held check run per PR a minute (`HELD_CHECK_INTERVAL_MS`): a head pushed sooner gets its check when the minute is up, if it is still the head. A held job that is superseded or closed owes GitHub nothing more, so fast pushes cost one check-run create and one update a minute.
- **The check's order:** a held job's check is made before the job can start (ReviewDO's drains run one at a time), so after an approval the commit's latest check is the review's own; a held check whose job moved on while it was being made completes as `cancelled`.
- **The setting:** `untrusted_reviews`, `hold` (the default) or `review` (every PR is reviewed), in Settings ("Reviews": one switch, with what turning it off means) or `PATCH /api/projects/:id/settings`. It decides heads as they arrive: switching to `review` starts nothing that already waits (held, overflow or without a job: the owner approves or dismisses those, or a new push is reviewed), and switching back to `hold` stops nothing that runs.
- **Rollout:** expand-only (five columns on ReviewDO's `jobs`, five on `prs`). A project whose repo an organization owns and that has no comments user trusts only the App's bot, so its people's PRs are held until a comments user is set.
- **Rollback:** the previous release has no row for `held` or `overflow` in its job table (`review-job.ts`). It reviews new PRs unasked again and leaves such jobs alone (it starts only `queued` ones). GitHub's "Re-run" of such a job's check throws there (the delivery fails, nothing starts), and its Reviews page can't show them. Redeploying this release picks them up as they were.

## Auto-merge

The owner's request (2026-11-02): "Auto-merge should be an option in the project, which writes back to the repo settings."

- **The settings:** `auto_merge` (default off) and `merge_method` (`squash`, the default, `merge` or `rebase`), set at create or with `PATCH /api/projects/:id/settings`.
- **The repo's "Allow auto-merge":**
  - Turning `auto_merge` on writes `allow_auto_merge: true` to the repo; turning it off writes `false`. The write is `PATCH /repos/{o}/{r}`, from ProjectDO's alarm, retried from 5 s doubling to 5 min.
  - A refusal that will repeat is shown (`repo_auto_merge.state: error`), with the setting kept as asked. `POST /api/projects/:id/auto-merge/retry` writes it again.
  - Looking at the project (`GET /api/projects/:id`) reads the repo's value again, at most once a minute, from the alarm. A value that differs from the setting is shown as `drifted` (changed by hand on GitHub), and the same retry writes it back. A repo whose setting the app never wrote isn't watched.
- **Per PR:**
  - While `auto_merge` is on, a task's PR gets GitHub's auto-merge when it opens or reopens, with the project's merge method. The app uses GraphQL `enablePullRequestAutoMerge` with the PR's `node_id` from the webhook.
  - Only a task's own PR counts: one from the repo's own branch `task/<id>`. Other PRs, and forks' branches with that name, are left alone.
  - Turning `auto_merge` on enables it on the task PRs already open, and turning it off disables it on them (`disablePullRequestAutoMerge`).
  - A PR's auto-merge waits until the repo allows it.
  - The task records each change (`auto_merge_enabled`, `auto_merge_disabled`, `auto_merge_failed` with GitHub's reason) and shows it in its drawer. GitHub's GraphQL `errors` are refusals for good, except its rate limit.
  - Changing `merge_method` applies to PRs opened after the change.
- **Merging stays GitHub's,** gated by the required `nest-projects/review` check and the branch's other rules. GitHub's auto-merge merges "after all required reviews and status checks pass" ([GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request)). A PR that could merge at once has no auto-merge to enable; GitHub refuses it, and that's recorded.
- **Each call's token:**

| Call | Permissions | Source |
|---|---|---|
| `PATCH /repos/{o}/{r}` (`allow_auto_merge`) | `administration: write` | [Permissions required for GitHub Apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps) ("Administration": `PATCH /repos/{owner}/{repo}`, write) |
| `GET /repos/{o}/{r}` (reading `allow_auto_merge`) | `metadata: read`, `contents: write` | the same page ("Metadata": `GET /repos/{owner}/{repo}`, read), and [Get a repository](https://docs.github.com/en/rest/repos/repos#get-a-repository): "To view merge-related settings, you must have the contents:read and contents:write permissions" |
| GraphQL `enablePullRequestAutoMerge`, `disablePullRequestAutoMerge` | `pull_requests: write`, `contents: write` | GitHub's [GraphQL reference](https://docs.github.com/en/graphql/reference/pulls) names none (unverified). [Auto-merge](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request) needs "write permissions to a repository". The merge it arms is Contents: write (`PUT …/pulls/{n}/merge`, same permissions page), and it changes the PR |

## Blocked

The owner's request (2026-11-02): "Agents might mark their tasks as blocked, which should bubble up to me."

- **A flag, not a state.** A blocked task keeps its state, its worker and its PR, and goes on from there once unblocked. A state would need a way back to wherever it was, and an `in_review` task blocked on a question still has its PR open and under review. The rules are pure, in `src/tasks.ts` (`canBlock`, `canUnblock`):
  - the manager may block any task that isn't over (`block_task` on `/mcp/board`); a worker only its own, while its worker is live (`report_blocked` on `/mcp/task`, which takes no task id, and the task's assignee must be the caller);
  - a blocked task isn't blocked again (clear it first). A task that ends (`done`, `cancelled`) drops its block, and auto-assign skips a blocked `ready` task.
- **What it carries:** who blocked it, their role, when, the reason, an optional question for the owner, and whether the session was tainted.
- **Unblocking:**
  - **The owner answers** (`POST /api/projects/:id/tasks/:task/answer {answer}`). The answer goes to the blocking agent's inbox, and to the manager's too when a worker blocked it. Those messages carry the owner's words and the task's id only, nothing an agent wrote, so they're never relayed.
  - **The manager** (`unblock_task`) **or the task's worker** (`clear_blocked`) clears it when it's resolved another way.
- **The manager is told** when a worker blocks, with the reason and the question. That text is relayed (`from: "projects/board"`) when the worker's session was tainted, as a brief from a tainted spec is.
- **Delivery:** messages to agents' inboxes are owed in ProjectDO's `messages` table, posted once each (a request id) from the alarm, retried from 5 s doubling to 5 min, and kept with the reason when nest refuses for good.
- **"Needs you"** is one area at the top of the board: open asks ([below](#asks)) and blocked tasks together, oldest first (`GET /api/projects/:id/attention`). Each shows who, why, how long ago, and its answer (approve or deny, or words). It is calm: the surface with a warning rule down its left edge and a warning icon by its title, not a tinted fill.
- **The count:** `GET /api/projects` gives each project `needs_you`: the number of items "Needs you" lists (`attentionOf` in `src/api.ts` makes both), so the projects list, the sidebar's badge and the panel agree. Triage and the review backlog are one item each, however many issues, proposals or PRs they hold.

## Asks

The owner's direction (2026-11-11): "eliminate any duplicate data which can become out of date". The app used to copy each `agent.ask` event into ProjectDO's `asks` table and mark a row answered only when the owner answered through the app. Answered anywhere else (the operator through nest's API, another path), or with its agent ended, the row stayed in "Needs you".
- **nest's record is the only one read.** "Needs you" (and, from the same read, the board's "Needs input" badges) reads the project's agents' open asks from nest whenever it's read: `GET /v1/asks?label=project=<id>` ([open asks across agents](../docs/control-plane/api/#open-asks-across-agents)), all its pages, and the whole list (`GET /v1/agents/<id>/asks`) of any agent a page names in `more` (a page shows 20 an agent). An ask answered anywhere, or whose agent ended (nest lists live agents only), is gone at the next read.
- **Whose:** only agents the app made itself (owner and client both the app, as the webhook routes events): an agent one of its agents spawned sets its children's labels. Role and task are the agent's labels (`role`, `task`). A manager's ask from one that isn't the project's manager now (a replaced one whose stop nest refused) is labelled "The previous manager".
- **nest not answering (or not configured) hides nothing else:** "Needs you" still lists the app's own items (blocked tasks, secret requests, triage, held reviews) and says the agents' asks couldn't be read (an `asks_unavailable` item, never counted); the next poll tries again. The projects list's count is then unknown (`needs_you: null`): "Couldn't check what needs you" there, and "?" on the sidebar's Board row. `GET /api/projects/:id/asks` alone answers 502. Every call to nest is abandoned after 15 s (`CALL_TIMEOUT_MS`).
- **What it costs:** one open board or Manager page reads nest once every 5 s (`GET /api/projects/:id/attention`, which the board's badges share), and the sidebar's projects list once every 10 s for every project together (`GET /v1/asks` over all the app's live agents, counted by their `project` label). Each `GET /v1/asks` page is one call per live agent inside nest (up to 100 a page). An agent with more than 20 open asks adds one call.
- **On the page:** "Needs you" shows the app's own items at once (`GET …/attention?local=1`, no nest read) until the first full read arrives; meanwhile it says "Reading the agents' asks…" and its count is "?". With none of its own items it shows that only when the sidebar's count (the projects list's, which includes the asks) says more waits, after 300 ms. On a cold load (a reload, a link), the board page is one loading state until the tasks and the first full read are in, for up to 1 s (`COLD_BUDGET_MS`); past that it shows with the panel saying the asks are being read, so the board doesn't jump when nest answers late. If the first full read fails, or nest can't be read, it says the asks couldn't be read, count "?": the app's own items are never presented as all that waits. The Manager page's context column says the same, never "Nothing waits on you." while the asks are unknown. A poll that fails after a good read keeps that read and says so ("Couldn't refresh; showing what was read at 1:47:05 AM"), its count "?" as the sidebar's, and a projects list that fails to refresh shows its counts as unknown ("?", on the Board row and the projects list), not the old numbers; the projects page keeps its cards with the same "Couldn't refresh" line, and the sidebar says the projects couldn't be loaded only when there's no list at all. An answer's buttons stay focusable while it's out (`aria-disabled`, not `disabled`); when an item leaves, focus moves to the next item's first control; when the last one does, the panel goes, focus moves to the board's "Tasks" heading, and a polite live region says "Answered; nothing else waits on you." A heading focus is moved to gets the theme's ring. An ask refused as no longer open leaves a calm note where it was, naming it ("Already answered: the call to WebFetch was answered elsewhere, or its agent ended."), not a failure; the note goes at the next poll or when focus moves on, and a panel holding only a note has no warning tone and no count.
- **Answering** (`POST /api/projects/:id/asks/:ask/answer`) finds the ask among the project's open ones first, so another project's ask, or one no longer open, is refused (409) without asking nest; then it goes to nest. Only an answer that reached the ask (nest's `delivered` isn't `already_answered`) counts as the owner's reply for the manager's `await_reply` ([waiting](#waiting)). The page reads the asks again either way, so a refused one leaves at once.
- **One release back:** a control plane from before `GET /v1/asks` answers it 401 (a client's unknown route); the app then lists the agents by label and reads each one's `GET /v1/agents/<id>/asks`.
- **The `asks` table (expand/contract):** each `agent.ask` event is still written there, and an answer through the app marks its row, as the release before reads them; nothing here reads it. So a rollback lists asks raised meanwhile. Asks answered elsewhere, or whose agent ended, aren't marked, so a rolled-back app may show them as open (answering one then finds nest's `already_answered`). A later release removes the writes and the table.

## Task changes

The owner's request (2026-11-02): "Workers should be notified when their assigned task is modified."

- **What's told:** a new title, body or spec, its block cleared by the owner (answering it) or the manager, PRs attached or detached ([PRs](#prs)), and its dependencies added, removed or done ([dependencies](#dependencies)). What's wrong with its PR is told separately ([PR upkeep](#pr-upkeep)). It doesn't matter whether the owner made the change (the API), the manager (`/mcp/board`) or the app.
  - The worker's own changes aren't told back, nor is a block it raised and the owner answered: that answer reached it already.
  - Cancelling stops the worker.
  - A task with a live worker (`assigned`, `in_progress`, or `in_review` while its worker lives) may be re-specced, so the spec can change under a worker (`spec` loops on those states in `src/tasks.ts`).
- **A reorder isn't told:** board order is priority among tasks not yet started, and a worker already on its task has nothing to do with that.
- **To whom:** only a live worker (the task's assignee, still live). A task without one tells nobody, since a worker started later gets the task as it is in its brief.
- **How:**
  - Each change is noted in ProjectDO (`task_changes`) and told within 10 s (`NOTIFY_WINDOW_MS`) from the alarm. Changes in that window go out as one message.
  - The message names the fields, gives each field's first before and last after (title and body clipped to 600 characters), the whole new spec, and asks the worker to re-read the task with `get_task`.
  - A set is frozen on its first try and posted with the request id `<task>/changes/<last change>`, so a retry after a lost answer posts once. A change after that try is the next message.
  - A set with any change from a tainted session is posted as relayed text (`from: "projects/board"`), as the brief is.
  - Each set is recorded in the task's history (`worker_notified`, or `worker_not_notified` when the worker had gone or nest refused).

## PRs

The owner's request (2026-11-03): "PRs should be attachable to tasks."

- **A relation, not one field.** A task has any number of PRs (ProjectDO's `task_prs`), and a PR belongs to one task at a time. `Task.pr` is the first attached PR (a migration made each task's single `pr` that, with its auto-merge); `Task.prs` lists them all.
- **Attaching:**
  - **the owner**, from the task's drawer: one of the repo's open PRs (`GET /api/projects/:id/prs/open`), or a number, `#n`, or the PR's URL (`POST /api/projects/:id/tasks/:task/prs`);
  - **the manager**, with `attach_pr` on `/mcp/board`;
  - **its worker's own PR** still attaches itself, by `report_pr` or by its branch `task/<id>`.

  The owner's and the manager's are checked on GitHub with a `pull_requests: read` token: the PR is in the repo and open, and GitHub says whether it's from a fork. A task in progress goes to review; a task that's over takes no PR.
- **One task per PR:** attaching a PR that's attached to another task is refused, naming that task: detach it there first. A branch `task/<id>` never moves a PR attached elsewhere; it's noted on the task it names. Moving it silently would take a PR from a task someone chose.
- **Detaching** (`DELETE …/prs/<n>`, or `detach_pr`) works on an open PR only, since a merged one stays as the record. A detached PR's auto-merge is turned off.
- **Done:** a task is done once at least one PR is attached and every attached one has merged (`prsDone` in `src/tasks.ts`). Merging one of several leaves it in review. A PR closed without merging is detached with a note, and the task is done if the rest have merged; the last open one leaving with none merged takes the task out of review ([the task machine](#the-task-machine)). A merge moves any task that isn't over, since a PR may be attached to a task with no worker. A ready or stalled task may hold an open PR; it isn't marked done by hand while it does.
- **Review and auto-merge:** every PR is reviewed already. With auto-merge on, every attached PR gets it: the owner's, the manager's, the worker's or the branch's, but only once GitHub has said it's from the repo itself and given its node id. A fork's PR never gets it, and neither does one whose head repo GitHub no longer names.
- **The live worker is told** when PRs are attached or detached ([task changes](#task-changes)), and when its PR fails review, has a failing check or conflicts with its base ([PR upkeep](#pr-upkeep)).
- **GitHub's order, not its delivery's** (B7). GitHub doesn't order its deliveries, so ProjectDO keeps each PR's latest `updated_at`, whether attached or not (`pr_facts`).
  - An `opened` or `closed` older than what's recorded is stale, and ignored.
  - Within the same second (GitHub's resolution), the actions' own order decides: an `opened` can't follow a close, a `reopened` can, and a close follows either.
  - A merged PR's `closed` arriving before its `opened` therefore leaves the late `opened` attaching nothing.
  - An attach is refused for a PR GitHub has said is closed, which covers an attach that raced its merge. The owner's attach records what its own read of GitHub said, so a reopened PR attaches.

## PR comments

The owner's request (2026-11-06): their comments on a task's PR reach that task's worker.

- **Events** (`/hooks/github`, the same signature check). Each delivery is claimed by its `X-GitHub-Delivery` before it's handled, in one step, so concurrent copies act once. The claim is confirmed when handling succeeds; one never confirmed (its handler died) lapses after 5 minutes, so a redelivery is handled:
  - `issue_comment` `created` on a PR (`issue.pull_request` present);
  - `pull_request_review` `submitted`, with text or requesting changes;
  - `pull_request_review_comment` `created`.

  An edit, a delete, an approval with no text, or a comment on an issue that isn't a PR is ignored.
- **Only the project's GitHub user** (Settings, "PR comments"), matched by GitHub user **id**, which is immutable. A login can be renamed and then registered by someone else; an id can't.
  - **The default** is the repo's owner, if a user, applied once at attach (a one-off migration attaches every already-attached project again, for it). After that, the owner's choice stands, nobody included, however often the repo is attached again, or transferred.
  - **A default isn't a choice** (2026-11-12, the owner's decision on the security review of the repo's owner): it's marked as one (`comments_default_id`, the id it defaulted to; projects from before count theirs as the default when it's the owner recorded at attach, or the owner DirectoryDO recorded at the binding's last read, since a re-attach on the previous release may have moved the first). When the repo's owner is another account (an event routed by the bound id names it, or a re-read, a sync or an attach reads it), a defaulted comments user is cleared to nobody, and "Needs you" says so ("… owns the repo now, so … is no longer the PR comments user", then what that means), with **Choose someone…** (Settings' PR comments, focused) and **Leave it unset** (`POST /api/projects/:id/comments-cleared/dismiss`), listed only while nobody is set. The new owner is never taken by itself. A comments user the owner set (a login, or "Use the repo owner") is never cleared.
  - **Settings** shows whose comments count ("last seen as" its login), takes a GitHub login (looked up with `GET /users/{login}`, kept as its id; an organization or a bot is refused), offers "Use the repo owner" (taken on the server as the bound repo's owner GitHub names at save, by id, never by a login it once had; refused while the binding isn't read from GitHub, or when GitHub's repo for the name is another), and warns about the account's credentials. An organization's repo has nobody until it's set.
  - With nobody set, a comment on a task's PR is noted on the task (at most once an hour), so the owner's comment isn't lost silently.
  - **The author must be a person writing as themself:** `user.type` is `User`, and `performed_via_github_app` is unset. An App acting with the user's token is refused, even though GitHub calls its comments the user's.
  - Everyone else is ignored, bots included, and so is the app's own reviewer, which posts as its App.
  - **Anything that holds a credential of that GitHub account** (a token in an agent's sandbox, a CI secret) can comment as it, and those comments count. So keep the account's tokens out of agents and CI, and use the App's brokered tokens there.
- **The PR's task:**
  - For the two review events, it's the head branch `task/<id>` of the repo itself, never a fork's, as for `pull_request`.
  - `issue_comment` names no head, so it's the task the PR is (or was) attached to, from its branch or the owner's attach. A fork's PR is never a task's.
  - A PR no task holds is ignored.
- **The message** (`prCommentMessage`) says it's a PR comment from the owner, and gives the kind, the author, the PR, the file and line for a review comment, and the link. Each of these is cut to one line, so a crafted file path can't add lines to the frame. The text comes between rules, cut at 4,000 characters with a pointer to the link.
- **Relayed, so the worker's session is tainted** (nest's rule for webhook input). A comment could be written by anything holding the user's credential, and a tainted worker is held to what tainted sessions may do. Workers with hands are tainted already, so it costs nothing today.
- **Delivery:**
  - **A worker that has started** (brief delivered: in progress or in review) gets it in its inbox through the app's outbox (`messages`, retried).
  - **A worker that's starting** (assigned, its brief not yet delivered) gets it after its brief, in order (`pr_inputs`), never ahead of it.
  - **No worker running**, with the task open (in review, stalled or ready): a worker is started again (`revise`: back to `assigned`), the comment after its brief.
    - Started from the alarm, not on the webhook's request.
    - Held to the task's dependencies, as any assign is, and to 3 restarts per task an hour (each refusal recorded).
    - Not held to `max_workers`: the owner's explicit comment, as with the owner's own assign.
  - **A merged PR, a closed or detached one, or a task that's over:** the comment is dropped and recorded on the task (`pr_comment_dropped`, with why). A comment after the work is over is the owner's to raise with the manager in chat; sending it on would restart work no one asked to restart.
  - Comments still queued are dropped (recorded) when the task ends, its worker's start fails, or the worker exits before its brief: never kept for a later worker.
- Each delivery is recorded on the task (`pr_comment`, `revise`).
- **Once per comment** (B6), by its own key (its kind and URL, `comments_seen`, kept 30 days). It's claimed where it's decided to act on it (deliver, queue, restart, or drop it on the record), in that step.
  - A delivery handled again acts once: its claim was released after a later step failed, or lapsed, or it came under a new delivery id. So it never sends twice, queues twice, or starts a second worker.
  - One with no task yet (its PR's `opened` not seen) isn't claimed, so its redelivery after can act.
- **Events are routed by `repository.id`,** read from GitHub ([the repo's binding](#the-repos-binding)), never taken by name from an event.

## PR upkeep

The owner's direction (2026-11-11): "Agents should manage their PRs to merge, including rebasing on conflict." Agents run on their own, and the owner is asked only for real decisions; the app keeps no copy of GitHub's or nest's state that can go stale, and reads through instead (events are only nudges).

- **The worker owns its PR until it merges.** Its prompt (`PROMPTS.worker`) says so, and that when told its PR failed review, has failing checks or conflicts with its base, it fixes it and pushes: it addresses the reviewer's findings (saying in the PR why where one is wrong), fixes CI, and brings the branch up to date with the base. It never blocks on, or asks the owner about, routine PR upkeep.
- **Rebase, force-pushed with a lease, on the task's own branch only** (decided 2026-11-11). nest's push guards scope a push by repo only ([GitHub guards](../docs/sandbox/networking/egress/policy/README.md#github), `control-plane/src/lib/rules/github.ts`): they see neither the ref nor whether it's a fast-forward, so a worker may force-push its own `task/<task-id>` branch. The app's branch protection covers only the default branch.
  - **Its own branch** (the PR's head is `task/<task-id>` on the repo itself, as the read says): the message gives numbered steps, each sha written out in full, since shell variables don't last from one of the worker's commands to the next (each Bash call is a new shell, and a rebase stopped on conflicts spans several). (1) Push its own unpushed commits plainly (refused because the branch moved: `git pull --rebase` onto it, finished with `git rebase --continue` if it stops on conflicts, and pushed, before step 2: `checkout -B` would otherwise drop the resolution and leave the rebase in progress). (2) `git fetch origin` and `git rev-parse origin/task/<id>`: that sha is the lease. (3) `git checkout -B task/<id> <lease>`: the branch exactly as pushed, so a commit someone else pushed (a suggestion committed on GitHub, "Update branch", the owner's own fix) is kept. (4) `git -c rerere.enabled=true rebase origin/<base>` (and `rebase --continue` the same way: rerere for those commands only, never kept in the clone), resolve, test. (5) `git push --force-with-lease=refs/heads/task/<id>:<lease> origin HEAD:refs/heads/task/<id>`: an explicit lease on exactly that sha, by an explicit refspec. A plain `--force-with-lease` after a fetch would protect nothing: the fetch moves the remote-tracking ref it compares against.
    - **Refused because the branch moved:** back to step 2. Step 3 throws the refused rebase away and starts from what's pushed now; rebasing the rebased branch onto the pushed one instead would replay the base's own commits onto it. rerere replays the resolutions. Never plain `--force`. A repo's own rules refusing any force-push (a ruleset on `task/*`) get a merge instead, from the branch as pushed, not the refused rebase (merging into that would find nothing to merge, and its push would be refused): `git checkout -B task/<id> <lease>`, `git merge --no-edit origin/<base>`, a plain push. The branch stays a plain diff against the base as it is, for the reviewer and the owner. A task PR is squash-merged either way.
    - **Checked by hand** (2026-11-12) against a local bare repo, each step its own shell: the owner pushing to the branch before step 1 and again between the fetch and the push; the first push was refused, the second attempt from step 2 went through, and the branch held every commit (the worker's, both of the owner's), the base's once, and the resolution. Also: step 1's `pull --rebase` stopping on a conflict, finished and pushed first; and a repo refusing non-fast-forward pushes, merged from the branch as pushed and pushed plainly. Another branch's pulls are `git pull --no-rebase --no-edit` (a plain `git pull` on divergent branches is refused by current git, 2.47 here).
  - **Any other attached PR** (one the owner or the manager attached from another branch, or a fork's named like the task's): never forced and never rebased. The message says to push the worker's own unpushed commits on it first (its next step resets the local copy to what's pushed), then merge the base in and push plainly to that branch, named: a plain push can't drop anyone's commits, and the branch is someone else's to rewrite. Told rather than left alone, because the task's done only once every attached PR merges, and its worker owns that.
  - **What the guards leave exposed,** since force-pushing is routine: anything with push access to the repo (every worker's sandbox) can push or force-push every branch the repo doesn't protect, other workers' `task/*` branches and the owner's own branches among them. Only the prompt and the message hold a worker to its own branch, and only the default branch is protected by the app. Ref-aware push guards (a sandbox pushing only to refs it's granted) would be the kernel's generic fix ([open question](../docs/sandbox/networking/egress/policy/README.md#open-questions)).
- **What it's told,** in one message per PR per read, relayed (`from`), recorded on the task (`pr_upkeep`):
  - **(a) the review failed:** the app's verdict on that head commit (ReviewDO's job, `verdictsAt`), with the reviewer's findings framed as data, never instructions, between `BEGIN FINDINGS <nonce>` and `END FINDINGS <nonce>`, a random marker per message that their text can't know (so no dash line, Unicode dash or zero-width trick closes the frame), cut at 6,000 characters. The worker is tainted already (it read the repo); relaying keeps it so for nest's rule. A review that ended without a verdict tells nothing: it's no finding to fix.
  - **(b) another check failed** on the head: any check run with `FAILURE`, `TIMED_OUT` or `STARTUP_FAILURE`, other than the review check (that's (a)), named with its link, each cut to one line (the names are the repo's CI's). Not `ACTION_REQUIRED` (a person's to act on, as the review gate's held check is), `CANCELLED` (usually a superseded run), `NEUTRAL`, `SKIPPED` or `STALE`. Told at the first failure on a head; checks failing later on that head aren't told separately (the worker reads them with `gh pr checks`).
  - **(c) it conflicts with its base:** GitHub's `mergeable: CONFLICTING`. GitHub computes it lazily: `UNKNOWN` (null in REST) until a background job has run, which the read starts ([GitHub](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)); it tells nothing, and the next read sees the answer. `BEHIND` (out of date, but merging cleanly) isn't told: it matters only to a branch protection with `strict`, which the app doesn't set, and every push to the base would otherwise set every worker rebasing.
- **How often:** each condition once per worker per head commit, and again every 3 hours (`PR_RETELL_MS`) while it still holds at that head, saying it's told again: a message lost or ignored doesn't strand the PR. A condition a read sees not to hold at that head is marked cleared, so one that returns there (a Re-run that fails again) is told as news, but no sooner than 30 minutes (`PR_FLAP_MS`) after its last telling: a flapping check isn't told at every failure. A conflict GitHub is recomputing (`UNKNOWN`, after a push to the base) is neither held nor cleared. Nothing is told while the task is blocked: its worker waits on the owner (a CI secret, say), and being told of its PR would push it to work around the block; it's told once the block clears.
- **To whom:** the live worker of the task the PR is attached to, past its brief (in progress or in review) and not blocked, for an open PR from the repo itself (the app's record and GitHub's `isCrossRepository`, read each time). Who owns which PR is read again after the read's awaits, so a worker that went meanwhile is told nothing. A worker that exited is told nothing, and its successor starts with its brief; a dead worker's PR waits for the owner or the manager.
- **Read through, never stored** (`src/pr-read.ts`): one GraphQL query per 25 PRs, by number (`pullRequest(number:)` aliases, the numbers as variables), answering each PR's state, title, head, base, `isCrossRepository`, `mergeable`, `mergeStateStatus`, auto-merge, and its head commit's check runs (each suite's latest per name, `checkType: LATEST`). A number GitHub has no PR for is null (its `NOT_FOUND`); any other error fails the read. Commit statuses aren't read (that would need `statuses: read`, which the grant doesn't name); GitHub Actions reports check runs. The app keeps its own copies of a PR's state, title and auto-merge (`task_prs.state`, `title`, `am_status`) besides; the read's answer could replace them.
- **The only state kept:** `pr_told (agent, pr, head, cond, at_ms, cleared)`, that this worker was told of that condition at that head, when, and whether a read has seen it not hold since (pruned after 30 days). Besides it, the read's schedule (`settings.pr_read_next_ms`, `pr_read_last_ms`, `pr_read_attempts`), which copies nothing of GitHub's.
- **When it reads** (ProjectDO's alarm): only while a live worker owns an open PR (no alarm is set for it otherwise); at once when that starts, then every minute (`PR_READ_EVERY_MS`). Nudges bring it forward, never closer than 30 s to the last read (`PR_READ_GAP_MS`), and only for a PR a live worker owns: a review of it that ends with `failure` (ReviewDO's word to the project), and a `check_run` `completed` webhook with a failing conclusion naming it (if GitHub sends those to the App for other apps' check runs: unverified). A push to the base sends no PR event, so a conflict is found by the minute's read. Each decision is the read's, never an event's.
- **A failed read** is tried again a minute on, backed off past that from the fifth failure in a row (to 5 minutes); nudges don't bring it forward while reads fail. GraphQL errors that are GitHub's own trouble (its timeout, `INTERNAL`, `SERVICE_UNAVAILABLE`, `TIMEOUT`; types as GitHub answers them, unverified as a list) and its rate limit are retried as transient; any other is a refusal. One that will repeat (a permission the grant lacks, the App gone) is among the project's errors (`pr_read_failed`), once a day.
- **Cost.** At most 120 reads an hour per project (one a minute, and nudged ones never within 30 s of the last), and none while no worker owns a PR. A read is one query per 25 owned PRs; a query cost 1 point for a few PRs and 6 for 25, measured against this repo (2026-11-12). So a project spends at most 120 points an hour on it with a few owned PRs, and at most 720 with 25 (another 720 per further 25). GitHub's GraphQL budget is per App installation, not per project: 5,000 points an hour, more for an installation on an organization with many repos or users, up to 12,500 ([GitHub](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api#primary-rate-limit)). It's shared with every project on that installation and everything else using its tokens (the reviewers' and workers' own `gh` among them), and apart from the REST budget. Its token is the App's own, reused while it has 10 minutes left ([GitHub tokens](#github-tokens)).

## Triage

The owner's request (2026-11-06): GitHub issues on a project's repo go into a triage queue, and accepted ones are added to the board.

- **Whose issues come in** (the owner's question, 2026-11-10: "Only my issues or comments trigger triage, right?"): by default only issues opened by the comments user or the repo's owner, by the issue's author (`issue.user.id`, never the event's sender), the same people a declined issue's reopening counts from. Others are ignored, not stored.
  - **The repo's owner** is the one the event names (`repository.owner`, a user; only for an event routed by the bound id), and for an import the one GitHub answers then for the bound repo (none while the binding isn't read from GitHub; refused when GitHub's repo for the name is another): never a copy kept from attach, so after a transfer the account the repo left counts no longer ([the repo's binding](#the-repos-binding), 2026-11-12).
  - **The setting:** `issues_from`, `trusted` (the default, "You only") or `anyone`, in Settings ("Triage", beside PR comments and Reviews: "Issues from") or `PATCH /api/projects/<id>/settings`. A project that wants outside reports opts in.
  - **Named:** "You only" names who that is, from the saved settings ("You only (by77er)", "(alice and by77er)"), and so does the Triage page's caption. On an organization's repo with no comments user set, no one counts (the owner is the org, which can't open issues): Settings says "No one yet: set the PR comments user, or choose Anyone.", and so does the Triage page.
  - **At most 200 wait** (`MAX_UNTRIAGED_ISSUES`, `src/issues.ts`), whichever the setting. Past it a new issue is dropped and counted (`issues_dropped` in the project's settings, with when the last was); the Triage page says how many were left out and what to do (accept or decline some, then Import open issues). An import counts afresh.
  - **Issues already waiting** from authors the setting now leaves out stay, until the owner accepts or declines them: nothing is removed by the rule.
- **Intake** (`/hooks/github`, the same signature check, delivery claim and repo → project routing), for issues the rule above lets in:
  - `issues` `opened` and `reopened` add an issue, or restore one that went, when the event shows it open (a late delivery for an issue closed since adds nothing).
  - A declined issue comes back only when reopened by the comments user or the repo's owner (the event's `sender`, by id), so its author can't undo a decline by closing and reopening it.
  - `edited` updates one still untriaged (or adds it, open, if its opening was missed).
  - `closed`, `deleted` and `transferred` take an untriaged one out.
  - An accepted issue is its task's from then on, and none of these change it.
  - A PR (GitHub sends a PR's issue as an issue) is ignored. Another repo's issue, a fork's included, reaches no project.
- **Anyone can file, so its text is data:**
  - The title and body are kept (300 and 20,000 characters, the rest at its link).
  - They're shown as plain text, never rendered as markup.
  - Accept carries the issue's `updated_ms` as the owner read it; an issue edited since is refused (`409`), and the page shows the new text and asks again. What becomes the task is what the owner read.
  - No agent reads them before the owner accepts the issue.
- **The Triage page** (after Board) lists the untriaged issues, oldest first, with title, number, author, age, the body as text (its first five lines, with "Show more" for the rest in place) and the link.
  - **Accept** makes a draft task: the issue's title, and its body plus a line linking back (`From issue #n: <url> (opened by <author>)`). The owner or the manager specs it, as any draft.
    - The task records its issue.
    - It's marked tainted (an `issue_accepted` record), since its text is anyone's. The manager's and its workers' sessions that read it are then tainted, as nest's rule has it.
  - **Decline** takes it out, with an optional reason. It doesn't touch GitHub: closing there is the owner's call.
  - **Import open issues** is a one-off that brings in the repo's open issues the app doesn't know yet (it reads the oldest 300 open items, and PRs, which GitHub lists among issues, count toward the 300 before they're left out). It needs `issues: read`. Issues opened before the app subscribed come in only this way: events GitHub sent before it was ignored and aren't replayed. It follows the same rule as an event (whose issues, and the cap), and says how many it left out: `{imported, known, ignored, dropped}`.
- **Routines' proposed tasks wait here too** ([routines](#routines)): under the issues, in their own section ("Proposed tasks", the Routines page's list: accept as a draft, or decline), shown only while there are some. They stay on the Routines page as well. With proposals waiting and no issues, the issues' section says "No issues to triage." in one quiet line; the page's empty state ("Nothing to triage") shows only when both are empty.
- **"Needs you"** shows one item for what waits for triage, linking to Triage: the issues and the proposed tasks, counted in words ("3 issues and 1 proposed task wait for triage"), as old as the oldest of them. The projects list's count includes each issue and each proposal. Accepting or declining either refreshes both.
- **A task made of an issue, done through a merged PR,** closes the issue: a comment "Done in #<pr>.", then closed as completed (`issue_closes`, from the alarm).
  - It needs Issues: write on the App's installation (in the fallback, `issues: write` in the client's grant).
  - A refusal that will repeat (no permission, the issue gone) is recorded on the task (`issue_close_failed`) and shown in its drawer, with **Retry closing the issue** (`POST /api/projects/<id>/tasks/<task>/issue/close`). In the fallback it's also tried again by itself when a read of the grant (`GET /v1/clients/self`) shows its `issues` permission changed to `write` or `admin`; with the App's tokens, the owner's Retry follows a permission granted to the App. Anything else is retried with backoff.
  - The comment is posted once: not again on a retry after it landed, nor when it landed and its answer was lost (the issue's comments since the close was owed are checked for the line first).
  - A task's message to its worker is relayed (`from`) whenever the task was ever tainted, whoever made the change.

## Routines

The owner's request (2026-11-06): "schedule periodic background tasks for things like spontaneous reviews and memory consolidation (dreaming)… on a timer or on some other condition, like 'n tasks completed', and have the ability to create tasks."

- **A routine** (`src/routines.ts`, pure; ProjectDO's `routines` and `routine_runs`): a name, a kind (`review`, `dreaming`, `custom`), the owner's prompt, enabled, its triggers, a cooldown, a time and turn budget, and where its proposals go. Nothing of it is in nest: nest sees only the agents it starts.
- **Triggers,** any of which fires it:
  - a timer: an interval of 15 minutes to 7 days, or a daily or weekly time in an IANA time zone (DST handled; a time skipped forward lands after the skip). Missed fires aren't caught up;
  - counters: N tasks reached `done`, or N task PRs merged (a task's own PR only), since its last run. The board keeps two totals (`tasks_done_total`, `prs_merged_total`, moved where a task becomes done and where a task PR merges); a routine keeps the totals at its last run, or at its enabling, so a long pause doesn't fire it at once.
  - "Run now", the owner's.
- **Starting** (`startVerdict`), decided in one synchronous step in ProjectDO (its alarm, or the step that moved a counter): a fired trigger makes the routine due (a second trigger while it's due is the same run). A due routine starts a run only if none of its own runs is live (one at a time), past its cooldown from its last start ("Run now" skips the cooldown, not the rest), and while the project's live runs are fewer than `max_routine_runs` (Settings, 1 to 3, default 1). Otherwise it waits, shown as `running`, `cooldown` or `cap`, and a run's end ticks again.
- **A run** is one agent, started as workers are (`Nest.startAgent`, `Idempotency-Key: <project>/routine/<run>/{sandbox,agent}`), labelled `project`, `role=routine`, `routine`, `run`:
  - the `projects/routine` template: ephemeral (nest ends it once its turn is done), no secrets of the owner's, no egress beyond nest's and the repo's, no timers, no spawning; each run's sandbox gets the read token's access ([the sandboxes' GitHub access](#the-sandboxes-github-access)): it reads the repo, never pushes;
  - a **dreaming** run uses `projects/dreaming` instead: no hands at all (no sandbox, no repo, no web), since the board, recent work, memory and transcripts are all it reads;
  - its brief: why it runs (the trigger and count), when the last run started, where its proposals go, whether it may read transcripts, and the owner's prompt. App-authored and the owner's, so not relayed;
  - **cost guards:** stopped (`stop {end, destroy_sandbox}`) when its time budget (`max_minutes`, 5 to 120, from its first start attempt) runs out (`timed_out`), or once its turns reach `max_turns` (1 to 20), each turn counted once by its event id (`run_turns`), so a redelivered event isn't a second turn. An exit with no turn counted waits a minute (`RUN_EXIT_GRACE_MS`) for that turn's event before the run fails, since nest's events aren't ordered. A start retried 8 times, or refused for good, fails the run; a run that ends while starting with no agent recorded (its answers lost, or the owner's stop meanwhile) has what its attempts made found by its labels (`project`, `role`, `run`), each agent stopped with its sandbox and any sandbox left destroyed, twice;
  - **its record:** the trigger, its state and outcome (`done`, `failed`, `timed_out`, `stopped`), its agent (its trace is viewable, as any agent's), its turns, its last turn's text as its report, and what it made (proposals, draft tasks, memory notes written or deleted).
- **Its tools** (`/mcp/routine`): `list_tasks`, `get_task`, `recent_activity` (task PRs merged, tasks done, reviews and their verdicts, the owner's PR comments relayed, for up to 30 days), `manager_chat`, `propose_task`, and the memory tools. Nothing that assigns, starts or changes a task.
- **Proposals:** `propose_task` puts a task into the triage queue (`proposals`, `GET /api/projects/:id/proposals`), marked with its routine and run; the owner accepts it (a draft task, recorded tainted: `proposal_accepted`) or declines it. A routine may instead be set to put them on the board as drafts (unassigned; a draft is never auto-assigned). At most 5 per run, and 50 pending across the project either way (untriaged, or drafts a routine proposed not yet specced, cancelled or deleted). A title the owner declined in the last 30 days (compared without case, punctuation or spacing) is refused, by any routine, and the run is told the owner's reason (rather than listing declines in its brief: the refusal holds whatever the run reads).
- **Taint:** a run has hands, so nest taints its session; the app records every write of a run as tainted whatever the session says (its proposals, its tasks, its notes), since it reads anyone's text (the repo, PRs, comments, reviews).
- **The API:** `GET`/`POST /api/projects/:id/routines` (a body of every field, or `{preset}`), `GET`/`PATCH`/`DELETE …/routines/:routine` (a routine with a live run isn't deleted), `POST …/routines/:routine/run`, `GET …/routines/:routine/runs`, `GET …/routine-runs`, `POST …/routine-runs/:run/stop`, `POST …/proposals/:proposal/{accept,decline}`.
- **Transcripts:** a dreaming run is spawned with nest's own transcript grant ([grants to its agents](../docs/control-plane/api/clients/#grants-to-its-agents): `grants: [{action: read_transcript, resource: "agent{project=<id>}", limits: {max_age_ms, max_entries: 200}, expires_ms}]` at `POST /v1/agents`). It reads the project's agents' transcripts back to its last run (a week for the first, 30 days at most), until its deadline (a grant can't be revoked on its own, so it expires with the run), with nest's `list` and `read_transcript`, which taint it. The app never reads or proxies a transcript. `routineSpawnExtras` is the one place it's made. It's kept with the run, with the run's template and brief, all frozen at its first start attempt, so a retry sends the same requests however the routine was edited meanwhile. Other kinds get none.

- **The Routines page** (`src/ui/features/routines/`, after Reviews in the sidebar), top to bottom:
  - **Routines,** as Panels: the name, a status badge only when there's something to say (Starting, Running, Queued, Cooling down, Off), the triggers in words ("Mondays at 09:00 (Europe/London) · Every 5 task PRs merged"), the next timer, the counters' progress ("3 of 5 PRs merged"), the last run and its outcome, and why a queued one waits. Edit and Run now at the top right. "Add routine" offers the two presets (one click, each once) and a custom one.
  - **The editor,** a Sheet: name, kind, instructions; when it runs (a timer, the two counters; empty is off); limits; where proposed tasks go. Checked with the Worker's schema before it's sent; its refusal is shown in the form. Delete is last, set apart, confirmed, and refused while a run is going.
  - **Proposed tasks** waiting for the owner, under a caption saying they come from what agents read: title; "Tainted", which explains itself on hover, focus or tap ("Written by an agent that read untrusted text…"); its routine, run and when; the body as plain text (never rendered), its first 5 lines or 400 characters with "Show more", as Triage shows an issue (the first 10 proposals, then "Show all"); "Accept as draft" at the left and Decline (an optional reason, confirmed) at the right edge, as on Triage.
  - **Runs,** newest first, the latest 10 then "Show older": routine, why, state, what it made, started, took; opened, why it ended, its report (plain text), what it made, Stop while live (confirmed), and its agent's trace (`RunTrace`, the shared viewer). A card per run below `sm`, its "Show details" the card's full width.
  - **Memory:** the latest 10 notes, then "Show all", and a filter by key or text once there are more; each note's key, its text (first lines, "Show more"), who wrote it ("the manager", "the routine Dreaming (run …)") and when, and "Tainted" on one a tainted session wrote; Delete, confirmed. Read-only otherwise for now.
- **Proposals wait for the owner** in "Needs you" and on the Triage page too ([triage](#triage)).
- **Not yet:** editing a note.

### Presets

Enabled with one click (`POST …/routines {preset}`), then edited like any routine (times in UTC until edited):
- **Spontaneous review:** every 5 task PRs merged, or weekly (Monday 09:00); 6 h cooldown, 30 min. Reviews what merged to the default branch since its last run for bugs, risks and smells, and proposes tasks.
- **Dreaming:** nightly (03:00), or every 10 tasks done; 12 h cooldown, 20 min. Consolidates memory: merges duplicates, rewrites stale notes, prunes, and folds in lessons from recent tasks, reviews, PR comments and the manager chat; may propose tasks.

## Memory

- **Notes** (`src/memory.ts`; ProjectDO's `memory`): a key (lowercase words joined by `-`, `.` or `_`), text (at most 2,000 characters), when it was last written, its source (`manager`, or `routine:<name> (<run>)`) and that write's taint. At most 100 per project: a write past that is refused until notes are merged or deleted.
- **Provenance:** a tainted session (every routine run, and any manager session nest has tainted) can't change or delete a note an untainted session wrote: refused, with the note kept as it was. It may write its own note under another key. So text a run read from anyone can't replace what came from a clean session; dreaming writes beside such a note and says why.
- **Who:** the manager reads and writes it (`memory_list`, `memory_get`, `memory_write`, `memory_delete` on `/mcp/board`; its prompt says to read it at the start and before it specs); a worker reads it (`memory_list`, `memory_get`); routine runs read and write it; a reviewer gets none. The owner reads it and deletes notes (`GET /api/projects/:id/memory`, `DELETE …/memory/:key`).
- **Why the app's own store:** nest's `memory` capability is per agent and not built (its tools answer `not_implemented`), and nest has no channel primitive yet. A project's memory is shared by its agents and outlives each one, so it's the project's state, like the board. If nest gains a shared keyed store an app can grant its agents, this moves there.

## Dependencies

The owner's request (2026-11-03): "Tasks should be able to block other tasks."

- **"Waiting on", a relation** (ProjectDO's `task_deps`): a task waits on others (`blocked_by`), and is waited on by others (`blocks`). This is distinct from "Blocked" ([above](#blocked)), the flag an agent raises for the owner, which is a "Needs you" item. A dependency is the board's own ordering, and nothing waits on the owner.
- **Valid** (`dependencyError` in `src/tasks.ts`, pure): within the project only, never on itself, never for a task that's over (it waits on nothing), never twice, and never closing a cycle, which is refused with the cycle's path (`tsk_a → tsk_b → tsk_a`).
- **Assignment:** a task waiting on any task not `done` can't be assigned, whether automatically, by the manager or by the owner. The refusal names the blockers and their states. **There is no override:** the owner removes the dependency instead, which says what changed and keeps the board's record honest.
- **Becoming assignable:** when its last blocker is done, the task can be assigned, and auto-assign takes it. **A cancelled blocker still holds it:** the work it waited on won't happen, so whether to go on without it is the owner's or the manager's call, made by removing the dependency.
- **Who:** the owner from the drawer (`POST /api/projects/:id/tasks/:task/dependencies {blocked_by}`, `DELETE …/dependencies/<task>`), and the manager with `add_dependency` and `remove_dependency`. A worker's `get_task` lists what its task waits on, with each one's state.
- **A live worker** on a task whose dependencies change (added or removed mid-flight, or one done) is told ([task changes](#task-changes)).
- **On the board:** a card says "Waiting on N", neutral (gray, light), since it's no one's to act on now. Hovering or focusing it lists the blockers. The drawer has a Dependencies section: what it waits on, each removable, a task picker (the switcher) to add one, and what waits on it.

## Waiting

The owner's request (2026-11-02): the manager "should be able to set timers and await things with a timeout".

- **Waits are the app's** (`src/waits.ts`, ProjectDO's `waits`): `await_task {task, states, timeout_s}`, `await_pr {pr, until: merged | review_done | closed, timeout_s}` and `await_reply {timeout_s}` on `/mcp/board`, with `list_waits` and `cancel_wait`.
  - **Why the app owns the timeout** (an alarm on the wait's deadline) rather than a nest timer: the condition and the timeout are then decided in one place, ProjectDO, in one synchronous step each, so a wait resolves exactly once and a timeout can never fire after its condition (or the other way round). A nest timer would race the app's message across two systems, and nest gives a client no way to set one (only to list and cancel); the manager setting it would mean two tool calls and a timer name to keep straight.
  - **The condition is watched where it changes:** a task's state (every move goes through one place), a PR's `closed` event (any PR of the repo, a task's or not), a review's end (ReviewDO's outbox of finished reviews, told to ProjectDO from its alarm, retried until taken), and the owner's chat message or answer in "Needs you".
  - **Resolving:** in the step that saw it, the wait's row changes only while it's pending (`rowsWritten`), and only then is the manager owed one inbox message (`await aw_…: task tsk_…: now in_review.`; `… ended without its condition …`; `… timed out after 2 h, still waiting for #12 to merge.`). App-authored, with ids and states only, so nothing relayed.
  - **At once:** a task already in a wanted state answers `met` (no wait left behind); a PR whose review already ended, or which a task records as merged, resolves right after it's recorded.
  - **Durable and deduplicated:** a pending wait for the same condition is the same wait (a partial unique index on its key). At most 32 pending. A wait on a task ends when the task ends (or is deleted) without reaching its states.
  - Timeouts are 10 s to 30 days, as nest's timers.
- **The manager's own timers:** its template names nest's `timers` capability (`timer_set`, `timer_cancel`, `timer_list`), for a wake-up at a time of its own ("check again in two hours"); a fired timer is an inbox message. Workers and reviewers don't get it: a worker's whole job is its task, which brings everything it waits on, and a reviewer reviews once. The prompt says how to wait: call an await (or set a timer), end the turn, and be woken by whichever comes first.
- **The Manager page's context column** lists the pending waits under "Waiting for", between "Working on" and "Needs you", soonest deadline first (`ManagerWaits`):
  - "Add search by tag to be In review or Done · 45 min left", "#118 to merge · 2 h left", "The owner's reply · 26 h left".
  - A task shows by its title, as a link to its drawer; its states use the board's labels; a PR shows by its number, as a link to it on GitHub.
  - What resolved in the last half hour follows: "#119 merged · met 3 minutes ago", and a timeout ("The owner's reply · timed out 10 minutes ago") in the warning tone.
  - While the manager isn't running (ended or errored) nothing is waited for: the pending waits aren't listed or counted, and one line says "Nothing pending while the manager isn't running." (the page's header says why and offers Restart; the composer says nothing of a reply either). The waits themselves are kept, and show again once a manager runs. What resolved lately still shows.
  - Nothing shows when there's neither. ui-review's `waits` check fails on a raw task id or snake_case state in it, on the section missing where the column shows and the fixture has waits, and on a task or PR line that isn't a link.
- **A condition that holds already** answers at once with no wait left behind and no message, for `await_pr` as for `await_task`: a message would wake the manager, which might ask again. If a second identical call found that wait pending meanwhile (while the first read the review queue) and was told "waiting", the wait is resolved instead, with the one message that caller waits for.
- **Resolved waits** beyond the 10 the API's `recent` returns are pruned as new ones resolve.

## Network

The owner's request (2026-11-02): "I should be able to modify the default network policy of workers and the manager."

- **The Network page** (between Secrets and Settings in the sidebar), on the frame like Settings: its intro at the reading measure, the two roles' Panels side by side (one column below `lg`) with Save under them, then the operator's policy and the live agents in a row of their own: per role (workers, the manager), the hosts its sandboxes may reach on top of the operator's policy, each with optional ports (default 80 and 443). Presets: npm, Node downloads, PyPI, crates.io, Go modules, Docker Hub, GitHub releases; or a custom host. Reviewers get none: they read the repo, which the operator's policy already reaches.
- **Within the grant:** each host must be inside the client's `egress_hosts` (`GET /v1/clients/self`). It's checked as it's added and again by the API (`PUT /api/projects/:id/network`): a 403 for a host newly added outside it ("isn't in this app's grant; the operator must add it"), a 400 for a malformed one.
  - **Narrowing:** a host saved before the operator narrowed the grant isn't refused. It stays in the rules, marked "Outside the grant now: kept, not applied", and it's left out of what's applied: the sandbox create, and each live layer, filtered by the grant read then. So a save that only removes or keeps rules always goes through, and a narrowing reaches the sandboxes (nest refuses a layer with any host outside the grant).
  - **The editor:**
    - A refused save shows why under Save and marks the host's row in the danger shade, with no notification; after a save, "Saved · reaching live agents".
    - A rule nest's defaults already cover says so, and a line near the top says what the default allows.
    - Removing a host by keyboard leaves focus on the next row's Remove (or the previous one's, then the Add select).
    - A failed live layer's error links to the rule it names: the row is focused, its tint flashed once.
    - The picker has its own row; a custom host's Host, Ports (its placeholder "Blank: 80, 443") and Add share one from `sm` up, their labels level.
    - ui-review's `network` checks fail on focus that isn't the next row's Remove in the same panel, on a refused save without its inline reason or marked row, and on a narrowed grant's kept host unmarked (`network-narrowed`); the selftest plants each case. nest checks once more on every write. The page shows the ceiling, and the operator's rules read-only, from the manager's sandbox's effective policy (`GET /v1/sandboxes/<id>/policy`, which a client may read for its own sandboxes), by each rule's [`source`](../docs/sandbox/networking/egress/policy/#sources): nest's defaults (`base`), the operator's (`operator`) and those from its repo allowlists (`repos`, only for an agent started on nest's repos). The app's own (`client`) are the role editors', and grants (`grant`) are left out; the GitHub hosts the app adds for every sandbox ([the sandboxes' GitHub access](#the-sandboxes-github-access)) are among the app's own, not the editors'. A control plane without `source` falls back to `layer` less the app's own rules (`GET …/client-policy`); that goes once every control plane answers `source`.
- **New agents** get their role's rules in their sandbox's create (`POST /v1/sandboxes {egress}`). A start attempt's rules are frozen at its first try (`frozen_egress`), since its sandbox's `Idempotency-Key` binds the request; a sandbox made with older rules is brought up to date at once.
- **Live agents** (the manager, each live worker) get them through their sandbox's client layer, which nest replaces whole. **`clientLayerFor(rules, role, feeds, current)`** (`src/network.ts`) is the one place that builds it: this role's rules, the app's GitHub part (its binding, variables and hosts, for a sandbox started with it), and each other part (injection bindings, env) from its feed, else as the sandbox has it now (read first; a binding nest answers as held, with its `client` and `placeholder`, goes back in the PUT's strict shape, `name`, `secret`, `hosts`, `locations`, `wildcard`). So a network change never drops a secret's binding: the [Secrets](#secrets) page feeds its bindings and env into the same function. A change to either bumps one revision (`network_rev`), so each live agent has one status for both. Each live agent's layer shows as applied, pending (retried from the alarm) or failed (a refusal that will repeat: shown, not retried), polled while any is pending.

## Built-in tools

The owner's decision (2026-11-11): agents' web access is autonomous, and so is every built-in a role launches.

- **Every role** runs the Claude Code built-ins it launches without asking: the task tools (`TaskCreate`, `TaskGet`, `TaskUpdate`, `TaskList`) for every role, dreaming included, and `WebSearch` and `WebFetch` on any URL for every role with hands (manager, worker, reviewer, routine). The worker's `Agent` is allowed by nest's `subagents` capability.
- **How:** nest's runner asks for a call no rule matches, and a template has no rules, so each role's capability (`projects/{board,task,review,routine}`) carries an `allow` rule for each of those six tools by exact name, with no URL pattern (`BUILTIN_RULES`, `src/catalog.ts`). nest joins a spec's capabilities' rules in their order, first match wins. `projects/routine`'s reach the dreaming template too, which launches the task tools but neither web tool.
- **The accepted risk:** neither web tool is governed by the sandbox's egress policy (the [Network page](#network) doesn't apply). `WebFetch` runs on the brain's host, and brain hosts reach any address on 443 today. `WebSearch` runs as Anthropic's server-side search tool (unverified), so its queries leave through Anthropic. A prompt-injected agent (by the repo, a PR, an issue or a page it fetched) could put what it has read, a private repo's code included, into a URL it fetches or a query it searches. The owner accepts this.
- **Running agents too:** the rules reach nest at the next catalog sync (the Admin page's **Sync catalog**, or a project's creation), and nest reads an agent's rules from its capabilities as they are now ([live rules](../docs/control-plane/durable-objects/catalog/#live-rules)), so running agents stop asking at the sync. An agent started before nest read rules live keeps its old rules until it's replaced, or until the operator clears them (`DELETE /v1/agents/<id>/rules`).
- **The grant:** nest doesn't check a client capability's `rules` against its grant: rules only decide whether a call an agent's spec already gives waits for an approval, which the client answers for its own agents. Its capabilities' rules reach only its own subtree's agents live ([the client's catalog](../docs/control-plane/api/clients/#the-clients-catalog)).

## Secrets

The owner's rule (2026-11-02): credentials never enter sandboxes. What an agent sends itself gets its credential injected at nest's egress proxy; CI/CD secrets are the owner's to add, and agents ask for them. Built on nest's secrets and injection ([API clients](../docs/control-plane/api/clients/), its Secrets, Injection and Workflow files sections, from nest PR #125).

- **Values go to nest at once:** the Worker sends a value straight to `PUT /v1/clients/self/secrets/<name>` and never hands it to a Durable Object. (The project's own GitHub tokens are the app's, not the owner's: [the sandboxes' GitHub access](#the-sandboxes-github-access).) No table, log, answer or brief holds one; a test reads every object's tables and every answer the board reads to check. The app keeps only each secret's metadata in ProjectDO: name, variable, description, hosts, how it's sent, roles, size, and times. Last injected comes from nest's listing.
- **Names:** project-local, `[a-z][a-z0-9_]{0,30}`, which is also the binding's name. nest's name is project-scoped and new at each creation (`<project id>-<name>-<generation>`, hidden from the page): two projects' `npm_token`s are two secrets, and a secret deleted and made again under its name is another, so a binding a sandbox still holds from before never reaches the new value. A new secret's name is minted for its first write and usable once, and a replacement goes under the row's own name (taking no new place in `max_count`), so a write racing a delete can't record the deleted generation again (409).
- **Each secret makes, on the sandboxes of its roles,** a binding (at most 16 per role, the first by name) and an environment variable holding its placeholder (`CLOUDFLARE_API_TOKEN=nest-ph.<client id>.cloudflare_token.`), so an agent's tools find it where they expect ([environment](../docs/control-plane/api/clients/#environment), nest PR #134). `secretFeeds` (`src/secrets.ts`) builds both.
- **New agents** get them in their sandbox's create (`POST /v1/sandboxes {inject, env}`). The role templates declare none, so no superset-and-narrow is needed. A start attempt's spec is frozen with its Idempotency-Key, so a retry sends the same request even after the secrets changed; a change since is owed to its layer once the agent is live.
- **Live agents** (the manager, each live worker, and each reviewer until ReviewDO stops it) get a change at once, through their sandbox's client layer: the feeds go into `clientLayerFor` with the role's network rules ([Network](#network); reviewers have none), so a secrets change keeps the rules and a network change keeps the secrets. Adding, deleting, or changing a secret's hosts, format, variable or roles owes the layer to each live agent of the roles it was or is for; a new value or description changes no layer (nest pushes values to the proxies, within its 15-minute refresh). The page lists each live agent's layer as applied, pending or failed, with the variables it has.
- **Fail closed, and revocations first:** a layer (and a create) is built only from what's inside the grant as it is now: a host outside `inject_hosts` is left out, a secret with none left is too, and the page marks it "Outside the grant". So nest never refuses a layer for one narrowed secret and holds back another's removal. A refusal (403) is tried once more against the grant read again, since it may have narrowed meanwhile. If nest still refuses, or the grant can't be read, what the change removes is applied on its own (`shrinkLayer`: the current layer less what the new one drops; with the grant unread, built from every secret, so only the owner's removal goes), and the agent shows failed or pending. A save is refused (503) when the grant can't be read.
- **Rotating to cut someone off:** a new value goes to every agent the secret is bound to, including one whose revocation hasn't applied yet. So remove its role first, wait for its layer to show Applied, then set the new value.
- **Upkeep,** every 10 minutes while the project has secrets: the grant is read, and a change in its hosts since last seen owes every live layer, so a secret left out comes back by itself once the grant is widened. And the sweep: a nest secret of the project's that no row names (a write whose cleanup failed, which counts against `max_count`) is deleted once 5 minutes old; one minted for a write in flight is kept.
- **The brief** names each variable, what it's for, its hosts and how it's sent, and says the owner may add or remove some while the agent runs. Never a placeholder or a value: the variables carry the placeholders.
- **Checked as nest will check:** the name (not `gh_push` or `gh_read`, the app's own GitHub bindings); the variable (`[A-Z_][A-Z0-9_]{0,63}`, not one nest or the guest sets, such as `PATH`, `GITHUB_TOKEN`, the proxy and CA variables or `NEST_*`, nor `GH_TOKEN`, `GIT_CONFIG*`, `GIT_ASKPASS`, `GH_ENTERPRISE_TOKEN` or `GITHUB_ENTERPRISE_TOKEN`, which would take over the sandbox's GitHub token ([the sandboxes' GitHub access](#the-sandboxes-github-access)), and not another secret's); 1 to 16 hosts (a `*.` host needs two labels), 1 to 3 locations (a header must be a token, not a reserved one), at least one role, and the value's size. Also against the grant from `GET /v1/clients/self`: a host outside `inject_hosts` is refused with "the operator must widen the grant's inject_hosts", and `max_count` and `max_bytes` are shown and enforced. The page shows the grant's hosts and how many of its secrets the app's projects use, saying each project's GitHub tokens take 2 of them.
- **Requests:** `request_secret {name, purpose, kind, hosts?}` on `/mcp/task` and `/mcp/board` makes a "Needs you" item. It never carries a value.
  - **`ci`** (a GitHub Actions secret) links to the repo's environments, with a warning: add it to an environment with required reviewers, never as a repository secret, which any workflow in the repo reads (one a worker pushes too). The owner marks it added.
  - **`injected`** opens the Secrets form, prefilled with its name and hosts. Saving a secret of that name finishes it.
  - Either way, the requesting agent is told: for `injected`, its variable, and that it arrives in a moment (not at all if its role wasn't given it). Asking for one that exists answers only what that agent has, never the roles it isn't given to.
  - A tainted session's request is marked Tainted, with a caution: its purpose may be an instruction planted in what the agent read.
- **The prompts:** never ask for a secret's value, nor write one into a file, a commit or a log. A placeholder isn't a secret. Ask with `request_secret`.
- **"Workers may change CI workflows"** (Settings; off by default): when on, the project's push token carries `workflows: write` (the GitHub App's installation must grant it; nest's grant isn't asked, and turning it on isn't refused), so workers' pushes may change `.github/workflows/`; turning it on or off writes the token again at once, and off revokes every one that had it ([the sandboxes' GitHub access](#the-sandboxes-github-access)). For a start frozen before B3 (nest's repos), the old way: its sandbox create carries `github_push: {workflows: true}`, and a change, either way, reaches live workers through their sandbox's client layer (`github_push` in `PUT …/client-policy`, nest #157), fed into `clientLayerFor` beside the rules, secrets and env, with the same refusal handling: turning it off is a removal, so it goes through even when nest refuses the rest (`shrinkLayer`). Within the grant as read at each apply: a narrowed `github_push.workflows` takes it from live workers started on nest's repos at the next upkeep (the project's push token isn't bounded by the grant's `github_push`: the App's installation decides). To a control plane from before #157 (its `GET` answers no `github_push`), the layer goes without it. Settings lists each live worker's layer, applied, pending or failed, and whether its pushes may change workflows. The manager and reviewers never get it. For workers on nest's repos only, it needs the grant's `github_push.workflows` (left out of their layer without it). The security note says that a pushed workflow runs with the repo's Actions secrets before review, so CI secrets belong in an [environment with required reviewers](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment). Turning it off abandons each start in flight that was frozen with it for a new attempt without it (its Idempotency-Key binds the old request, so it can't be resent without it), and destroys what the old attempt made, found by its labels (`project`, `role`, `task`, `start`) through `GET /v1/agents` and `GET /v1/sandboxes`, `POST /v1/agents/<id>/stop` and `DELETE /v1/sandboxes/<id>`: looked for twice, the second time after nest's idempotency lease, so a create still landing is caught.
- **The Secrets page** (between Routines and Network):
  - under the title, that values are write-only and agents see only a placeholder;
  - a table of name and variable, description, hosts, how it's sent, roles, updated and last injected; below `sm` a card per secret instead, its Edit and Delete in it;
  - adding and editing in a Sheet: a service preset (Cloudflare API, npm, PyPI upload, GitHub API with a note that every sandbox already has the app's token for the repo, or custom), the variable (the preset's, such as `CLOUDFLARE_API_TOKEN`, else the name upper-cased, until typed in; GitHub's has no preset variable, since `GH_TOKEN` is the app's own), the value masked and write-once (an edit replaces it only through "Set a new value"), the hosts, the format and the roles (workers by default);
  - the live agents' layers (reviewers' too), as on the Network page (one list, `LiveAgents`), with the variables each has;
  - deleting is confirmed, naming who loses it and when.

### The manager chat

`src/ui/features/chat/` (the model in `model.ts`, pure), styled by `layout/ChatLog.tsx`. The bar is Claude.ai's and Linear's.

### The live trace

**Built (2026-11-02):** an agent's turns as they happen, from nest's live trace ([API](../docs/control-plane/api/), "Live trace"). Code: `src/trace.ts` (the route) and `src/ui/features/trace/` (the viewer, self-contained). Tests: `test/trace.test.ts` (the route, against a WebSocket in the fake nest) and `src/ui/features/trace/trace.test.tsx`.
- **The route:** `GET /api/agents/<id>/trace?after=<seq>`, behind Access like the rest of `/api/`. Only an agent DirectoryDO recorded for one of the app's projects (its manager, a worker, a reviewer, a routine run); any other id is `404` before nest is asked. Then it opens the upgrade to nest with the client token (`fetch` with `Upgrade: websocket` and `Authorization`, nothing of the browser's forwarded) and returns nest's socket as its own `101`. Workers proxy a WebSocket that way ([Response](https://developers.cloudflare.com/workers/runtime-apis/response/): "This establishes a WebSocket connection proxied through a Worker"), so the app holds no state for it and the token never reaches the browser. nest's retryable `503` (minutes after its deploy) stays a `503`; its `404` is a `404`; any other refusal is a `502` with nest's message.
- **The history route:** `GET /api/agents/<id>/trace/history?before=<cursor>&limit=<n>`, behind Access, for the same agents as the trace (404 before nest is asked otherwise), proxying nest's [trace history](../docs/control-plane/api/) (its stored transcript) with the client token. nest's `400` and its retryable `503` pass on; its `404` is a `404`; anything else a `502`.
- **The viewer** (`TraceView`, and one mount per place: `ManagerTrace` on the Manager page's "Trace" tab, `TaskTraces` for a task's worker in its drawer, `ReviewTrace` for each review job's reviewer, `RunTrace` for each routine run), a terminal transcript as Claude Code prints one (2026-11-02, the owner's):
  - **The terminal** (the `Terminal`, `TermLine` and `TermRule` primitives): the `terminal` surface with a hairline, the mono family throughout, long lines wrapped (`pre-wrap`, breaking anywhere: no sideways scroll), code keeping its spacing, and every line text, so it selects and copies.
  - **Its lines:** each turn under a quiet rule (its start time, its input's kind, how it ended, its tokens); the assistant's text after `●`; a tool call as `● Name(argument)` (an MCP tool by its own name, the main argument's first line), a disclosure whose region holds the full input; its result on the next line after `⎿`, the first 3 lines then `… +N lines (expand)`; a running call's `○`; states, asks, rate limits and exits as dim one-liners (`·`, `?`). An error is the danger role's text shade and `✗`, on the result and on the call's bullet. The glyphs are pinned by codepoint (U+25CF, U+25CB, U+23BF, U+2717, U+00B7): none has an emoji presentation, so none renders as an emoji (U+23FA would). `●`, `○`, `✗` and `⎿` are drawn in CSS at the font's stem weight (`Terminal.module.css`): JetBrains Mono's subsets lack all four (and DejaVu Sans Mono and Noto Sans Symbols 2 lack `⎿`), so the character stays in the text and the shape is what shows, the same on every system (unverified in the owner's browser). That covers a table, raw HTML, an image, math, a footnote, a reference link and its definition, a link the renderer won't follow, a fence with an info string beyond its language, and a list holding any of these. It shows as its Markdown source, edited in place like code, under a caption saying why ("The editor can't show this (a table); edit its Markdown here"), and it's written back as it stands.

    - Literal text is escaped where Markdown would read it as something else: a line starting `1. `, `- `, `+ `, `#`, a `---` or `===` line, a table's delimiter row, or a heading's trailing `#`s. Tiptap escapes the inline marks itself.

## Retention

Terminal rows of history-like tables are pruned by age, at most hourly from each object's drain (`src/retention.ts`):
- ReviewDO: ended review jobs after 30 days, except an open PR's current head's (a re-run of its check needs it) and any whose check update, or the clearing of its waiting-for-room error, is still owed.
- ProjectDO: that a worker was told of a condition on its PR at a head ([PR upkeep](#pr-upkeep)) after 30 days; nest's error events after 30 days, except a refused stop (`stop_failed`) while its stop is still failed ([outboxes](#outboxes): the only sign an agent nest wouldn't stop may still run, until the owner retries or dismisses it); triaged proposals after 30 days; ended routine runs after 90 days (none with a clean-up owed); a run's counted turns a day after it ended.
- Both: exits that came before their start named the agent (`early_exits`), after a day.

Kept: a task's history, the chat, memory, issues (a declined issue's row keeps an import from bringing it back), and anything live or owed.

## Agents that exit before they're named

An agent's `agent.exited` can overtake its create's answer. A worker's, reviewer's or routine run's exit that no row names yet is kept (`early_exits`), and the start that learns the agent from the create's answer finds it: the task stalls, the review spends an attempt, the run waits for a turn as after any exit before one. Each start also names its agent in the step the answer comes, before any other await.
