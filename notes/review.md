- **high** docs/sandbox/networking/README.md:11 (line edited by this PR) and docs/sandbox/networking/egress/steering/README.md:10 (unchanged, in a touched doc) -- both state as built that everything else is *rejected* (TCP reset, ICMP port-unreachable, "UDP/443 too, so HTTP/3 falls back to TCP" at once). The netns ruleset has no reject rule: the `input` and `forward` chains are `policy drop`, so such traffic is silently dropped and QUIC waits out a timeout. The parent summary already says so: docs/README.md:180 "(built: nest-proxy's check; the kernel rule and the reject are designed)". Leaf and parent now contradict. Evidence: crates/nestd/src/net.rs:218-227 (`type filter hook input ... policy drop;`, `hook forward ... policy drop;`, no `reject`). Mark the reject designed, not built, in both docs.
- **low** docs/README.md:180 -- "hard-denied ahead of any policy" has the same ordering problem as the egress README finding above; the check runs at dial time (crates/nest-proxy/src/http.rs:840-846). Only worth fixing alongside it.
- **medium** docs/compute/provisioning/README.md:8 (line edited by this PR) -- "Each kind's bootstrap enables only its own units ... a sandbox host still installs the agent runner" understates the code: the sandbox bootstrap enables *and starts* `nest-runner.service`. - **low** docs/sandbox/state/object-store/README.md:5 -- the line this PR edits still opens with "behind a local write-through cache", then says committed chunks don't go into the cache. Only manifests are written through; chunks are cached only on fetch or by a same-host fork's `keep_local`. Evidence: crates/nestd/src/s3.rs:469-477 (`put_chunk` doesn't cache), 504 (`put_manifest` does), 478-482 (`keep_local`).
- **high** docs/sandbox/fencing/README.md:50 ("...re-resolves its binding and is told what was lost (not built)"), docs/architecture/README.md:87 ("(and what was lost: designed)") and docs/sandbox/fencing/README.md:27 ("(not built: the move notice carries only the new epoch and host)"). These mark as unbuilt something the code does. On a move, AgentDO tells the brain what the restore lost, mid-turn as a system note or at the start of its next turn: "Your sandbox moved to another machine and was restored from its state saved at <head.created_ms>[; running processes stopped]. File changes after that were lost." What isn't built is SandboxDO's loss *record* (docs/control-plane/durable-objects/sandbox/README.md:51); the head-based notice is built. Evidence: control-plane/src/do/agent.ts:2016-2051 (`onSandboxMoved`, `movedNote` reads `headGeneration()`), 2842-2855 (`pump` prepends the note); built since #30/#62. Reword so the loss *record* is designed, while the agent is already told the restore point and that later changes (and, from a disk-only head, processes) were lost. On main, architecture:87 already had this right; this PR made it wrong.
- **low** docs/sandbox/README.md:37 -- the parent's component line "drivers/: Firecracker (primary), gVisor, Lambda MicroVM" gives no status, while this PR marks gVisor not built and Lambda rejected (drivers/README.md:8-9, gvisor/README.md:3, lambda-microvm/README.md:3).
