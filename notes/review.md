# Review: docs sandbox/compute vs code

Findings (severity, doc:line, problem, evidence)

- **medium** docs/sandbox/networking/egress/README.md:27 -- "Non-public addresses are refused by the proxy before any policy applies" (kept by the diff) now contradicts the leaf it links: policy/README.md:42 was rewritten to "whatever the policy says: the proxy checks every address it is about to dial", which is what the code does (the check is in `connect_addrs`/`is_public` at dial time, after `decide`). Evidence: crates/nest-proxy/src/http.rs:840,861; decide at http.rs:370-374 runs first. Reword the parent to match the leaf.
- **medium** docs/sandbox/networking/egress/policy/README.md:61 -- "Designed, not built: a sandbox without a policy has a connection limit of 0, so its connections are refused at once (`connection_limit`) and its DNS queries get REFUSED." reads as if the 0-limit refusal were the unbuilt design; it is today's built behaviour (the 30 s hold is what is unbuilt). Evidence: crates/nest-proxy/src/state.rs:333 (`unwrap_or(0)`), listener.rs:93 (`connection_limit`), dns.rs:46 (`Refused` without policy). Suggest "Designed, not built. Today a sandbox without a policy ...".
- **low** docs/sandbox/networking/egress/README.md:15-17 -- pipeline puts "decide the request against the current policy" after the Host/SNI name check; code decides first, then checks the request host. Evidence: crates/nest-proxy/src/http.rs:370-374 (decide) before 378 (`check_request_host`).
- **high** docs/sandbox/networking/README.md:11 (line edited by this PR) and docs/sandbox/networking/egress/steering/README.md:10 (unchanged, in a touched doc) -- both state as built that everything else is *rejected* (TCP reset, ICMP port-unreachable, "UDP/443 too, so HTTP/3 falls back to TCP" at once). The netns ruleset has no reject rule: the `input` and `forward` chains are `policy drop`, so such traffic is silently dropped and QUIC waits out a timeout. The parent summary already says so: docs/README.md:180 "(built: nest-proxy's check; the kernel rule and the reject are designed)". Leaf and parent now contradict. Evidence: crates/nestd/src/net.rs:218-227 (`type filter hook input ... policy drop;`, `hook forward ... policy drop;`, no `reject`). Mark the reject designed, not built, in both docs.
- **low** docs/README.md:180 -- "hard-denied ahead of any policy" has the same ordering problem as the egress README finding above; the check runs at dial time (crates/nest-proxy/src/http.rs:840-846). Only worth fixing alongside it.
- **medium** docs/compute/provisioning/README.md:8 (line edited by this PR) -- "Each kind's bootstrap enables only its own units ... a sandbox host still installs the agent runner" understates the code: the sandbox bootstrap enables *and starts* `nest-runner.service`. Evidence: deploy/host/bootstrap.sh:163-166 (`systemctl enable --now nest-proxy.service nestd.service nest-gateway.service nest-runner.service`); dev/deploy.md:93 ("Sandbox hosts keep the agent runner enabled"). Say "still enables the agent runner". The same sentence also ends in a tombstone-style clause ("no rollback reaches ... any more"), and bootstrap.sh:164-165's comment still says the opposite (stale code comment, out of scope here).
- **low** docs/compute/nestd/README.md:5 (line edited by this PR) -- tombstone wording kept on an edited line: "which nothing blocks any more". State the fact without the history (e.g. "nothing blocks it").
- **low** docs/compute/nestd/README.md:23 (line edited by this PR) -- "Built (M2): where its sandboxes' filesystem reflinks (probed at start), the pause covers only a `FICLONE` of the disk" leaves out that `disk_cut: auto` picks M3′'s shadow cut first wherever `shadow_cut_works`, and uses the whole-file reflink only as the fallback. Evidence: crates/nestd/src/host.rs:2928-2944 (`decide_cut`); docs/sandbox/state/disk/README.md:80 (this PR) says the same. The parent summary should mention the shadow cut, as docs/README.md:166 and state/README.md:122 do.
- **low** docs/sandbox/state/disk/README.md:78 vs :80 -- the heading still reads "(option 1 built and measured, not deployed)" while this PR drops "not deployed" from M2 everywhere (nestd:23, state:34, state:122, object-store:5) and rewrites :80 to "merged in #159; `disk_cut: auto` picks it". Deployment can't be shown from code either way, so the treatment is inconsistent. If the heading changes, docs/README.md:222 links to its anchor (`#m3-the-pause-follows-what-a-turn-changed-option-1-built-and-measured-not-deployed`) and must change with it.
- **low** docs/sandbox/state/README.md:114 -- "**Designed, not built:** a sandbox has one disk, committed whole." Same ambiguity as policy:61: the sentence after the label is today's built state, not the design (the design is the Durable / Local-only split below it). Suggest "Designed, not built (today a sandbox has one disk, committed whole):".
- **low** docs/sandbox/state/object-store/README.md:5 -- the line this PR edits still opens with "behind a local write-through cache", then says committed chunks don't go into the cache. Only manifests are written through; chunks are cached only on fetch or by a same-host fork's `keep_local`. Evidence: crates/nestd/src/s3.rs:469-477 (`put_chunk` doesn't cache), 504 (`put_manifest` does), 478-482 (`keep_local`).
